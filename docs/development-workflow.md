# 高效开发与验证流程

这份流程解决一个问题：功能不能只写得快，检查和上线也要又快又稳。

Agent 开始较大的功能、修复或数据库改动前，先按本页确定检查范围。不要做到上线时才临时决定“还要检查什么”。

## 这次为什么会慢

`0.2.0` 跨日结转上线时，主要有五个问题：

1. SQL 只通过了模拟测试，没有先用真实 MySQL 和 `aiomysql` 执行。百分号转义问题因此到服务器回算时才暴露。
2. 部署目录没有提前核对完整，缺少前端和版本文件，回算完成后才发现不能直接切换。
3. 生产验证命令是临时拼出来的，多层 Shell、中文字段和 SQL 转义反复出错。
4. 开工前没有列出固定的验收证据，检查范围在过程中不断增加。
5. 修复只改了后端 SQL，却重复执行了部分没有变化的检查。

结论很明确：生产服务器被当成了集成测试环境，验证工具本身也没有提前验证。这是流程问题，不是“检查认真”造成的。

## 开工前先写清楚四件事

开始编码前，用几行文字确定：

- 要解决什么问题。
- 会修改前端、后端、数据库还是部署配置。
- 最大风险是什么。
- 完成后用哪些证据证明正确。

没有列入这里的检查，不要在上线时随意追加。发现真正的新风险时可以补充，但要先说明原因。

## 固定开发流程

### 1. 先看代码，再定最小改动

- 找到真实入口、数据流和现有测试。
- 只修改解决本次问题需要的文件。
- 先确定兼容方式和回退方式，再动数据库。

### 2. 先做最小测试

编码过程中只运行与改动直接相关的检查：

- 前端样式：检查对应页面和组件。
- 岗位仪表盘：逐岗位检查电脑和手机 `/`、固定首页导航、旧 Dock 配置自动补齐、`/summary` 在线汇总迁移、无部门和停用社区、多个社区/片区、管理员附加模块和无权限模块不返回数据。核对职责范围与具体权限范围取交集、今天无快照显示未知、近七日贡献补零、组织聚合不含实名排名，以及数字卡跳转后的 URL 筛选与后端明细数量一致。缓存检查要覆盖同账号 30 秒内直接复用、30 秒至 5 分钟先显示后刷新、超过 5 分钟重新加载、手动刷新绕过缓存、登录退出清除及不同账号绝不串用。
- 在线工作表：检查普通和全屏状态下的工具栏、列筛选、下拉单元格和颜色浮层；浏览器全屏必须覆盖文档根节点，表格卡片只负责覆盖视口。全链条还要分别用 14 列旧表头和含“登记情况”的 15 列新表头验证读取、来源缓存、业务入库、归档、单格回写、整行新增与下发发布的物理列位置，确认旧来源和旧快照把登记情况补空，并确认研判不会落入二次反馈。核查人和社区需分别模拟腾讯文本格和真实下拉格，确认编辑器选择器不改变物理写入类型，文本格写显示文本、下拉格写真实选项 ID，写后回读按同一物理类型比较。公式栏不能显示强制文本的前导单引号，但 `7.30`、身份证号和长手机号仍须保持完整字符串；在页面中部拖动工作表底部横向滚动条时，分别制造由内容主区域和浏览器文档承担纵向滚动的布局，确认按下、拖动和松开后页面都不跳到顶部，同时不影响表格自身横向移动。
- 手机任务工作台：同时检查全端 `/` 先进入岗位仪表盘、手机 `/query` 的任务分流、电脑完整工作台、组长和组员的本人/社区范围、管理员及超级管理员的全所范围、管理员手机 Dock 的独立“流口任务”入口及 Univer 入口并存、其他岗位 403、查看和编辑权限分离、五类完成口径、卡片身份证号/手机号/全链条来源摘要、空白腾讯下拉元数据的同表复用和业务兜底、多手机号拆分与系统原生选择、非手机拨号回退、只有组长能向本社区在岗组员转派、未保存离开提醒，以及保存后停留当前任务。`0.15.8` 还要检查 POST 搜索、多选社区/核查人、空值选项、实际任务选项、关键词不入 URL、URL 刷新恢复、互斥优先级卡数量、已研判优先和已完成沉底，以及状态与复核阶段组合筛选。
- 数据下发：用合成文件检查 `.xls/.xlsx`、标题行、重复表头、文本身份证号/手机号、缺少手机号优先进入待研判且不能分配或下发、地址冲突、重复人员差异、全部业务字段修改、公式注入防护和平均分配恒等式；确认“小区管理”不再暴露一次性映射表导入接口。权限同时覆盖功能、逐权限全所范围和岗位硬限制，敏感搜索必须走 POST。审核接口检查版本 `409`、重新分类、社区停用保护、批量确认只处理明确任务、反馈 XLSX 三个工作表以及下载不改变状态。批次删除要检查仅超级管理员、未发布批次事务删除、已开始发布或有关联来源时拒绝以及脱敏审计。发布状态要分别覆盖写入前失败、请求结果不确定、正常同步对账、内容冲突两种处理、缓存待同步和逐条安全续传。真实腾讯批量发布只能在专用测试表或由项目管理人验收。
- 在线区间汇总：检查唯一任务按流水去重，“无法核实”跨日结转、同日最多一次、跨日最多两次、最终结果修正不增加有效工作量；在岗人日只累计有同步快照的日期，并覆盖工作日请假、离岗、双休日备勤、缺排班隐藏指标、社区筛选后重算总计和旧列名兼容。概览的结转、新下发、变化、待完成和已完成明细必须与卡片数量一致，按历史快照显示详情，跳过同步失败留下的缺失快照，并确认“首次下发”优先取业务下发字段而不是区间首次活动日期。完成率、见底率、两列模式、工作日志和 XLSX 必须使用同一口径。
- 汇总 XLSX：检查当前账号数据范围、日期和业务类型，表头筛选及排序后的可见行、重新计算的总计、两张工作表、数字与百分比格式和安全文件名；不能为导出重新读取更大范围的数据。在线汇总、走访汇总和下发反馈表都要写入可读的导出操作记录，并确认安全摘要不含工作簿正文、身份证号、手机号或敏感关键词。
- 前端认证：搜索本次涉及页面的原生 `fetch`，确认它使用统一认证封装；分别验证会话被顶替、空闲超时和登录密码错误，不允许页面自己维护另一套 401 跳转逻辑。登录页样式改动还要检查 1366×768、较矮桌面、900px 临界宽度及 360/390/430px 手机：警徽不得拉伸，桌面左右分栏和城市线稿不得遮挡主文案，手机只保留平台品牌与表单，深浅色主题下输入内容和错误提示都必须可读。全局滚动条改动还要检查浏览器文档、侧栏、抽屉、弹窗、下拉虚拟列表、表格横向滚动和 Univer 底部滚动条，确认浅色和深色对比度、滑块最小长度、表头列对齐及拖动时页面位置均未受影响。
- 个人资料与贡献日历：检查人员管理的桌面表格和手机卡片姓名都能进入资料详情，旧 `/people` 重定向且侧栏、账号菜单和 Dock 不再出现独立目录。只有成功的核查业务字段回写、逐条下发审核和工作日志编制会增加贡献，任务分配和普通平台操作不增加；批量审核按任务数、工作日志保存按人员/草稿/业务日幂等。检查账号改绑仍按人员归属、业务时区跨午夜、年度边界、连续天数、深色模式和手机横向滚动。公开接口和前端不得出现用户名、身份证号、手机号、权限、会话或业务正文，历史回填重复执行不能增加事件。已研判的流口任务还要在列表和详情直接显示具体研判内容，但保持只读且不改变完成口径。
- 运维操作记录：检查人员姓名、账号显示姓名和已删除账号三种回退，覆盖当前及历史操作代码、目标、结果和详情翻译；确认同步触发记录动态显示 `_sync_log` 的真实终态、找不到任务时回退原状态，在线汇总、走访汇总和下发反馈 XLSX 的导出记录能翻译为中文摘要；默认列表不再直接铺开 JSON，展开按钮保持正常方形点击区且展开项仍保留原始审计字段。
- 普通后端逻辑：运行对应单元测试和 Python 编译。
- SQL、报表、同步或迁移：必须使用测试数据库，通过真实 MySQL 和真实数据库驱动执行。
- 外部数据回写：除权限和官方请求结构测试外，还要同时检查 HTTP 状态与第三方业务返回码，并验证来源定位、版本或哈希冲突、写后读取校验、同步互斥和完整审计。没有专用测试表时不能拿生产业务表试写；把真实写入明确列为人工验收项。
- 文档：检查链接和格式。
- 迁移与运维脚本：用合成备份检查固定命令、路径穿越、大小、SHA-256、gzip、三库标识、幂等上传和7天保留；
  在Linux运行Shell语法、systemd unit、Nginx候选配置和WireGuard `/32` 路由检查。真实服务器只在脚本通过Review
  后安装，最终数据库覆盖仍保留独立人工确认门。

模拟数据库游标只能验证流程分支，不能代替真实数据库测试。

### 3. 完成后只跑一次完整检查

代码稳定后，再按改动范围执行完整检查：

| 改动类型 | 必须检查 |
| --- | --- |
| 仅文档 | 文档链接、`git diff --check` |
| 仅前端 | 相关页面、`npm.cmd run build` |
| 后端但不碰数据库 | 相关测试、完整后端测试、Python 编译 |
| SQL、同步、报表或迁移 | 相关测试、真实 MySQL 集成测试、完整后端测试、数据恒等式 |
| Compose 或 nginx | 配置检查、健康接口、端口和日志 |

某一层没有变化，就不重复检查那一层。完整检查通过后，如果代码没再改，也不要重复运行。

### 4. 合并前准备一张上线清单

上线清单必须提前写好：

- Git 提交和版本号。
- 本次需要上传的文件。
- 是否需要构建前端或后端镜像。
- 受影响的数据库和备份范围。
- 上线命令、验证命令和回退命令。
- 外部回写开关的初始状态、启用时点，以及无需真实写入也能完成的只读核验清单。

部署包必须在停机前检查：

- `backend`、`frontend/dist`、`VERSION` 等本次需要的内容是否齐全。
- 文件是否来自准备上线的同一个提交。
- 关键文件哈希是否与本地一致。

缺一项就不进入停机和数据迁移。

发布包不再由开发电脑临时拼接。提交进入 `main` 后，由 GitHub 的 `Deploy production` 手动工作流重新运行
后端测试、部署测试、Python 编译、前端测试和生产构建，再从同一个完整提交生成源码包和前端产物。发布包
记录版本、完整提交号、备份范围、文件大小和 SHA-256；服务器必须再次校验，不能接受工作区未提交文件。

手动发布固定填写三项：已经进入 `main` 的 Git ref、精确版本号和数据库备份范围。普通 push、Pull Request、
CI 通过或创建标签都不能自动触发生产切换。数据库备份范围仍按本页和运维手册判断，不能为了省时间统一选择
`none`。同一时刻只允许一个生产发布任务。

### 5. 数据迁移分成三步

涉及数据库时固定执行：

1. 在测试数据库完整跑通。
2. 在线上运行只读审计，并备份受影响的数据库。
3. 短暂停机后执行正式迁移，再原子切换程序。

日报有效工作量历史回算额外固定为：先调用正式服务做只读预览，记录受影响日期、快照和流水数量；
再备份 `daily_report`；最后通过 `scratch/` 中的一次性包装按日期升序执行并复核幂等性。一次性包装不进
Git，完成后清理。没有真实测试库时只能交付代码和模拟测试，必须把真实 MySQL 与正式回算列为未验证。

生产环境不负责发现 SQL 语法、驱动转义或脚本缺文件等基础问题。

### 6. 上线后只核对固定证据

通常只检查下面五项一次：

1. 健康接口和版本号。
2. 容器状态和近期错误日志。
3. 本次迁移的数据量、唯一性和恒等式。
4. 受影响的关键接口或页面。
5. 只有改动涉及定时任务时，才等待一次真实定时任务。

固定发布脚本已经核对健康版本、前端主资源、后端与运维代理容器、启动期错误数和发布历史；项目管理人仍要
按本次功能补充关键页面或只读数据核对。脚本失败时会恢复旧程序与旧镜像，但不会自动恢复数据库。若新版本
已经执行了外部写入或数据库迁移，必须按单独确认的业务回退方案处理，不能反复点击发布按钮。

证据已经足够时就结束，不为了“更放心”重复查询相同内容。

## 出错时的止损规则

- 同一条验证命令连续失败两次，停止继续改转义字符。
- 把复杂 SQL 或远程命令写成可检查的脚本，先在测试环境运行，再执行线上版本。
- 上线包不完整时先补齐，不把迁移、文件切换和排错混在一起。
- 生产验证发现代码问题时，恢复旧版本，在本地修复并重新走测试和 PR。
- 不在生产服务器临时修改业务代码。

## 每次任务结束时怎么汇报

只需要说明：

- 改了什么。
- 哪些检查通过。
- 哪些内容没有验证，以及原因。
- 是否已经合并和上线。
- 回退材料放在哪里。

不要用大量命令输出代替结论，也不要把同一项检查重复汇报。

## 一页检查单

- [ ] 开工前写清目标、范围、风险和验收证据。
- [ ] 先运行最小测试。
- [ ] SQL 已在真实 MySQL 和真实驱动上执行。
- [ ] 完成后按改动范围运行一次完整检查。
- [ ] 部署包在停机前确认完整。
- [ ] 备份范围与实际影响一致。
- [ ] 上线命令和回退命令已经提前准备。
- [ ] 上线后只核对固定证据。
- [ ] 定时任务没有改动时，不额外等待。
- [ ] 同一验证命令失败两次后改用脚本。
