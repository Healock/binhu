# 高效开发与验证流程

## 帮助中心与 Markdown 文档验证

- 帮助文档基线位于 `backend/help_docs/*.md`。新增或修改文档时必须运行内置文档加载检查，确认 front matter 完整、slug 唯一、order 为整数、正文以一级标题开始，并核对实际发布文档数量。
- 新功能、路由、权限、字段名称或操作步骤发生变化时，同一 PR 更新对应帮助文档；不得继续写入已下线的腾讯表操作、旧保存按钮或已经取消的人工门槛。
- 普通登录用户只验证读取、搜索、分类目录和 Markdown 展示；超级管理员额外验证编辑、预览、保存、恢复内置版本、版本冲突 409 和刷新后内容一致。
- 内置文档升级时，未自定义内容应随版本更新；已经在线自定义的标题、摘要和正文必须保留，系统分类、排序和内置摘要可以跟随新版本。重复初始化不得重复创建文档。
- 前端不得使用 `dangerouslySetInnerHTML` 渲染 Markdown。检查 GFM 表格、列表、代码块、外部链接安全属性、深浅色、900px 单列和 520px 窄屏编辑布局。
- 审计测试要确认保存和恢复只记录 slug、revision 与字符长度，不保存 Markdown 正文或用户业务资料。本机没有真实 MySQL 时，必须在 PR 中写明建表、种子更新和乐观锁事务尚未通过真实驱动验证。

## 地址匹配、小区确认与分配验证

- 首版地址匹配只启用本地 `RuleMatcher`。固定格式、缺字段、全半角、栋幢号楼、别名、历史地址、同名小区、跨街道、跨社区、低信息和空地址都要用虚构数据覆盖；不能假设标准地址一定具有统一模板。
- 规则匹配不得覆盖任务原始地址和原始社区。唯一、有效、无街道或社区冲突的 `suggested` 作为“自动匹配”直接使用；人工 `confirmed` 修正仍是最高优先级，投影重建和维护重跑不得覆盖。
- 候选先按规范化小区名和正式社区去重。去重后只有一个有效候选时应直接成为 `suggested`；测试必须单独覆盖“一个弱候选”“同一小区重复地址项”和“两个真实不同小区分数接近”，防止继续把单候选误报为 `ambiguous`。
- 人工反馈记忆只允许复用完全相同的规范化地址和正式社区。测试要覆盖重复确认计数、不同小区确认触发冲突熔断、跨社区不复用、停用小区不复用、硬冲突不被记忆覆盖，并确认反馈表和普通审计都不保存地址正文。
- 指令核查列表、详情和分配工作台必须同时核对社区、小区和匹配状态筛选。`confirmed` 或唯一可靠的 `suggested` 且来源唯一、社区一致的任务可进入单人或平均分配；`ambiguous/conflict/unmatched/invalid`、停用小区和来源异常仍必须返回明确跳过原因。
- 房屋档案要验证小区列、匹配状态、候选依据、待确认数量、单条修正、批量确认和详情展示；页面不得把匹配对象渲染成 `[object Object]`。
- 房屋维护命令固定为：`python backend/migrations/property_small_community_matching.py measure`、`migrate --apply`、`verify`。生产写入前备份 `RegistryData`；若同次发布包含在线任务投影结构，则备份范围提升为 `OnlineData + RegistryData`。
- 在线任务匹配规则升级固定执行：`python -m migrations.address_match_feedback measure`、`migrate --apply`、`verify`。先记录单候选误报数量，写入前备份 `OnlineData`，重算后核对 `ambiguous` 只剩真实多候选或无候选记录；人工 `confirmed` 数量和目标小区必须保持不变。
- 本机没有真实 MySQL 时只交付模拟测试、完整自动化测试和静态检查，并在 PR 中明确“真实 MySQL 结构、驱动和维护命令尚未验证”；不得在生产库制造测试数据补齐这一项。
- Elasticsearch 和 MGeo 未启用时，依赖、配置、网络调用和后台任务都不应出现；以后接入也只能参与召回/精排，不得绕过街道、社区、唯一性和有效状态硬约束，也不得覆盖人工确认。

## 指令核查自动保存、增量投影与所内移交验证

- 普通详情页不得保留常驻保存按钮。文本、地址和备注使用 700ms 防抖保存，选择类字段立即保存；待登记和唯一拟登记房屋一次原子提交，结构化研判继续通过专用按钮和接口提交。
- 连续输入、快速切换筛选和房屋搜索必须验证请求序号：旧请求不得覆盖新草稿、选项或任务列表。保存失败保留草稿与重试入口，409 冲突才重新读取完整详情；未分配组员取消领取后保留未保存草稿且不循环弹窗。
- 普通保存、领取、地址确认、批量分配和撤销分配要断言没有调用整业务投影重建，只增量更新实际变化的 `parser_type + row_key`。前端先局部合并成功响应，再进行不阻塞操作反馈的静默刷新。
- 批量分配测试至少覆盖唯一自动匹配、人工确认、多候选、冲突、来源异常、部分成功、版本变化、平均分配和撤销分配；每条跳过或失败都要返回明确原因。性能验收目标为单条本地保存服务端处理低于 1 秒、4 条本地批量分配低于 2 秒，网络耗时另计。
- 研判页面固定接管六类业务并默认显示全部研判阶段；每条当前“无法核实”任务必须进入明确阶段或来源异常。历史补录仅统计当前有效 canonical 来源，维护命令依次执行 `python -m migrations.unverifiable_review_backfill measure`、`migrate --apply`、`verify`，重复执行必须幂等。
- 所内移交只允许基础管控及更高管理岗位操作。验证单组长自动选择、多组长明确选择、无组长阻止、普通组员越权、版本/哈希冲突，以及社区与接手组长同事务更新。
- 第一社区与第一核查人必须同时存在才可固化，并通过不可覆盖写入保存。接手组长负责当前待办，但日报、在线汇总和个人贡献只能归第一核查人；没有可靠历史事件或日报证据时进入问题清单，不得猜测。维护命令依次执行 `python -m migrations.task_assignment_responsibility measure`、`migrate --apply`、`verify`。
- 上线前备份 `OnlineData` 和 `daily_report`，两套维护命令均先 measure、再 apply、最后 verify。本机没有真实 MySQL 时，PR 必须明确真实数据库结构、驱动、事务行为和正式维护命令尚未验证。

## 无法核实两级研判与最终导出归档

- 六类流口业务（全链条、出租房屋核查、寄递业、疑似返苏、苏州涉警、交通涉警）统一按“无法核实 → 初步研判 → 深度研判 → 最终无法核实”推进；疑似未注销模型三不进入此流程。
- 初步研判成功只进入延时复核，系统按业务日期自动将截止日期顺延 2 个完整自然日；深度研判成功顺延 1 个完整自然日。截止日当天不流转，只有业务日期晚于截止日才自动推进。
- 研判成功和失败都必须保存结构化意见。失败立即进入下一阶段，成功在延时期间等待网格员反馈；到期没有反馈也只能记录“逾期自动流转”，不能伪造网格员反馈。
- 初步待研判、深度待研判允许按研判页当前筛选和排序导出统一 XLSX。基础管控只填写“本次研判决定”和“研判意见”后回导；系统逐行复用结构化研判接口，校验业务类型、来源 ID、来源版本、行哈希、流程版本和阶段。空白决定跳过，过期或冲突行明确失败，不能新建任务或覆盖最新数据。
- 网格员在延时期间改为正式结果时立即结束本轮；正式结果再次变为“无法核实”时创建新轮次，不复用历史研判。来源删除、重复、版本或行哈希变化、社区/业务主键变化时进入来源异常，禁止自动导出。
- 只有最终无法核实才可在当前业务任务列表的归档 Panel 中预览、确认和执行最终归档导出。导出文件先持久化，随后在本地事务中写入对应历史表并移出当前任务池；任一本地步骤失败都必须保留当前任务并显示冲突，不得恢复腾讯删除或写回路径。
- 待研判工作簿导出与最终归档导出必须明确分开：前者只服务离线研判和回导，不归档、不删除、不伪装成最终无法核实。
- 流口任务列表、房屋档案、人员档案和机构档案导出时，后端必须复用页面当前筛选、权限范围与稳定排序，并查询完整结果；验证页面第一行与工作簿第一条业务数据一致，不能拼接浏览器当前分页。
- 研判正文和反馈正文不进入普通日志或审计详情；审计只记录阶段、业务类型、操作和安全原因代码。所有自动推进、写回和归档任务必须幂等，并在服务重启后可恢复或安全暂停。

## 全链条已登记自动确认与归档验证

- 不再通过公安网原始数据判断“已登记”。开发和测试不得新增公安网上传入口，也不得在候选 SQL 中读取 `_fullchain_police_raw_uploads` 或 `_fullchain_police_raw_identities`；旧 POST 入口固定返回 410，历史列表和下载保持原权限只读。
- 自动确认必须证明两个不同扫描周期连续匹配同一地址 HMAC，并且腾讯写回成功后才进入 `confirmed`。来源上下文刷新失败时必须回到人工复核，不能记录确认成功事件，也不能开始 24 小时计时。
- 归档候选测试至少覆盖：缺少确认链、未满 24 小时、精确满 24 小时、来源/身份/社区变化、房屋停用或版本变化、来源重复、本地待写回/冲突、已进入其他批次。测试时间必须验证完整小时边界，不能只验证日期变化。
- 创建批次后、腾讯删除前必须重新验证冻结登记证据。验证失败时断言腾讯客户端没有收到读取或删除调用；腾讯已明确删除后的恢复测试则不得重新执行登记证据校验或删除，只能使用冻结快照完成平台对账。
- 前端验收确认数据上传中心已无公安网入口；全链条归档区仍能只读下载历史材料；任务详情和候选列表按系统时区显示确认时间、保留期结束时间及是否已满足完整 24 小时。

## 房屋档案走访历史关联验证补充

- 房屋档案和走访明细继续分别保存在 RegistryData、VisitData，不复制走访正文，不建立跨库外键。
- 只允许使用“当前权限范围内房屋 + 正式社区 + 标准化地址摘要”精确关联；有效地址别名和地址版本历史可以参与匹配，禁止用地址包含、前缀或其他模糊规则串联不同房屋。
- 房屋列表必须批量读取走访摘要，不得逐房产生 N+1 查询；列表只展示最近走访日期和最近星级评定，走访次数与具体历史只在详情中展示。
- 历史走访接口必须沿用 `registry.property.view` 和房屋社区数据范围，使用服务端分页；不得返回身份证号、手机号或星级隐患正文。
- 使用虚构数据覆盖当前地址、别名、旧地址版本、跨社区隔离、同社区同地址歧义、无走访、分页和星级为空场景。

- 发布默认关闭 `task_graph_enabled`。先做只读预览，再回填 WorkflowData 图表并仅向超级管理员开启；测试和审计不得记录业务正文。

## v0.23.0 Rete.js 自动编排原型验证补充

- Rete.js 原型必须使用独立延迟加载路由，仅超级管理员可进入，不替换或破坏现有 React Flow 任务流页面。
- 画布节点代表“工作类型和任务队列”，不能把每条真实业务任务直接铺成一个节点；当前节点至少覆盖下发、审核、发布分配、网格核查、基础管控研判、调照片和完成归档。
- 节点数量使用现有只读接口聚合，点击“进入队列”只能跳转现有业务页面；原型不得修改任务状态、数据库、腾讯表格或现有权限边界。
- Rete 区域应支持拖动、缩放和端口连线，ELK 自动布局按从左到右的依赖关系排列；等待研判和调照片继续作为可见协作节点保留。
- Rete 运行库必须按路由拆包，普通页面首屏不能直接加载编辑器；新增依赖需要锁定在 `package-lock.json` 并通过生产构建。

## 这次为什么会慢

`0.2.0` 跨日结转上线时，主要有五个问题：

1. SQL 只通过了模拟测试，没有先用真实 MySQL 和 `aiomysql` 执行。百分号转义问题因此到服务器回算时才暴露。
2. 部署目录没有提前核对完整，缺少前端和版本文件，回算完成后才发现不能直接切换。
3. 生产验证命令是临时拼出来的，多层 Shell、中文字段和 SQL 转义反复出错。
4. 开工前没有列出固定的验收证据，检查范围在过程中不断增加。
5. 修复只改了后端 SQL，却重复执行了部分没有变化的检查。

结论很明确：生产服务器被当成了集成测试环境，验证工具本身也没有提前验证。这是流程问题，不是“检查认真”造成的。

## 固定开发流程

### 1. 先看代码，再定最小改动

- 找到真实入口、数据流和现有测试。
- 只修改解决本次问题需要的文件。
- 先确定兼容方式和回退方式，再动数据库。

### 2. 先做最小测试

编码过程中只运行与改动直接相关的检查：

- 前端样式：检查对应页面和组件。
- 岗位仪表盘：逐岗位检查电脑和手机 `/`、电脑侧栏固定首页、手机顶部品牌返回首页且 Dock 只显示首页之外最多四类、旧 Dock 配置兼容、`/summary` 在线汇总迁移、无部门和停用社区、多个社区/片区、管理员附加模块和无权限模块不返回数据。桌面还要确认双列瀑布流不会因左右卡片高度不同留下整行空白，手机保持单列。核对职责范围与具体权限范围取交集、今天无快照显示未知、近七日贡献补零、组织聚合不含实名排名，以及数字卡跳转后的 URL 筛选与后端明细数量一致。缓存检查要覆盖同账号 30 秒内直接复用、30 秒至 5 分钟先显示后刷新、超过 5 分钟重新加载、手动刷新绕过缓存、登录退出清除及不同账号绝不串用。

- 照片批次：用虚构的同身份证多工单覆盖 `queued`、`in_progress`、`pending_requester` 和已终结状态。确认 ZIP 后，未领取和处理中工单都应获得附件并完成，待申请人补充只进入人工提示；历史已确认批次必须先只读预览遗漏数量，再明确确认复制同 SHA-256 附件。来源行缺失时不得创建无法定位的自动腾讯回写任务，重复预览或确认不得重复附件、事件或通知。
- 在线区间汇总：检查唯一任务按流水去重，“无法核实”跨日结转、同日最多一次、跨日最多两次、最终结果修正不增加有效工作量；在岗人日只累计有同步快照的日期，并覆盖工作日请假、离岗、双休日备勤、缺排班隐藏指标、社区筛选后重算总计和旧列名兼容。概览的结转、新下发、变化、待完成和已完成明细必须与卡片数量一致，按历史快照显示详情，跳过同步失败留下的缺失快照，并确认“首次下发”优先取业务下发字段而不是区间首次活动日期。完成率、见底率、两列模式、工作日志和 XLSX 必须使用同一口径。
- 汇总 XLSX：检查当前账号数据范围、日期和业务类型，表头筛选及排序后的可见行、重新计算的总计、两张工作表、数字与百分比格式和安全文件名；不能为导出重新读取更大范围的数据。在线汇总、走访汇总和下发反馈表都要写入可读的导出操作记录，并确认安全摘要不含工作簿正文、身份证号、手机号或敏感关键词。
- 工作每日明细 XLSX：使用合成人员和统计数据检查 22 列表头、合并单元格、列宽、行高、边框、打印区域和仅保留 `Sheet1`；确认示例姓名、数字、备注和背景色不进入输出。分别覆盖出租房/自购房目标数、岗位对应类别、日报快照“已核查＋已完成”、无快照留空、请假、周末备勤、超过 64 人扩展行、账号目标数记忆及安全操作记录。
- 前端认证：搜索本次涉及页面的原生 `fetch`，确认它使用统一认证封装；分别验证会话被顶替、空闲超时和登录密码错误，不允许页面自己维护另一套 401 跳转逻辑。登录页样式改动还要检查 1366×768、较矮桌面、900px 临界宽度及 360/390/430px 手机：警徽不得拉伸，桌面左右分栏和城市线稿不得遮挡主文案，手机只保留平台品牌与表单，深浅色主题下输入内容和错误提示都必须可读。全局滚动条改动还要检查浏览器文档、侧栏、抽屉、弹窗、下拉虚拟列表、表格横向滚动和 Univer 底部滚动条，确认浅色和深色对比度、滑块最小长度、表头列对齐及拖动时页面位置均未受影响。
- 个人资料与贡献日历：检查人员管理的桌面表格和手机卡片姓名都能进入资料详情，旧 `/people` 重定向且侧栏、账号菜单和 Dock 不再出现独立目录。只有成功的核查业务字段回写、逐条下发审核和工作日志编制会增加贡献，任务分配和普通平台操作不增加；批量审核按任务数、工作日志保存按人员/草稿/业务日幂等。检查账号改绑仍按人员归属、业务时区跨午夜、年度边界、连续天数、深色模式和手机横向滚动。公开接口和前端不得出现用户名、身份证号、手机号、权限、会话或业务正文，历史回填重复执行不能增加事件。已研判的流口任务还要在列表和详情直接显示具体研判内容，但保持只读且不改变完成口径。
- 人员管理：使用只有 `personnel.basic.view` 的账号检查桌面表格和手机卡片都显示电话，并允许按电话搜索；没有 `personnel.sensitive.view` 时仍不能看到备注、请假原因和完整出勤记录。身份证号及填写状态继续只向超级管理员返回。
- 运维操作记录：检查人员姓名、账号显示姓名和已删除账号三种回退，覆盖当前及历史操作代码、目标、结果和详情翻译；确认同步触发记录动态显示 `_sync_log` 的真实终态、找不到任务时回退原状态，在线汇总、走访汇总和下发反馈 XLSX 的导出记录能翻译为中文摘要；默认列表不再直接铺开 JSON，展开按钮保持正常方形点击区且展开项仍保留原始审计字段。
- 普通后端逻辑：运行对应单元测试和 Python 编译。
- SQL、报表、同步或迁移：必须使用测试数据库，通过真实 MySQL 和真实数据库驱动执行。
- 腾讯同步读取：覆盖同主键多来源、代表行稳定性、来源骤降二次确认、异常读取不替换缓存或归档、连续失败通知去重和首次恢复通知；生产发布前只能做只读来源预览，不能为测试制造或修改腾讯业务行。
- 告知书后台读取：用虚构分页覆盖任务创建去重、逐页进度、页面刷新恢复、断点最后一页摘要复核、来源变化后强制重读、请求超时后的继续、服务重启状态恢复、成功预览幂等和临时分页正文清理。前端轮询不能携带用户活动标记，失败日志和审计只能保存任务 ID、页码、数量及错误类型。
- 外部数据回写：除权限和官方请求结构测试外，还要同时检查 HTTP 状态与第三方业务返回码，并验证来源定位、版本或哈希冲突、写后读取校验、同步互斥和完整审计。没有专用测试表时不能拿生产业务表试写；把真实写入明确列为人工验收项。
- 固定生产发布脚本：部署测试除固定命令、包边界和回退路径外，还要检查接收、校验解压、预检、镜像构建、程序备份、数据库备份、文件切换、容器重建和健康检查九段耗时字段；计时只能增加观察信息，不能绕过任何安全步骤。
- 文档：检查链接和格式。
- 迁移与运维脚本：用合成备份检查固定命令、路径穿越、大小、SHA-256、gzip、八库标识和7天保留；在 Linux
  运行 Shell 语法、systemd unit 和 Nginx 候选配置检查。WireGuard/异地备份脚本只作为历史归档，不属于当前发布链路。
  真实服务器只在脚本通过 Review 后安装，最终数据库覆盖仍保留独立人工确认门。

模拟数据库游标只能验证流程分支，不能代替真实数据库测试。

### 3. 完成后只跑一次完整检查

代码稳定后，再按改动范围执行完整检查：

| 改动类型 | 必须检查 |
| --- | --- |
| 仅文档 | 文档链接、`git diff --check` |
| 仅前端 | 相关页面、`npm.cmd run build` |
| 后端但不碰数据库 | 相关测试、完整后端测试、Python 编译 |
| SQL、同步、报表或迁移 | 相关测试、真实 MySQL 集成测试、完整后端测试、数据恒等式 |
| Compose 或 nginx | 配置检查、健康接口、端口和日志 |

某一层没有变化，就不重复检查那一层。完整检查通过后，如果代码没再改，也不要重复运行。

### 4. 合并前准备一张上线清单

上线清单必须提前写好：

- Git 提交和版本号。
- 本次需要上传的文件。
- 是否需要构建前端或后端镜像。
- 受影响的数据库和备份范围。
- 上线命令、验证命令和回退命令。
- 外部回写开关的初始状态、启用时点，以及无需真实写入也能完成的只读核验清单。

部署包必须在停机前检查：

- `backend`、`frontend/dist`、`VERSION` 等本次需要的内容是否齐全。
- 文件是否来自准备上线的同一个提交。
- 关键文件哈希是否与本地一致。

缺一项就不进入停机和数据迁移。

发布包不再由开发电脑临时拼接。提交进入 `main` 后，由 GitHub 的 `Deploy production` 手动工作流重新运行
部署测试始终运行；后端范围运行后端测试和 Python 编译，前端范围运行前端测试和生产构建，完整范围两者都运行。
`release_scope=auto` 会先读取生产最近一次成功发布的提交：纯后端运行代码生成仅含 `VERSION + backend/` 的精简包，
纯前端运行代码生成仅含 `VERSION + frontend/dist` 的精简包；前后端同时变化、Compose、Nginx、部署脚本、未知路径
或无法验证生产祖先提交时自动回退为完整包。发布包记录版本、完整提交号、备份
范围、发布范围、文件大小和 SHA-256；服务器必须再次校验，不能接受工作区未提交文件。

手动发布固定填写四项：已经进入 `main` 的 Git ref、精确版本号、数据库备份范围和发布范围（`auto`、`backend`、
`frontend` 或 `full`）。普通 push、Pull Request、
CI 通过或创建标签都不能自动触发生产切换。数据库备份范围仍按本页和运维手册判断，不能为了省时间统一选择
`none`。同一时刻只允许一个生产发布任务。

### 5. 数据迁移分成三步

涉及数据库时固定执行：

1. 在测试数据库完整跑通。
2. 在线上运行只读审计，并备份受影响的数据库。
3. 短暂停机后执行正式迁移，再原子切换程序。

日报有效工作量历史回算额外固定为：先调用正式服务做只读预览，记录受影响日期、快照和流水数量；
再备份 `daily_report`；最后通过 `scratch/` 中的一次性包装按日期升序执行并复核幂等性。一次性包装不进
Git，完成后清理。没有真实测试库时只能交付代码和模拟测试，必须把真实 MySQL 与正式回算列为未验证。

生产环境不负责发现 SQL 语法、驱动转义或脚本缺文件等基础问题。

### 6. 上线后只核对固定证据

通常只检查下面五项一次：

1. 健康接口和版本号。
2. 容器状态和近期错误日志。
3. 本次迁移的数据量、唯一性和恒等式。
4. 受影响的关键接口或页面。
5. 只有改动涉及定时任务时，才等待一次真实定时任务。

固定发布脚本已经核对健康版本、前端主资源、后端与运维代理容器、启动期错误数和发布历史；项目管理人仍要
按本次功能补充关键页面或只读数据核对。脚本失败时会恢复旧程序与旧镜像，但不会自动恢复数据库。若新版本
已经执行了外部写入或数据库迁移，必须按单独确认的业务回退方案处理，不能反复点击发布按钮。

证据已经足够时就结束，不为了“更放心”重复查询相同内容。

## 出错时的止损规则

- 同一条验证命令连续失败两次，停止继续改转义字符。
- 把复杂 SQL 或远程命令写成可检查的脚本，先在测试环境运行，再执行线上版本。
- 上线包不完整时先补齐，不把迁移、文件切换和排错混在一起。
- 生产验证发现代码问题时，恢复旧版本，在本地修复并重新走测试和 PR。
- 不在生产服务器临时修改业务代码。

## 每次任务结束时怎么汇报

只需要说明：

- 改了什么。
- 哪些检查通过。
- 哪些内容没有验证，以及原因。
- 是否已经合并和上线。
- 回退材料放在哪里。

不要用大量命令输出代替结论，也不要把同一项检查重复汇报。

## 一页检查单

### 全链条导出归档验收

1. 用虚构数据分别验证离苏、无需登记、移交（所外）可预览并导出；确认导出历史可重复下载。
2. 验证移交（所内）、历史移交、截止日期后的无法核实都必须先审核；保留决定仍留在任务池，归档决定才进入预览。
3. 使用自然产生的待登记任务确认两个独立居住证扫描周期后才写回“已登记”；写回确认时间未满完整 24 小时时不可选择，满 24 小时后才进入候选。
4. 检查旧“已登记”但没有确认链的数据保持不可归档；在腾讯表格制造版本、行哈希、重复来源、房屋版本或同步冲突，确认后台在删除前显示冲突而不是自动删除或隐藏。
5. 检查后台进度、重启恢复为部分完成、导出文件和历史公安网材料只读下载；本功能发布建议使用 `backup_scope=online`，若同批还有其他跨库结构调整则提升为 `backup_scope=all`。

- [ ] 先运行最小测试。

- [ ] 完成后按改动范围运行一次完整检查。
- [ ] 部署包在停机前确认完整。
- [ ] 备份范围与实际影响一致。
- [ ] 上线命令和回退命令已经提前准备。
