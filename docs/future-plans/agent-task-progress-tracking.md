# Agent 复杂任务进度追踪

- 当前状态：已确定方向，未开始实施
- 文档类型：Agent 长任务协作、进度展示与状态治理计划
- 计划边界：本文件只定义后续实现方案，不代表已经增加进度工具、修改 Agent 规则或改变现有开发流程
- 目标：让项目管理人能够看到复杂工程当前做到哪一步、已经完成什么、有什么证据、卡在哪里以及下一步由谁处理

## 为什么需要这个项目

简单功能通常可以由 Agent 在一个 PR 中完成，但架构升级、跨服务改造、数据迁移、环境治理和多端适配往往不能一步完成。此类任务如果只依赖最终 PR 或聊天消息，会出现几个问题：

- 任务尚未形成 PR 时，无法直观看到已经完成的调查、设计和实现阶段；
- Agent 可以报告一个百分比，但没有说明百分比的计算依据；
- 编码完成、测试通过、Dev 部署、Staging 验收和 Production 发布容易被混成一个“完成”；
- 子 Agent 并行工作时，主 Agent 不容易汇总各自结果和阻塞项；
- Agent 长时间等待构建、测试、部署或用户决策时，外部人员看不出它是在工作还是已经卡住。

本项目建立一个由里程碑、证据和事件组成的任务进度台账。进度条只反映可验证的工作项，不按代码行数、聊天长度或 Agent 的主观判断计算。

## 目标模型

### 一个复杂工程对应一个任务台账

每个需要跨多个阶段完成的工程使用稳定的 `task_id`，建议目录结构如下：

```text
docs/work-items/<task-id>/
├── plan.md
├── progress.json
├── events.jsonl
└── evidence/
```

文件职责固定如下：

| 文件 | 职责 |
| --- | --- |
| `plan.md` | 描述目标、范围、阶段、完成条件、风险和停止条件 |
| `progress.json` | 保存当前机器可读状态，供报告和进度条读取 |
| `events.jsonl` | 追加记录每次状态变化，不覆盖历史事件 |
| `evidence/` | 保存测试、构建、PR、部署和验收证据的安全摘要或链接 |

临时调试输出、真实业务数据、凭据、令牌、Cookie、身份证号、手机号、完整地址和外部系统响应正文不得写入任务台账。

### 进度由里程碑加权计算

默认里程碑权重如下，具体任务可以在 `plan.md` 中调整，但调整后必须说明理由：

| 里程碑 | 默认权重 | 完成条件 |
| --- | ---: | --- |
| 需求、边界和完成标准 | 5% | 目标、范围、禁止事项和完成判定已经写清 |
| 现状调查 | 10% | 相关代码、文档、环境、数据边界和影响面已经有证据 |
| 方案设计和回滚设计 | 15% | 接口、兼容策略、迁移路径、回滚入口和验收方案已经确定 |
| 核心工程实现 | 30% | 计划中的代码、配置或脚本改动已完成并形成可审查差异 |
| 自动化验证 | 15% | 相关测试、静态检查、构建或编译已经执行并记录结果 |
| Dev 验证 | 10% | Dev 环境身份、运行契约和目标功能验证完成 |
| Staging 验证 | 5% | 预发布环境验证完成，问题和限制已经记录 |
| PR、合并、发布和业务验收 | 10% | PR、CI、部署、环境验收和业务验收分别记录 |

总进度由各里程碑状态和权重计算。里程碑内部可以记录 `percent`，但一个里程碑的内部百分比不能直接冒充整个工程的完成百分比。

### 任务状态和里程碑状态分开

任务状态至少支持：

```text
planned
in_progress
waiting_for_test
waiting_for_deployment
needs_user
blocked
paused
completed
cancelled
```

里程碑状态至少支持：

```text
not_started
in_progress
completed
blocked
skipped_with_reason
```

状态必须伴随 `current_action`、`next_action`、`blockers` 和 `updated_at`。没有新的验证结果时，Agent 不得为了让进度条前进而修改百分比。

## `progress.json` 最小格式

每个任务的当前状态至少包含以下字段：

```json
{
  "task_id": "event-pipeline-upgrade",
  "title": "Dev event pipeline architecture upgrade",
  "status": "in_progress",
  "overall_percent": 52,
  "current_milestone": "M4",
  "current_action": "实现 outbox relay 的重试和幂等边界",
  "next_action": "运行重复事件、断线恢复和版本冲突测试",
  "updated_at": "2026-09-14T08:30:00Z",
  "updated_by": "codex",
  "milestones": [
    {
      "id": "M1",
      "title": "需求、边界和完成标准",
      "weight": 5,
      "status": "completed",
      "percent": 100,
      "completion_criteria": [
        "已记录任务范围和明确不做事项"
      ],
      "evidence": [
        "docs/work-items/event-pipeline-upgrade/plan.md"
      ]
    },
    {
      "id": "M4",
      "title": "核心工程实现",
      "weight": 30,
      "status": "in_progress",
      "percent": 40,
      "completion_criteria": [
        "outbox relay 重试和幂等边界通过相关测试"
      ],
      "evidence": [],
      "current_action": "实现重复事件保护"
    }
  ],
  "links": {
    "prs": [],
    "commits": [],
    "deployment_runs": [],
    "acceptance_records": []
  },
  "blockers": [],
  "next_update_condition": "完成重复事件测试后更新状态"
}
```

示例中的任务名称和证据路径只用于说明字段结构，真正任务必须使用实际任务 ID 和实际证据。`overall_percent` 应由工具根据里程碑计算并校验，不能由 Agent 随意填写一个与里程碑不一致的数字。

## 进度条必须同时展示四条线

复杂工程的总进度不能掩盖交付阶段。报告至少显示：

```text
方案与调查    [██████████] 100%
工程实现      [██████░░░░]  60%
自动化验证    [███░░░░░░░]  30%
环境与交付    [░░░░░░░░░░]   0%
```

同时单独显示：

```text
工程进度：52%
PR 状态：尚未创建
Dev：未部署
Staging：未部署
Production：未部署
```

工程进度和交付进度不得合并成一个模糊的“已上线”状态。一个任务可以处于“工程实现完成、PR CI 通过、Dev 已部署、Staging 未验收”，报告必须保持这种差异。

## PR 和环境状态的关联

如果功能可以拆成多个可审查单元，应把 PR 作为子交付项挂到任务台账：

```text
任务 T-001：事件管线架构升级
├── PR #701：数据结构兼容层
├── PR #702：后端事件写入
├── PR #703：消费端投影
├── PR #704：Dev 部署和验证
└── PR #705：监控、文档和发布台账
```

每个 PR 至少记录：

- PR 编号和标题；
- 当前分支和 head commit；
- 目标分支；
- PR 状态；
- 远程 CI 状态；
- 是否已合并；
- 合并提交；
- 部署到哪些环境；
- 哪些环境验收完成。

任务台账应链接多环境发布清单中的 `deployment_run_id` 和 commit。这样可以同时回答：

- Agent 正在做哪一个工程阶段；
- 哪些 PR 已经产生；
- 哪些 PR 已经合并；
- 哪些 PR 已经部署到 Dev、Staging 或 Production；
- 当前环境差异是否阻塞任务完成。

环境发布清单的具体结构由[多环境版本与 PR 可追溯治理](environment-release-traceability.md)计划定义，本项目只保存关联关系，不复制整份环境历史。

## Agent 状态更新协议

复杂任务开始时，主 Agent 必须先建立 `plan.md` 和 `progress.json`，再进入调查或实现。每完成一个可验证里程碑，立即执行以下更新：

1. 更新 `progress.json` 的任务状态、总进度、当前里程碑、当前动作和下一步。
2. 在 `events.jsonl` 追加一条事件，记录更新时间、更新者、状态变化、完成内容、证据、阻塞项和下一步。
3. 将新的 commit、测试、构建、PR、部署或验收编号写入对应关联字段。
4. 如果状态为 `blocked`、`needs_user` 或 `waiting_for_deployment`，明确写出等待对象、阻塞原因和恢复条件。
5. 只有满足里程碑完成条件并存在证据时，才将状态改为 `completed`。

推荐的事件格式如下：

```json
{
  "event_id": "2026-09-14T08:30:00Z-M4",
  "task_id": "event-pipeline-upgrade",
  "updated_by": "codex",
  "status": "in_progress",
  "milestone": "M4",
  "overall_percent": 52,
  "completed": ["已完成重复事件保护的第一版实现"],
  "current_action": "补充断线恢复测试",
  "next_action": "运行后端相关测试",
  "evidence": ["commit:abc1234"],
  "blockers": [],
  "created_at": "2026-09-14T08:30:00Z"
}
```

事件文件只能追加，不能用后一次状态覆盖历史。更新失败时必须保留原状态，并在下一次可写时补充失败原因；不能显示一个没有事件证据的“已完成”状态。

## 实时更新频率和等待状态

Agent 在正常工作期间应在以下节点更新：

- 开始调查、设计、编码、测试、部署或验收阶段时；
- 完成一个可验证里程碑时；
- 产生 commit、PR、CI、部署 Run 或验收记录时；
- 遇到阻塞、失败、等待用户决策或等待外部环境时；
- 长时间运行任务至少每 10 分钟更新一次，说明当前正在等待的具体命令、测试、构建、工作流或部署对象。

“等待”也是一种有效状态。例如：

```text
状态：waiting_for_test
当前动作：等待 frontend CI run 结束
阻塞项：本机没有完整 Node 依赖，不能替代远程检查
下一步：CI 完成后读取失败步骤或通过结果
```

进度条在等待期间可以保持不变，但最后更新时间和等待对象必须实时变化。重复刷新相同状态不能伪造工作进度。

## 子 Agent 协作规则

子 Agent 不直接覆盖主任务的 `progress.json`。每个子 Agent 使用独立的子任务 ID，并向主 Agent 返回结构化结果：

```json
{
  "subtask": "backend-event-write",
  "status": "completed",
  "result": "已完成 outbox 写入边界设计",
  "evidence": [
    "docs/work-items/event-pipeline-upgrade/backend-design.md"
  ],
  "commits": [],
  "tests": [],
  "blockers": []
}
```

主 Agent 负责：

- 判断子任务结果是否满足主里程碑完成条件；
- 汇总总进度和交付状态；
- 处理不同子 Agent 之间的冲突；
- 将 commit、测试、PR、部署和验收关联到主任务；
- 对项目管理人提供唯一的总状态。

如果子 Agent 报告与 Git、测试或部署证据不一致，以实际检查结果为准，并把差异记录为阻塞或问题，不直接合并进度。

## 查看方式

第一阶段先提供只读命令行报告和 Markdown 状态文件：

```powershell
python tools/task_progress.py --task event-pipeline-upgrade
python tools/task_progress.py --task event-pipeline-upgrade --watch
python tools/task_progress.py --all --format markdown
```

默认报告显示：

- 任务名称、状态、总进度和最后更新时间；
- 方案、实现、验证和交付四条进度条；
- 当前里程碑和当前动作；
- 已完成内容、下一步和阻塞项；
- 关联 PR、commit、CI、部署 Run 和验收记录；
- 工程进度与 Dev、Staging、Production 交付状态；
- 需要用户或项目管理人处理的动作。

`--watch` 只重新读取状态文件和事件记录，不直接修改任务状态。后续如果需要页面，应复用同一份 `progress.json` 和 `events.jsonl`，不能另建一套互相矛盾的状态来源。

## 必须更新 `AGENTS.md`

本项目实施时必须同步更新根目录 [AGENTS.md](../../AGENTS.md)，把以下规则写入 Agent 开始工作、长任务执行和交付汇报部分：

- 复杂任务开始前建立任务计划和 `progress.json`；
- 任务拆分为有明确完成条件和证据的里程碑；
- 每完成一个里程碑立即更新 `progress.json` 和追加 `events.jsonl`；
- 更新内容必须包含当前进度、当前动作、已完成内容、下一步、阻塞项和关联证据；
- 代码、测试、构建、PR、合并、部署和业务验收分别记录；
- 等待测试、部署或用户决策时使用明确等待状态，不把等待显示成正常开发中；
- 子 Agent 使用子任务汇报，由主 Agent 汇总总进度；
- 没有新的验证证据不得虚构进度，不能用“基本完成”“差不多完成”作为完成标准；
- 进度台账不得保存凭据、真实业务数据或敏感业务正文；
- 任务完成前要核对计划、进度事件、Git 状态、PR、环境发布清单和验收证据。

在 `AGENTS.md` 实际更新并通过文档检查前，这套协议只属于未来计划，不自动约束当前任务。

## 实施拆分

### 阶段一：任务台账和状态 schema

- 定义任务、里程碑、事件、阻塞项和证据引用的数据结构。
- 实现 `progress.json` 读写校验，拒绝权重总和不一致、百分比越界、完成里程碑缺少证据和非法状态转换。
- 实现 `events.jsonl` 追加器，保证历史事件不被覆盖，并限制输出字段不包含敏感正文。
- 编写正常推进、等待、阻塞、恢复和完成的单元测试。

### 阶段二：进度计算和只读报告

- 实现按权重计算总进度和四条阶段进度。
- 实现 Markdown、纯文本和 JSON 三种报告格式。
- 报告显示当前动作、下一步、阻塞项、最后更新时间和证据链接。
- 对没有进度台账、台账损坏或长时间未更新的任务显示明确的追踪异常。

### 阶段三：PR、commit 和环境关联

- 读取本地 Git 状态、远程 PR 元数据和多环境发布清单。
- 把任务子 PR、commit、CI、部署 Run 和验收记录关联起来。
- 分别显示工程阶段进度、PR 生命周期和各环境交付状态。
- 对 Dev 分支领先服务器、Staging 未绑定 commit 和 Production 紧急发布等情况显示可执行处理路径。

### 阶段四：主 Agent 与子 Agent 协作

- 为子任务定义结构化结果协议。
- 主 Agent 汇总子任务结果，拒绝未经证据核对的完成状态。
- 记录子任务之间的依赖、冲突、失败和恢复关系。
- 支持一个主任务下多个相互独立的子任务，但不允许并行写入同一个总进度文件。

### 阶段五：规则接入和可视化

- 按本文件要求更新 `AGENTS.md`，并为规则增加可执行的文档或工具检查。
- 在本地命令可用后，再考虑接入运维工作台或 Codex 面板。
- 页面和命令都只读取同一套任务台账，不新增第二个进度真相源。

## 验收标准

完成本项目后，至少满足以下条件：

- 新建一个包含至少四个阶段的合成任务，可以通过命令看到实时总进度和四条阶段进度。
- 每个进度变化都有追加事件，事件包含时间、更新者、当前动作、下一步、阻塞项和证据。
- 修改里程碑状态后，工具能拒绝权重总和错误、百分比越界和缺少完成证据的状态。
- 任务可以准确区分进行中、等待测试、等待部署、等待用户、阻塞、暂停和完成。
- 一个任务可以关联多个 PR、commit、CI、部署 Run 和环境验收，并分别显示其状态。
- Dev 分支领先服务器、Staging 缺少 commit 和 Production 紧急发布时，报告能显示差异而不虚构统一版本。
- 子 Agent 不能覆盖主任务总进度；主 Agent 汇总前必须核对子任务证据。
- 进度报告、事件和证据摘要不包含凭据、真实业务数据或敏感业务正文。
- 根目录 `AGENTS.md` 已补充并通过文档检查；规则明确要求实时更新进度和分别记录 PR、部署、验收状态。
- 测试、构建、PR、部署和业务验收结果分别记录，不能把进度条本身当作完成证据。

## 停止条件和明确不做

出现以下情况时，任务必须标记为追踪异常或阻塞，不能继续显示为正常完成：

- 进度百分比与里程碑状态不一致；
- 里程碑标记完成但没有可核对证据；
- `events.jsonl` 无法追加或历史事件被覆盖；
- 当前状态超过规定时间没有更新，且没有明确等待对象；
- PR、commit、部署或验收记录与实际 GitHub、Git 或环境状态不一致；
- 子 Agent 报告与实际验证结果冲突；
- 状态文件包含敏感业务正文或凭据。

本项目不做以下事情：

- 不用代码行数、文件数量、聊天次数或时间流逝推算进度；
- 不让进度条替代测试、CI、部署或业务验收；
- 不允许多个 Agent 无协调地覆盖同一个总进度文件；
- 不因定时刷新而制造虚假的进度事件；
- 不在没有授权时自动提交、合并、部署或修改生产数据；
- 不把当前计划写入 `AGENTS.md` 前的内容当作已经生效的项目规则。
