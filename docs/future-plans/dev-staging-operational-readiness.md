# Dev 与 Staging 投入开发流程计划

- 当前状态：Dev event-pipeline 的任务元数据投影/计数域核心门禁已通过；Staging 晋级评估已提交，等待独立评审，尚未部署或签署 Staging 日常开发流程可用
- 目标：Dev 可承载开发与架构实验，Staging 可承载候选版本回归和 75 人压测
- 边界：不改变生产业务数据、腾讯下线路径或生产运行方式；Shadow 仅在替代能力验收后退役

## 目标职责

Dev 使用独立 Compose 项目、数据库、网络、Cookie、卷和密钥，使用虚构或已脱敏数据。它是开发者提交分支后的部署、功能调试、Kafka/Schema Registry/Flink/Redis 实验和小规模集成验收环境。未完成验证的架构能力必须在 Dev 内明确标记，不能默认晋级 Staging。

Staging 使用生产脱敏副本和与候选版本一致的制品，承担发布前回归、数据关系验证、权限与并发检查及 75 人、30 分钟真实前端请求模型压测。Staging 不写生产，不连接腾讯或其他生产外部写入服务。

## 投入使用前的工作包

### 1. 版本与部署基线

- 统一记录提交、版本号、镜像摘要、数据库迁移版本和配置摘要。
- Dev 部署指定分支或候选提交；Staging 只部署 Dev 验收通过的同一制品，不从工作树临时构建另一份代码。
- 固定 `/dev/` 和 `/staging/` 入口，Bootstrap、API 入口、Cookie 和数据库身份必须一致。
- 建立环境级部署锁、回滚入口和失败证据目录；环境不可用时返回结构化错误，禁止回退生产 API。
- 版本晋级记录进入部署台账，生产发布仍按独立 PR、主线 CI 和发布门禁执行。

### 2. Dev 数据和全链路

- 准备可重复、可清理的虚构数据和管理员、组长、组员、观察者测试账号。
- 验证任务下发、查询、编辑、分配、地址匹配、研判和权限拒绝等日常开发场景。
- 完成一条业务事件闭环：Backend 产生事件，经 Kafka、Schema Registry、Flink 和 Redis/派生库处理后，由 Backend 查询并在 Dev 页面呈现。
- 验证重复消息、乱序 revision、失败重试、worker 重启、checkpoint/savepoint 恢复、幂等和运行编号隔离。
- 确认 Dev 的 Kafka、Flink、Redis、派生库和 checkpoint 不复用 Shadow 或生产资源；外部业务 worker 保持关闭。

### 3. Staging 脱敏副本

- 使用白名单导出、脱敏、关系校验和零敏感值扫描生成新的 `staging_snapshot_id`。
- 仅按已批准范围排除三条无效房屋—小区关系，保留房屋并写入拒绝导入报告；其他引用断裂仍阻止导入。
- 在独立候选八库重建表结构、导入数据、重建登记 HMAC 和任务投影，完成数量、关系、版本和环境身份验证。
- 应用切换前保留上一个可用副本；导入或投影失败不得覆盖可回退副本。
- Staging 页面必须显示“预发布环境 · 脱敏数据”，并通过浏览器完成登录、改密、查询、编辑和权限验收。

### 4. 资源、性能与安全

- 实测 CPU、内存、Swap、磁盘、Docker 根目录、数据库存储、Redis 和日志上限，确认非生产资源不会挤占生产。
- 在 Staging 执行一次 75 人、30 分钟真实前端请求模型复测。每个虚拟用户独立运行核心业务、自动轮询和实时连接，起始与失败重试均带随机抖动；记录分层成功率、P50/P95/P99、重连峰值、锁等待、连接池、死锁、Kafka lag、Flink checkpoint、Redis、队列排空和资源使用，并与历史 Shadow 基线分开保存。
- 验证 Staging/Dev 不能跨环境登录、不能访问生产数据库或生产网络，生产容器未重启且生产数据无变化。
- 所有日志、报告和 URL 不得包含密码、令牌、姓名、证件号、手机号、完整地址或正文。

## 日常开发流程

```text
开发分支 / PR
    ↓
部署到 Dev，开发者验收并记录结果
    ↓
冻结候选提交与镜像摘要
    ↓
部署同一制品到 Staging，执行回归和压测
    ↓
通过发布门禁后进入 Production
```

Dev 允许快速重建虚构数据和实验资源；Staging 数据刷新、应用切换和压测必须有运行编号、可回退快照和清理记录。任何环境不得把另一环境的数据库卷、Kafka 数据目录、Redis 卷或 Flink 状态目录作为运行时资源。

## 签署标准

只有同时满足以下条件，Dev 和 Staging 才能标记为“投入开发流程使用”：

- 两个入口可访问，环境标签、Bootstrap、API、Cookie 和数据库身份一致；
- `observer@dev`、`observer@staging` 及所需测试角色可在本环境登录，跨环境登录被拒绝；
- Dev 业务事件闭环和故障恢复通过，且实验能力与未验收能力有清晰标记；
- Staging 脱敏副本导入、关系核对、投影重建、浏览器业务流程和回退演练通过；
- 同一候选制品可以从 Dev 晋级 Staging，部署台账和回滚入口可复现；
- Staging 75 人趋势复测完成，资源和错误率在约定范围内；
- 生产数据、容器、网络和外部业务路径未受到影响。

任一门槛失败，环境只能作为实验或准备环境使用，不能宣称已投入日常开发流程。

## Shadow 退役顺序

完成上述签署后，留存 Shadow 配置、容器、卷、网络、镜像、运行编号和压测结果证据，确认无回滚、监控和脚本依赖，再停用 `observer@shadow`、关闭 `/shadow-api`，最后分批清理无依赖资源。保留恢复入口和证据目录，禁止使用宽泛的 Docker 清理命令。

## 2026-09-20：真实前端 75 人模型修订（开发中）

基于生产窗口的请求分布，本轮先在隔离分支 `codex/staging-realistic-load` 补齐了 Staging 专用的固定环境合同、脱敏/关系元数据校验、分层指标报告和 75 人请求模型。模型持续 30 分钟，每个虚拟用户独立执行登录、列表/详情、保存/领取/分配、心跳、未读数、维护状态、身份检查、任务列表刷新、行内编辑器读取、Query 版本、脱敏房屋搜索、SSE 和 Query WebSocket，并受控模拟断线重连。前端共享恢复调度器已加入指数退避、随机抖动、连续失败熔断和页面隐藏暂停；Query WebSocket 与全局 SSE 使用显式重连游标，写请求仍不自动重放。后端性能快照新增轮询/实时分组、SSE/WebSocket 当前连接数、重连峰值和 `resync_required` 指标。

Staging fixture 固定生成 75 个 `@staging` 虚构账号和六类业务共 1,440 条虚构任务，密码只经标准输入进入私有播种进程，运行索引不保存密码或业务正文。候选 manifest 绑定不可变 `staging_snapshot_id`，部署前必须核验 Staging Backend 正在使用对应快照。Staging 网关只采集 Staging 指标；Production 健康样本必须通过独立只读路径采集，并与 Staging 样本在 90 秒窗口内逐一对齐。任何资源指标或 Production 样本缺失时，报告必须标记为 `unverified`，不能按零值通过。

当前状态是“本地实现与单元测试完成，等待 PR CI”，不代表 Staging 已部署或压测通过。仍需在候选制品冻结后完成 Staging 脱敏副本、真实关系/权限核验、同一镜像摘要部署、75 人压测、Python Worker 回滚演练和页面人工验收。`/api/query` 历史 500 的具体后端根因尚无新的真实证据，本轮不以猜测修改 SQL；若 Staging 复现则按停止条件保留证据并单独修复。
