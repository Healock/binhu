# 外部 Agent XLSX 地址标注与回导

- 当前状态：已确定作为地址匹配的低复杂度探索路线，未开始实施
- 首选工作方式：DeepSeek Harness 或经批准的同类 Agent，以 XLSX 文件离线批处理
- 首期范围：流口任务现有地址匹配待处理队列；房屋档案地址另行评估，不混成同一种来源
- 平台责任：生成最小标注包、校验回导、展示预览，并由有权人员逐条确认
- Agent 责任：提供候选建议、固定原因码和不确定标记
- 禁止行为：Agent 输出不得直接写数据库、自动确认小区、改变社区或任务分配

## 目标

借助已有 Agent 的地址理解能力，减少为地址匹配自建模型服务、向量库、精排和训练流程的前期投入。平台继续使用现有 `RuleMatcher`、地址匹配队列、社区硬约束、人工确认接口和反馈事件作为业务核心。

DeepSeek Harness 在本计划中是可替换的文件处理工具，不假设存在稳定 API，也不要求平台把 Agent 凭据、任务或地址上传到在线服务。首期以显式导出和重新导入 XLSX 为界；Harness 的实际运行位置、数据留存、是否用于训练、访问控制和文件处理上限，实施前必须核实并记录。

## 首期工作流

```text
平台按权限筛选待处理地址
→ 生成带批次标识的最小 XLSX 标注包
→ 人员在获准的数据处理环境中交给 Harness
→ Harness 按候选清单填建议、原因码或不确定状态
→ 平台导入并校验批次和逐行结果
→ 只读预览变更、冲突和版本过期数量
→ 有权限人员逐条复核并明确确认
→ 平台复用现有地址确认逻辑和乐观锁
```

### 1. 导出标注包

用户从现有确认地址工作台选择范围并导出。首期只覆盖已有任务地址匹配记录；任务列表的权限范围、正式社区筛选和稳定排序继续由服务端执行。每个批次应限制行数并包含批次版本、生成时间、规则版本和候选生成版本，便于复现和失效处理。

给 Agent 的工作簿只包含匹配所需内容：

- 不透明的 `package_id` 与 `row_token`，用于平台回导关联；
- 原始地址和正式社区；
- 当前有限候选及每个候选的不透明 `candidate_key`、小区名称和必要地址特征；
- 预留的 Agent 输出列。

不导出姓名、身份证号、手机号、照片、账号、`source_id`、`row_key`、数据库小区 ID、`revision`、`row_hash`、来源正文或内部权限数据。内部任务定位、导出时 revision/hash 和 candidate_key 到数据库小区 ID 的映射保存在平台控制的批次清单中，不交给 Agent。Agent 只能返回本行已有的 `candidate_key`，不得创建小区或返回任意小区 ID。

地址和候选小区本身仍可能属于敏感业务信息。把真实地址交给 Harness 之前，必须由项目管理人确认具体运行环境、数据处理协议、留存/删除方式、训练使用设置、访问主体及本地规则允许范围。无法确认时，只能用虚构或获准脱敏样本验证工作簿，不得上传真实地址。不得把导出文件、候选清单或 Harness 输出提交到代码仓库。

### 2. Harness 标注格式

Agent 只能填写固定列，不修改原始地址、正式社区、批次标识和候选清单：

- `agent_decision`：`suggested_match`、`needs_review`、`manual_unmatched` 或 `cluster_conflict`；
- `agent_candidate_key`：仅在 `suggested_match` 时填写，且必须是本行导出候选之一；
- `agent_reason_code`：固定原因码，例如 `canonical_name`、`historical_alias`、`road_house_number`、`building_room`、`insufficient_detail`、`community_conflict`、`candidate_conflict` 或 `no_reliable_candidate`；
- `agent_note`：可选的简短解释，仅供复核界面显示，不进入普通日志、审计正文或训练集。

若同一规范化地址簇内的多行建议不一致，标记 `cluster_conflict` 并进入人工复核。相似地址不能仅因文本接近而合并；社区不同的地址不能进入同一簇。Harness 可以返回“无法判断”，不得被迫选一个候选。相似度或 Agent 自报置信度仅作提示，不显示为已校准概率，也不作为自动确认门槛。

### 3. 回导和只读预览

回导文件作为不可信输入处理。平台通过 `package_id + row_token` 查找服务端批次清单，并忽略工作簿中任何被修改的原始地址、社区或候选描述；回导结果必须与导出时冻结的行和候选映射比较。不得仅凭 XLSX 行号、地址文本或用户填写的小区名称定位当前任务。

导入先做完整只读校验，至少检查：

- 批次存在、未过期、尚未关闭，行 token 唯一且属于该批次；
- 行数、任务类型和导出范围完整，不接受新增行、重复行或批次外 token；
- 决定、原因码和候选键属于允许枚举；
- `suggested_match` 有候选键，且该键确实属于该行候选；其他决定不能携带候选键；
- 当前任务仍存在且来源唯一，社区、地址、`source_id`、`revision`、`row_hash` 均与批次清单相符；
- 候选小区仍启用，仍属于任务正式社区，且未发生街道或社区硬冲突；
- 任务尚未被人工确认或进入来源异常；
- 地址簇中的结果一致，否则整簇进入复核。

预览展示总行数、Agent 建议匹配数、待人工复核数、无匹配建议数、簇冲突数、版本过期数、候选失效数、社区冲突数和无效行数。预览不写业务表、不新增人工反馈、不调用外部系统。任何一行校验失败都保留明确原因码；是否允许用户只确认通过的其他行，由实现设计明确提供逐行选择，不得隐式忽略失败。

### 4. 人工确认与结果应用

Agent 建议始终不是确认结果。预览通过后，由具备现有地址确认权限的人员检查原始地址、正式社区、候选、规则结果和 Agent 理由，并逐条选择：确认 Agent 候选、改选其他有效候选、记录人工无匹配或跳过。

确认时必须重新读取并锁定当前任务，在事务中重验来源唯一性、权限、社区归属、小区启用状态、`source_id`、`expected_revision` 与 `expected_row_hash`。应用逻辑复用现有结构化地址确认服务和人工无匹配服务；不得直接更新 `_online_task_address_matches`、来源投影或人工反馈记忆。每条记录遵循现有事务和版本冲突行为，批次可以部分成功，但失败行不得被当作成功或自动盲目重放。任何人工确认都记录真实操作人和确认时间；不能使用 Agent 名称冒充确认人。

每行应具备幂等批次操作标识和明确状态，例如 `pending_review`、`applied`、`stale`、`rejected`、`skipped`。重复导入相同批次不能重复确认；对 `stale` 行必须刷新并重新导出/判断，不能把旧建议应用到新地址。已应用后需要改正时，沿用新的人工确认事件，不删除旧反馈历史。

## 安全、隐私和运行边界

- 平台数据库仍是业务事实来源；Agent 和 XLSX 均为不可信建议载体。
- 不使用外部模型 API 作为平台在线请求路径，不新增 Agent 自动回调、平台到 Harness 的网络连接或长期保存的 Harness 密钥。
- 本批次流程不访问腾讯、全民防、居住证或其他业务外部接口，也不执行写入。
- 导出、回导、预览和确认都执行当前用户权限与社区范围；批次下载和回导需绑定创建者/授权管理范围，防止跨用户读取或套用。
- 地址正文不得进入应用普通日志、审计、错误报告或指标标签。审计只记录批次 ID、操作人、行状态数量、原因码、时间和安全定位信息。
- 批次清单需要最短必要留存期和显式关闭/过期机制；到期后清除可恢复内部定位的清单和缓存文件，仅保留不含地址正文的汇总审计。XLSX 导出副本由下载者和 Harness 环境按批准的数据处理规则管理。
- XLSX 防公式注入、宏、外部链接和恶意压缩包。拒绝 `.xlsm`、超限文件、宏部件、公式化的控制列、未知 sheet、重复行 token 和超出限制的压缩展开大小；文本值按文本写入并按上限处理。
- 所有批次输出都绑定规则、候选和工作簿 schema 版本。候选或规则变化不自动重解释旧批次。

## 评估与分阶段推进

### 阶段 A：工具和数据边界确认

确认 Harness 是本地处理还是远端服务、数据是否被保留或用于训练、是否能按原行 token 回填、文件大小/行数限制、并发和失败恢复方式。使用虚构或已批准脱敏工作簿验证导出/回导模板。未完成数据处理审查前不得发送真实地址。

### 阶段 B：离线只读评估

选取经批准的人工核验样本，冻结测试集并按地址簇拆分，防止近重复泄漏。对比 `RuleMatcher` 与 Harness 建议，至少统计 Top-1/Top-3 命中率、可建议覆盖率、人工接受率、改判率、无法判断率、地址簇一致率、跨社区错误、门牌楼栋房号错误、每批耗时和失败率。以规则输出为基线；未经人工核验的 Agent 输出不能作为训练或校准标签。

本阶段只生成报告和人工复核样例，不更新任务、小区、房屋档案或反馈记忆。若关键硬约束错误、隐私边界不清或不能稳定保留行对应关系，停止该路线或仅用于非真实样本。

### 阶段 C：标注包和回导预览

若离线评估有明确收益，再另立实现 PR：增加服务端范围导出、批次清单、XLSX schema 校验、只读回导预览、状态查询、留存/关闭机制及安全审计。先在 Dev 使用虚构或批准脱敏数据验证恶意文件、重复导入、跨社区、跨用户、地址/版本变化、候选停用和部分失败场景。此阶段仍不自动写入人工确认结果。

### 阶段 D：人工逐条确认

导出/回导预览稳定后，另行验证受控的逐条确认入口。每次确认由当前有权人员主动执行，并调用现有确认服务。之后再评估地址簇一致性辅助和批量选择体验；批量操作必须逐行重验并保留部分成功明细。

该路线先于 MGeo、Embedding、Qdrant、Reranker 或 Fine-tune 评估。它不会自动启动那些组件；Agent 效果不够好时可停止或更换工具，不影响现有规则和人工确认路径。

## 回滚与验收边界

- 未确认的 Agent 批次可以关闭或过期；关闭只清除批次和临时文件，不删除任务、人工确认或业务数据。
- 已确认结果不能通过删除批次回滚；修正时必须产生新的人工确认事件，并保留历史责任链。
- 首期不修改数据库业务事实、不改任务原始地址/社区、不改变分配、不创建小区、不调用外部系统写接口。
- 本计划本身不代表 Harness 已通过隐私审查，也不代表地址匹配已改善、真实地址已处理、功能已开发或已部署。
- 真实数据处理、Dev 验收、真实 MySQL、外部 Agent 行为和设备验收分别留证，不能用本地 XLSX 测试替代。

## 实施前检查

开始代码实施前重新核对本计划、`AGENTS.md`、当前地址确认接口、确认权限、人工反馈事件和 `RuleMatcher` 行为。先确定批次清单的持久化位置、过期清理机制、文件上限、授权的数据处理环境和最小字段，再编写实现计划；这些决定不得由导出工作簿中的内容控制。
