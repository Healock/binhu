## 原计划（0.29.x）

平台已经以本地 MySQL 业务表作为唯一主数据源，但在线任务接口和部分表结构仍保留腾讯表时期的缓存、物理行定位和多重正文副本。`0.28.8` 只停止本地热路径读取腾讯元数据并优化派生队列，不更换生产主键、不删除历史表。

后续开发固定按以下阶段推进：

1. 建立稳定本地 `task_id` 和轻量任务头表；任务正文只保存在对应业务表。
2. API 从缓存意义的 `source_id` 迁移到 `task_id`，兼容期只维护 ID 映射，不复制任务正文。
3. 停止在业务表、`_online_source_rows` 和 `_local_source_records` 之间保存多份 `values_json`、摘要和 revision。
4. 将 `_online_writeback_audit` 迁移为通用任务变更审计；将 `_online_local_changes`、腾讯缓存状态、单元格元数据和物理行字段转为历史只读资料。
5. 清除正常运行路径对 `spreadsheet_id`、`sheet_id`、`physical_row` 和 `cell_meta_json` 的依赖。
6. 每阶段先测量查询和引用范围，备份受影响数据库，再执行分批迁移、双读核验和最终切换；不采用长期双写。
7. 历史腾讯表只在保留期内用于审计和回滚。删除历史表、OAuth 记录或备份必须另行审批，不得夹带在普通功能或补丁版本中。

开始实现前必须重新统计生产表行数、索引、外键式引用、API 使用点和审计保留要求，并为每个阶段提供 `measure → migrate --apply → verify` 工具及独立回滚说明。

## 2026-09-30：腾讯路径退场边界复核

本文件仍是长期迁移规划，不代表本次或任何后续代码已恢复腾讯业务路径。当前生产以本地 MySQL 业务表、本地来源记录和本地归档为唯一业务主数据源；腾讯快照、旧来源表和迁移脚本只能作为受限历史审计、回滚和兼容材料。不得重新引入 OAuth、腾讯读取、写回、删除行或依赖物理行号，也不能因为事件流、ORM 或 Repository 的 Dev 试验而宣称模型退场已经完成。

## 2026-11-02：统一任务与来源记录设计提案

### 背景与目标

当前在线任务的权威业务字段按解析类型保存在多个 `t_*` 业务表中；`_online_source_rows` 保存来源正文、哈希和 revision，`_local_source_records` 又镜像来源身份、规范化正文和内容哈希，`_online_source_projection` 保存供任务查询使用的派生字段。这些表的职责不同，但任务正文和版本信息存在多份副本，写入路径必须在同一事务里维护多处记录。Production 的外部只读监控又在 `daily_report` 保存独立快照，形成另一套任务身份和历史口径。

目标是将任务的规范化当前记录和来源身份合并到 `OnlineData` 中的一张权威任务表。每条记录同时说明它是什么任务、来自哪里、当前正文版本是什么；本地来源与外部只读来源共用稳定 `task_id` 和查询模型。任务分配、研判、登记、人工确认、事件和审计仍使用各自有明确事务边界的关联表，不把这些不同生命周期的状态拼成一张无约束的大表。可重建的搜索、统计和任务图投影继续作为派生数据，不再是任务正文的第二权威副本。

本提案不开放外部行写入腾讯，不让外部来源自动获得本地编辑权限，不改变 Production、Staging 与 Development 的隔离，也不批准任何生产迁移或历史数据删除。

当前 `AGENTS.md` 仍要求外部监控正文留在受限监控表，并禁止写入本地业务表或 `_local_source_records`。因此，本设计只是目标架构提案；任何把外部行写入统一任务表的实施 PR，必须先通过项目规则审查并明确更新这一数据边界、访问权限、留存责任和备份口径。设计 PR 本身不构成该例外或实施授权。

### 建议的目标模型

核心表暂称 `_task_records`，最终名称须在实现 PR 前按数据库命名惯例确认，位于 `OnlineData`。建议包含：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 平台生成的稳定主键；API、分配、研判和归档关联统一引用该 ID。 |
| `parser_type` | 保留各业务解析器和字段校验边界。 |
| `source_kind` | 服务端定义的来源类别，例如 `local_table`、`local_dispatch`、`external_readonly`。它是写入策略的输入，不由客户端指定。 |
| `source_ref` | 来源侧稳定引用；本地可使用受控的本地业务 ID，外部使用不含物理行号的不可逆 HMAC 引用。 |
| `business_key_hash` | 在解析器类型与来源范围内稳定识别任务；涉及个人信息的键使用密钥化摘要，不存明文主键。 |
| `values_json` | 当前规范化任务正文；字段名与解析器 schema 一致。访问沿用任务权限，禁止进入普通日志和审计。 |
| `content_hash`、`revision` | 检测内容变化并支持乐观锁；涉及个人信息的身份和内容摘要应使用受密钥保护的 HMAC；本地修改与外部来源更新不得互相覆盖 revision。 |
| `source_observed_at`、`source_last_seen_at`、`source_missing_at` | 描述外部观测时间和缺失状态。一次完整读取缺少某行只标记观测状态，不删除已保存任务。 |
| `created_at`、`updated_at`、`archived_at` | 管理平台记录生命周期；归档继续由现有归档事务和冻结证据控制。 |

唯一性至少覆盖 `(source_kind, source_ref)`；任务业务键的唯一规则须按 `parser_type`、来源范围及已核实冲突样本确定，不能把不同来源中碰巧相同的姓名/日期直接合并。来源引用必须稳定且不包含腾讯物理行号、表格正文或未脱敏个人信息。

`source_kind` 决定来源内容的写入权限：本地来源只允许现有授权流程写入；`external_readonly` 的上游正文只由成功的只读采集事务更新，普通任务编辑接口必须拒绝直接改写。若外部任务需要平台内的分配、研判或备注，写入独立的本地工作流状态或人工覆盖层，并记录操作者、时间及来源 revision；后续上游读取不得覆盖这些本地状态。客户端不能通过改请求字段改变来源类型或解除只读限制。

任务版本历史和读取覆盖属于历史证据，不应靠覆盖当前 `values_json` 实现。保留一个按 `task_id + revision` 记录内容版本的受控历史表，以及一次外部成功运行到任务版本的成员映射；运行状态与来源正文必须在 `OnlineData` 同一事务内提交。若日报或汇总要在独立的 `daily_report` 数据库维护派生结果，通过可重放的 outbox/投影流程跨库更新，不能假设两个连接池上的事务天然原子。历史版本、任务事件、审计和派生投影是关联数据，不是第二份可写的当前任务正文。

### 对现有表的目标关系

| 当前结构 | 目标处理 |
| --- | --- |
| `t_*` 解析类型业务表 | 按解析器批次迁移到统一任务记录；兼容期只读或由 repository 适配，不与新表长期双写；验证完成并过保留期后另行退役。 |
| `_local_source_records` | 将来源身份并入任务记录；迁移后停止复制 `values_json` 和 `content_hash`。 |
| `_online_source_rows` | 作为兼容定位和历史证据分阶段下线；正常路径不再依赖 `spreadsheet_id`、`sheet_id`、`physical_row` 或 `cell_meta_json`。 |
| `_online_source_projection` | 保留为可重建派生读模型，键改为 `task_id`，不得接受独立业务正文写入。 |
| `_txdocs_monitor_*` | 运行摘要与去敏统计可作为采集/观测证据；外部规范化正文与行版本逐步写入统一任务模型。跨库汇总采用 outbox 或重建，不让报表表成为任务正文权威源。 |
| `_online_*` 分配、研判、登记、事件、审计及归档表 | 保留各自业务职责，逐步把关联键切到稳定 `task_id`；不得在本提案中合并删除。 |

### 迁移阶段与验证门槛

1. **生产只读盘点**：按解析类型统计业务表、来源表、任务投影及来源快照的行数、重复业务键、正文哈希差异、引用表、查询路径和历史保留要求。明确 `OnlineData` 与 `daily_report` 当前结构和备份范围；不读取或导出未授权的完整个人资料。
2. **隔离库建模**：在测试数据库建立目标 schema、唯一索引和查询索引；验证 MySQL JSON、并发锁、事务和查询计划。用合成数据覆盖每种 `parser_type`、同业务键重复、外部缺行、来源内容变化、空成功快照及同一任务跨来源冲突。
3. **兼容适配与测量**：增加 repository 和旧主键映射；先执行只读 `measure`，列明将新增、冲突、跳过和无法映射的记录。冲突必须进入问题清单，不以当前核查人、姓名或腾讯行号猜测归并。
4. **分类型回填**：经单独实施 PR 和发布授权后，备份所有受影响数据库，按 `parser_type` 分批将业务表和来源身份映射到 `task_id`。回填应幂等，保留历史原始表，不开启长期双写。
5. **逐入口切换**：每次只切一类读取或写入入口；业务事务同时写权威任务记录及必要工作流状态。旧接口适配层继续检查权限、版本和来源类别。比较旧新结果的任务数、哈希、社区、任务状态和稳定 ID 后才推进下一入口。
6. **外部只读接入**：成功外部读取按 HMAC 来源身份 upsert 到统一表，并在同一 OnlineData 事务记录版本和运行映射；失败读取不得覆盖成功记录，空快照必须与读取失败区分。跨库日报更新允许延迟并可重放，不能丢掉已经提交的任务行。
7. **退役和保留**：所有入口切换并通过验收后，停止旧表写入，先只读保留并运行对账；清理历史正文、旧缓存或个人信息必须另有明确保留期限、影响测量和审批，不随模型迁移自动删除。

每阶段要求 `measure → migrate --apply → verify` 证据、明确数据库备份范围、回滚开关、批次和行数恒等式。回滚先切回旧读适配器并保留新表；若切回会丢失新写入，必须先做反向对账或补偿，不允许简单恢复旧代码后声称数据已回滚。禁止在生产库制造验收数据。

### 必须在实施 PR 前决定的事项

- 各解析类型的规范字段 schema、可空规则、索引列及 `JSON` 查询与投影的性能边界。
- 同一业务身份跨本地和外部来源出现时，是建立关联还是进入人工冲突；默认不自动合并。
- 本地来源正文被平台编辑后的来源 revision、平台 revision 和上游最新值如何分别保存及处理冲突。
- 外部成功快照的保留期限、个人信息备份期限、数据责任人和受控清理方式。
- 历史本地业务表、`_local_source_records`、`_online_source_rows`、`daily_report` 外部快照的最终保留与退役顺序。
- `task_id` 的 API 兼容时间、跨库 outbox 重试/对账合同和每类入口的性能目标。

本设计 PR 只记录目标和门槛。实现前必须复核最新 `main`、外部监控持久化 PR 的状态、真实数据库结构和生产引用范围；本机没有项目 MySQL，未执行真实 MySQL 或 Production 验证。
