本次基线于 2026-07-26（Asia/Shanghai）通过仓库源码检查、未认证健康请求和 TCP 连通性探测建立；没有登录或修改服务器。

## P0 — 立即安全处置

### R-001 既有生产凭据应视为已暴露

- 状态：开放。
- 证据：旧本地项目记忆曾保存 SSH、数据库和管理员真实凭据；默认管理员值仍存在于源码。
- 风险：凭据可能被复制到聊天、备份或其他非受控位置。
- 第二阶段：在备份和回滚准备完成后轮换 SSH、MySQL 业务用户、MySQL root 与管理员凭据；确认旧凭据失效。共享文档不得记录新值。

### R-002 MySQL 端口可从公网建立 TCP 连接

- 状态：开放。
- 证据：`docker-compose.yml` 发布 `3306:3306`；对配置的生产主机探测时 TCP 3306 可连接。
- 风险：数据库攻击面直接暴露。既往数据丢失事故的原因尚未确认，不能据此归因到端口暴露。
- 第二阶段：移除 MySQL 公网端口发布，增加主机防火墙拒绝规则，只允许容器网络或受控本地管理通道，并从外网复测端口关闭。

## P1 — 生产入口与认证安全

### R-003 实际生产入口与 nginx/Compose 配置不一致

- 状态：开放。
- 证据：公网健康接口返回 `Server: uvicorn`；公网 37125 可连接，8000 不可连接。仓库 nginx 监听 37125 并代理 8000，而 Compose 同时把后端 37125 发布到宿主机。
- 风险：配置不能按文档复现，nginx 与 Docker 可能争用端口，TLS、限流和代理头策略没有统一入口。
- 既定方向：宿主机 nginx 成为唯一公网入口；后端只绑定回环地址供 nginx 代理。

### R-004 默认超级管理员凭据硬编码

- 状态：开放。
- 证据：`backend/database.py` 在用户表为空时使用固定用户名和密码创建超级管理员，并把凭据写入日志。
- 风险：新环境和数据库重建后产生可预测的高权限账号。
- 第二阶段：改为一次性环境变量或初始化流程；禁止默认密码和日志输出；轮换现有账号。

### R-005 OAuth 凭据明文存储

- 状态：开放。
- 证据：OAuth 路由直接写入 `_config_oauth_tokens`；`ENCRYPTION_KEY` 只在配置模型中声明，没有加解密调用。
- 风险：数据库读取权限可直接获得第三方访问令牌。
- 第二阶段：确定密钥管理、加密格式、旧数据迁移和轮换方案后实施，不能只把配置名写成“已加密”。

### R-006 CORS、Cookie 与 HTTP 传输策略未完成安全验证

- 状态：开放。
- 证据：FastAPI 配置通配 CORS 并允许凭据；会话 Cookie 设置 `httponly` 和 `samesite=lax`，但没有 `secure`；当前入口为 HTTP。
- 风险：跨域行为、会话传输和未来代理后的安全属性可能不符合生产预期。
- 第二阶段：在 nginx/TLS 架构确定后统一允许来源、代理头、HTTPS 和 Cookie 属性，并进行浏览器登录/登出验证。

## P2 — 行为与文档漂移

### R-007 测试 API 模块存在但未注册

- 状态：开放。
- 证据：`backend/routers/test_mock.py` 定义 `/api/test`，但 `backend/main.py` 没有注册该路由；旧文档曾写成 `/api/test_mock`。
- 风险：测试能力、生产暴露边界和维护意图不清晰。
- 第二阶段：明确删除、仅开发环境启用或受超级管理员保护三种方案之一，并增加验证。

### R-008 bind mount 必须重启才能刷新尚未被证明

- 状态：开放。
- 证据：旧文档把“宿主文件更新后必须重启容器”写成普遍结论，但标准 bind mount 通常会反映文件内容变化；可能的差异在于替换整个目录或部署脚本行为。
- 风险：错误排障步骤会造成不必要中断，并掩盖真正的挂载或上传问题。
- 第二阶段：分别测试原位覆盖文件、删除重建目录和原子替换目录，记录容器内 inode 与内容变化后再下结论。

6. 运行健康、端口、日志、鉴权、OAuth、同步和数据完整性验收，再逐项关闭风险。
