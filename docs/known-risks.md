# 风险清单

## 先看结论

### v0.19.7 腾讯批次边界与 ZIP 到达顺序

- 业务人员可能先在腾讯表增加时间分隔行，稍后才上传照片 ZIP。此时工单已经完成但尚无附件；平台现允许最近批次在七天内补挂，不能再把“已完成”简单等同为永远不参与照片匹配。
- 补挂只按身份证 HMAC 精确匹配，姓名仍仅作警告。同一身份证对应多个符合条件的工单时会按既定规则全部挂载；未找到安全候选的照片保持未匹配。
- 重传同一个部分完成 ZIP 会复用原批次并覆盖已清理的受保护 ZIP 原文件，但不会覆盖工单附件。确认阶段仍按附件 SHA-256 幂等去重。

### v0.19.6 调照片名单完整核对与行变动

- 腾讯表允许插行、排序和完全重复的 A-F 申请。完整核对现按摘要与稳定行序重新配对，不再要求摘要唯一；但如果用户直接修改了旧申请正文，摘要无法对应时仍会保留旧工单并进入冲突，不会自动猜测新旧关系。
- 完整核对会在单个事务内临时释放来源的全部物理行号。数据库异常会整体回滚；运维人员不得在任务运行期间手工改动映射，也不得把 `relocating` 或 `missing` 状态当作可删除数据。
- `missing` 表示腾讯当前完整读取中未找到对应行，不表示工单应删除或业务已撤回。后续腾讯行恢复后，下一次完整核对可以按摘要重新定位。

### v0.19.5 调照片名单即时写回与调度隔离

- 平台快捷申请提交后会立即异步追加腾讯名单，但第三方请求仍可能出现“已经写入、回读超时”。第一次失败后的重试必须先扫描并按 A–F 摘要重定位，不能再次盲目追加；多个相同候选仍进入冲突列表人工处理。
- 腾讯人工新增申请最多等待约五分钟进入平台。每日整表核对已经与增量同步解耦并设置超时，但若腾讯增量接口本身持续不可用，平台仍只能保留失败运行记录并等待下一周期重试。
- 本机没有真实 MySQL 和腾讯测试子表。自动化测试覆盖事务提交顺序、首次尾行追加、失败重定位和调度隔离；真实自然申请的外部读写仍应在发布后只读核对并由业务自然数据验收，不能制造测试身份证或测试行。

### v0.18.0 调照片名单同步风险

- 腾讯名单允许完全相同的 A–F 申请重复出现，因此初次导入严格按物理行创建工单。出站请求发生“请求可能到达腾讯但回读失败”时，若随后发现多个相同候选，系统会停止自动定位并进入冲突列表，避免重复追加或覆盖错误行。
- 历史时间边界缺少年份时只能依据相邻申请日期推导，页面会保留推导标记。生产只读预览必须核对批次数和最后边界；不能仅凭离线文件基准直接执行导入。
- 照片附件和工单完成不依赖 G 列写回成功。腾讯故障期间 G 列会保持待重试，不能为了“看起来一致”回滚已完成工单或删除附件。
- 本机没有真实 MySQL 和腾讯测试子表，`0.18.0` 的兼容加字段、上万行事务时长和在线回读仍需在生产备份后验证。正式导入前必须使用 `backup_scope=all`，且同步读写开关保持关闭。

### v0.18.1 腾讯传输型 400010

- 腾讯 `GetWorkSheetInfos` 偶发把 TCP 读取超时包装为 HTTP 200 + 业务码 `400010`。客户端只对明确包含传输超时特征的错误有限重试；若三次仍失败，预览保持原结果，不把异常当作空表。
- 生产环境仍需关注 DNS、上游网络和腾讯接口响应时间。历史导入前必须重新只读预览并核对摘要，不能仅凭一次成功或一次失败判断数据状态。

2026-07-28 已完成生产安全切换和运维中心上线：

- SSH、MySQL root、MySQL 业务用户和超级管理员密码已经更换，旧密码已验证失效。
- MySQL 不再发布公网端口，后端只绑定服务器本机。
- 平台统一通过 nginx 的 HTTPS 443 访问。
- `ops-agent`、运维中心、每日备份和操作记录已经上线并完成生产检查。

仍有多项事情需要以后处理，其中最重要的是 OAuth 凭据和走访身份证号加密、单机备份，以及统一初始密码公告的风险。

## 仍需处理的事项

### R-005：OAuth 明文

数据库目前直接保存腾讯文档访问令牌。虽然应用已经配置独立加密密钥，但旧数据加密迁移
还没有实施，因此不能把这一项写成已解决。

迁移时要先备份，再实现新数据加密、旧数据兼容读取、分批迁移和回退验证。

### R-008：前端目录热更新

当前部署会在替换前端后重建后端容器，所以实际运行稳定。是否能只替换目录而不重启，
尚未单独验证，不应把猜测写成部署规则。

### R-009：单机备份（异地备份已退役）

运维中心的每日备份与服务器故障可能同时丢失。当前每日八库备份保存在物理服务器的独立备份盘，已完成 gzip、
SHA-256、7 天保留和恢复核对；旧云上的异地备份接收已于 2026年8月9日停止。以后如需恢复异地容灾，必须选择新的
受控设备或对象存储，并增加加密、保留时间和恢复演练。

### R-010：SSH 密钥

当前已经使用新的高强度密码，但仍允许 root 密码登录。家里和单位电脑分别配置自己的
SSH 密钥并验证后，可以关闭密码登录，进一步降低暴力破解风险。

### R-011：走访身份证号明文

走访明细的“操作人账号”是网格员身份证号。第一阶段按项目管理人确认的方案明文保存到
`t_visit_details`，并在网格员资料为空时补入 `_grid_members`。这是为了后续稳定关联人员，
但数据库或备份一旦泄露，完整号码也会随之泄露。

只有超级管理员可以在人员管理接口和页面查看、修正完整号码；普通管理员即使拥有人员敏感资料
权限，也不能获得填写状态、遮盖号码或完整号码。导入问题、操作记录、CSV 和日志仍不得返回完整
号码。这只能减少日常使用中的暴露，不能代替数据库加密。后续迁移需要先备份，再实现新数据
加密、旧数据兼容读取、分批迁移和回退验证。

### R-012：React Router 版本

2026-07-29 运行生产依赖审计时，当前 `react-router-dom` 和 `react-router` 6.30.4 报告两条
中等安全公告。平台当前没有使用 React Router 的服务端渲染，代码中的跳转地址也都是固定的
内部路径，因此已知受影响入口较少，但不能把它写成已经解决。

已修复版本需要升级到 React Router 7.x，属于主要依赖升级。应在独立分支中完成登录保护、
左侧栏、手机 Dock、设置页和未知地址跳转的完整回归，不在 `0.4.0` 的手机体验改造中顺带升级。

### R-013：旧出勤历史不完整

平台从 0.6.0 开始保存多条请假历史和每周双休日备勤。上线以前只保留人员当前或最近一次
请假，已经被覆盖的更早记录无法从数据库自动恢复。管理员可以按纸面或原系统记录补录过去
请假和历史周末排班；补录以前，页面会提示这段历史的人均日指标只能作为参考。
当前人员管理页面在双休日会把缺少当周记录的人员明确显示为“未排班”，而不是猜测为在岗或休息；只有保存了当周安排后，页面才显示“今日备勤”或“休息”。

### R-014：统一初始密码公开

`0.9.0` 名单导入按项目管理人确认的方式，为新账号使用同一个初始密码，并通过全员公告公开。
这便于开发阶段集中开通账号，但任何看到公告的人都可能在账号本人第一次登录前尝试其他用户名。
唯一登录只能顶掉旧会话，不能阻止第一次抢先登录。

当前缓解办法是把新账号标记为临时密码并持续提醒本人尽快修改，名单、密码和导入过程不进入
Git、共享文档、日志或操作记录。更安全的正式方案是为每个人生成不同的一次性密码，或通过
私下渠道分别发放；届时再移除公开密码公告。

### R-015：人员管理入口可以创建账号

为了保持“一名业务人员对应一个账号”，拥有人员管理权限的管理员可以在新增人员时关联尚未使用的
普通账号，或同时创建新账号。这项能力不会开放用户管理、权限组选择或超级管理员创建：新账号只
能继承人员岗位的默认权限，用户名必须唯一，初始密码至少 8 位，人员和账号在同一事务中写入，
失败时整体回滚。请求正文、密码和完整用户名不进入操作记录。自定义权限仍只能由超级管理员在
用户管理中单独设置。

`0.9.4` 允许在人员管理中改绑账号。目标为空闲账号时释放旧账号；目标已关联另一名人员时交换
双方账号。两种情况都会清除受影响账号的有效会话，并按新人员岗位重新继承权限，避免登录中的
身份与数据库关联不一致。账号 ID 和是否互换可以进入审计，用户名和身份证号不能进入审计。

### R-016：超级管理员可读取完整身份证号

人员资料中的身份证号属于高敏感数据。`0.9.4` 为满足资料修正需求，只允许超级管理员从人员接口
读取和修改完整号码；普通管理员即使拥有人员敏感资料权限，也不会收到是否已填写、遮盖号码或
完整号码。接口请求、操作记录和日志不得记录完整号码。超级管理员账号被盗仍可能导致号码泄露，
因此应继续使用独立强密码、唯一登录和空闲退出，并定期检查账号与操作记录。

### R-017：腾讯在线表格真实回写

`0.10.0` 根据腾讯文档现有读取和批量更新接口实现单元格修改、新增数据和物理删行，并用自动化测试
覆盖请求结构、物理行号、行哈希冲突、同步互斥、岗位范围和审计保留。`0.10.2` 依据官方文档取消
未公开的插行请求，改为向最后一条非空记录后的现有空行执行区域更新，并同时检查 HTTP 状态、腾讯
业务返回码和写后回读。但按项目管理人要求，Agent 不能在腾讯测试表或生产业务表执行真实新增、修改、
删除，因此第三方接口对新增、删除、下拉单元格以及 `0.12.0` 手机任务一次保存多个字段的最终行为
仍属于上线后的人工验收项。`0.17.10` 根据生产只读审计确认：腾讯范围读取会返回 `select`，但官方区域
更新接口只支持文本、链接和数字；此前写入选项 ID 的请求未真正保存，写后回读为空并被平台正确判为
失败。新版先使用真实选项校验，再写显示文本并回读比较。自动化测试覆盖请求结构，但 Agent 仍不在生产
业务表制造修改；“已登记”“离苏”和模型三结果需由项目管理人使用现有任务完成最终验收。
工作表没有
现有空行时，需要先在腾讯表格中扩充行数。腾讯对超出 `rowTotal` 的读取返回业务错误，新版读取层
会先读取文件元数据并收窄分页范围；文件元数据结构再次变化时，自动同步会明确失败而不会静默截断。

程序首次建表时把 `online_writeback_enabled` 设为关闭。生产部署先只读检查来源缓存、重复投影、
片区映射和权限，再明确启用。任何异常都应先关闭回写开关；查询、归档和正常同步不受影响。修改和
删除前的完整原始内容在 `_online_writeback_audit` 保留 90 天，但删除不提供自动恢复，必要时由超级
管理员参考审计记录人工补回。该审计包含身份证号、手机号等原始字段，只能由超级管理员读取，不能
复制到普通操作日志、诊断包或共享文档。

腾讯 v3 范围读取接口对数值单元格只返回浮点值，且 `CellFormat` 不包含数字显示格式，所以数字
`7.30` 与 `7.3` 都会返回 `7.3`。平台不能在不知道原始输入的情况下安全补零，否则会把真实的
`8.3` 错写成 `8.30`。需要保留尾零的日期列必须在腾讯来源表中设置并录入为文本；平台新增和回写
继续强制使用文本值。

2026-08-09 排查确认，旧版 Univer 在任意编辑结束后会重新读取整张工作表，并把内部数值化造成的
长数字差异误判为用户修改，进而逐格提交腾讯回写。受影响数据已依据回写前审计和腾讯当前物理行完成
恢复，修复前备份与脱敏核验记录保留在服务器；共享文档不记录完整号码。`0.17.3` 改为只处理本次
明确编辑的单元格，并在前后端同时拦截没有明确文本输入依据的长数字精度变化和尾零丢失。在线回写
在修复版部署和项目管理人验收前继续保持关闭；恢复开关后仍需观察修改审计和下一次正常同步。

### R-019：公安任务腾讯批量发布

### R-020：“无法核实”历史回算

`0.12.12` 把“无法核实”调整为已核查但未完成，并新增隐藏的有效工作量：首次无法核实和之后跨日完成
最多各计一次。代码提供只读预览及按日期升序重建流水、分汇总和总汇总的正式服务，但本机没有真实
MySQL 测试库，本轮也按要求不连接生产库，因此兼容列、SQL 和历史数据规模尚未做真实驱动验证。
正式上线前必须先在测试库执行，再预览生产影响范围、备份 `daily_report`，最后通过 `scratch/` 一次性
包装回算并复核重复执行结果一致。失败时恢复旧镜像并保留备份，不得在未确认范围时直接清空日报表。

### R-021：个人贡献历史完整性

`0.13.0` 才开始长期保存独立工作贡献事件。在线回写审计只保留 90 天，管理操作审计只保留 180 天；
因此首次上线只能幂等回填这些保留期内的可靠记录，并从仍存在的工作日志草稿补一条创建贡献。更早的
核查处理和审核没有同时可靠保存操作者、业务时间与成功状态，不能从当前腾讯内容或业务库反推，否则
会把后续修改错误归给其他人。页面和说明不得把首年热力图描述成完整历史；上线后新实际工作会实时
写入无业务正文的永久事件，后续新增工作入口必须先明确是否属于实际工作并补相应测试。

### R-022：受控发布身份

`0.15.0` 把逐文件人工上传改成 GitHub 人工发布。专用私钥只能登录密码已锁定的 `binhu-deploy` 账号，
服务器通过 `restrict`、强制命令和固定 sudo 脚本限制其能力；工作流还要求提交已经进入 `main`、版本精确匹配、
生产发布互斥和主机指纹固定。GitHub 不保存 root 密钥、数据库密码或第三方凭据。

这仍不是零风险：服务器通过专用 SSH 密钥确认发布来源，但不能独立证明压缩包一定由 GitHub 主线构建；如果
这把私钥泄露，攻击者可能绕过正常工作流并伪造包内提交标识。应为 GitHub 账号启用强认证、限制 Environment
管理权限、定期核对 Actions 与服务器
`/var/lib/binhu-deploy/history/`，人员或设备变化时轮换专用密钥。普通 CI 永远不能引用生产 Secret；人工 root
SSH 只作为紧急入口，不能回填进工作流。发现部署私钥疑似泄露时，先从服务器删除该授权并暂停发布，再创建
全新的专用密钥和 GitHub Secret；不能只修改工作流名称或重新运行旧任务。

### R-023：生产磁盘与发布材料保留

固定发布会为每个版本留下源码快照、程序归档、旧后端镜像标签，以及按发布范围创建的即时数据库备份。
为了避免误删唯一回退材料，第一版不会自动清理这些文件或执行 Docker prune；服务器会在构建前检查最低可用
空间，空间不足时直接停止，不切换现有服务。

这只能防止最后时刻耗尽磁盘，不能解决长期增长。后续应在异地加密备份可用后制定保留数量，逐项确认当前版本、
上一稳定版本、数据库即时备份和每日备份，再通过固定白名单清理；不得用宽泛路径、未解析变量或
`docker system prune -a` 代替保留策略。

### R-024 至 R-027：物理服务器迁移例外

物理服务器没有公网 IP，使用 SakuraFRP 提供 HTTPS 和 SSH 穿透。直接入口已经切换为服务商托管、受浏览器
信任的 HTTPS 子域名，健康检查和 GitHub 自动发布不再跳过 TLS 校验。旧云原有的 HTTPS 透明代理已于
2026年8月9日退役；旧云平台、MySQL 和运维代理容器均保持停止，不能继续运行独立可写后端。

WireGuard 已于 2026年8月9日停用并归档，旧云网页代理和异地备份接收也同时退役。FRP 网页或 SSH 隧道故障时不再有
旧云入口或专线兜底，只能通过物理服务器固定局域网地址和公钥 SSH 维护。

现场备用供电需要人工切换，不是 UPS。项目管理人选择正式切换前不执行完整重启演练，也暂不轮换已暴露的
SakuraFRP 凭据和本地 root 口令。物理服务器公网 root 只接受公钥，但旧云当前仍允许 root 密码登录，因此
公网暴力登录和口令泄露风险尚未消除；控制台口令、隧道账号和突然断电也仍是风险。生产切换后必须持续检查
SMART、RAID、挂载、容器启动顺序和 FRP 隧道；发现异常时不能把旧数据库作为自动故障转移节点。

### R-028：新辖区档案明文身份证和手机号

按项目管理人确认，`RegistryData` 新档案中的身份证号和手机号暂时明文保存，并另存 HMAC 摘要用于精确检索、去重和任务命中。HMAC 密钥只放在服务器私密配置中，不进入数据库、日志或 Git。该选择降低了实施复杂度，但数据库备份或只读账号泄露时仍可能暴露完整号码；后续如调整策略，应先备份、增加密文兼容字段，再分批迁移和恢复演练。

### R-031：辖区档案敏感字段仍按明文策略保存

`RegistryData` 依照当前确认同时保存身份证号/手机号明文和 HMAC 摘要。数据库备份、只读账号或服务器文件泄露仍可能暴露完整号码；普通日志、审计和通知不得记录这些字段。未来若调整为加密存储，必须先备份、增加兼容字段、分批迁移并演练恢复。

### R-032：应用级维护不等于服务器完全停机

v0.17.0 的维护模式主要用于预约业务停用。普通用户由后端返回 503，超级管理员、健康接口、登录页静态资源和维护状态接口仍然可用，因此它不能替代数据库迁移或容器重建时的 Nginx 维护页。若底层操作只打开应用维护模式，仍可能有超级管理员请求或后台任务继续运行；正式迁移必须继续按运维手册暂停同步、备份、回写并切换 `new-maintenance`。

### R-033：照片预览 ZIP 的容器生命周期

`0.17.2` 至 `0.17.4` 的数据库会长期保存等待确认的照片批次记录，但 Compose 没有为预览 ZIP 配置绑定挂载，文件实际写入后端容器的 `/workflow-photo-imports`。2026年8月9日的首个真实批次在容器重建后出现“数据库预览仍在、ZIP 已丢失”，因此无法确认；真实照片内容无法从数据库明细反向恢复。

`0.17.5` 将目录改为服务器 RAID 数据盘上的受保护绑定挂载，并允许相同 ZIP 在文件丢失时恢复原预览批次。发布后仍需实际核对容器挂载源、容器内目标目录和写入权限；旧批次必须由持有原 ZIP 的项目管理人重新上传，Agent 不复制、下载或制造真实照片。

### R-034：每日明细依赖日报快照和当前名册

`0.17.6` 的工作每日明细使用所选业务日期的在线日报人员快照，但人员排列和岗位类别读取当前人员管理名册。若事后调整人员姓名、岗位、社区或片区，重新生成旧日期文件时基础人员行可能随当前名册变化；指令数量仍以旧日期日报快照为准。所选日期没有日报快照时指令列保持空白，不能用当前在线投影补造历史数据。原始参考工作簿含真实示例内容，仓库和发布包只能保存已清空人员、数字、备注和背景色的脱敏结构模板。

### R-035：腾讯同步 DNS 与异常空读

2026年8月11日生产日志确认，服务器当时唯一上游 DNS `61.177.7.1` 对 `docs.qq.com` 连续约十分钟解析超时，六类腾讯业务同时失败；网络接口和 Docker 本身没有重连。同期还发现旧读取流程会在返回空列表后立即替换来源缓存，并可能把旧数据当作腾讯真实删除而归档。

`0.17.21` 只为后端容器配置两个独立国内 DNS，不修改服务器系统解析；同步对已有数据突然清空或大幅骤降执行第二次完整读取，两次不一致或读取报错时不修改缓存、快照、业务表或归档。全链条同主键多来源继续完整保存在来源缓存并显示异常，旧统计使用最早物理行，不再阻断其他任务。相同错误连续发生时只通知一次，首次恢复再发送恢复提示。此前疑似返苏和寄递业的历史归档无法确认是否源于用户真实清空，因此不自动恢复。

### R-036：腾讯数值日期的历史尾零不可恢复

腾讯范围读取对数值单元格只返回数值结果，不返回原始输入和小数显示位数，因此现有 `8.1` 无法可靠判断原来是 `8.1` 还是 `8.10`。`0.17.22` 从编辑缓存、粘贴文本和后端区域写回三处固定保留后续日期/时间文本，但不自动修改已经缩短的历史单元格。历史修复必须以可核对的原始文件或明确业务日期为依据，先生成预览再人工确认。
