# 开发与运维手册

开始较大的功能、修复或数据库改动前，先看 [高效开发与验证流程](development-workflow.md)，提前确定检查范围，避免上线时临时追加和重复验证。

## 当前运行基线（2026-08-11）

- 当前准备发布版本为 `0.19.3`；实际运行版本仍应以健康接口为准。八库分域迁移记录继续按 `0.16.0` 保留，不能把本地构建结果直接当作生产迁移完成。
- 正式发布统一使用 GitHub Actions 的 `Deploy production` 工作流；开发电脑不再逐文件上传程序。
- 生产服务由 `binhu-backend`、`binhu-mysql` 和 `binhu-ops-agent` 三个容器组成。后端只监听服务器本机，公网统一经过 nginx HTTPS。
- `binhu-backend` 单独配置 `119.29.29.29` 和 `223.5.5.5` 两个 DNS 上游，避免腾讯文档同步依赖单一运营商 DNS；不修改服务器系统 DNS。部署后用容器内解析检查确认 `docs.qq.com` 可解析。
- 所有登录用户访问 `/` 先进入仪表盘；在线数据汇总使用 `/summary`；电脑端 `/query` 为 Univer 在线工作表，手机端按岗位转入相应任务工作台。
- 数据库使用同一个 MySQL 实例，目标域划分为 `PlatformData`、`OnlineData`、`OnlineDataArchive`、`daily_report`、`VisitData`、`DispatchData`、`RegistryData` 和 `WorkflowData`。截至 2026-08-08，走访、下发、小区地址和平台基础域已完成迁移并切换；日报、辖区档案/人员标记新功能和工单域仍按维护窗口推进。本地开发电脑没有项目 MySQL 或 Docker 运行环境。
- 2026-08-06 完成一次容量整理：磁盘使用率从 96% 降至 83%，保留当前版和上一版后端镜像，数据库卷、每日备份、发布源码留档及自动发布记录均未删除。
- GitHub 旧的已合并功能分支已经清理，目前远端只保留 `main`。`main` 尚未启用 GitHub 分支保护，因此仍必须人为坚持“功能分支 → PR → CI → 合并”的流程。
- 生产业务已经运行在物理服务器；旧云的平台容器和 HTTPS 透明代理均已于 2026年8月9日退役。旧云只保留原数据库、卷、程序和历史备份作为人工回退材料，WireGuard 与异地备份接收能力也已停用；主机 Nginx 继续服务旧云上与本平台无关的站点。

版本号、容量和容器状态会变化。执行生产操作前仍要以健康接口、GitHub 工作流和服务器只读检查为准，不能只照抄本节数值。

## 最常用：两台电脑怎么开发

记住三句话：

1. 开工前先拉取。
2. 换电脑前先提交并推送。
3. 功能完成后才合并到 `main`。

### 开始一个新功能

不管在家里还是单位，都先更新正式代码：

```powershell
git switch main
git pull --ff-only
```

然后建立一个功能分支。项目管理人手工开发可以使用 `feat/`，Codex 创建的分支使用 `codex/`：

```powershell
$branchName = "feat/example-topic"
git switch -c $branchName
git push -u origin $branchName
```

把 `example-topic` 换成简短的功能名称。不要建立“家里分支”或“单位分支”。

### 准备换电脑

离开当前电脑前，把进度保存到 GitHub：

```powershell
git status
git add -- path/to/reviewed-file
git commit -m "开发进度：简单说明做了什么"
git push
```

功能没写完也可以提交到功能分支，只要暂时不合并进 `main`。

### 在另一台电脑继续

这台电脑第一次使用该分支：

```powershell
git fetch origin
git switch --track origin/feat/example-topic
```

这台电脑已经有该分支：

```powershell
git switch feat/example-topic
git pull --ff-only
```

### 功能完成

检查通过后推送最后一次修改，在 GitHub 创建 Pull Request，然后合并到 `main`。

合并时删除对应远端功能分支；不要删除仍有开放 PR、尚未合并或需要跨电脑继续开发的分支。正式版本还要继续执行文末的 [正式部署入口](#正式部署入口)，普通 `git push` 和 PR 合并本身不会更新生产服务器。

合并后，两台电脑分别运行：

```powershell
git switch main
git pull --ff-only
```

`.env`、`backend/.env` 和 `AGENTS.local.md` 不会通过 GitHub 同步，两台电脑要分别配置。

### GitHub 分支收尾

每次 PR 合并后应删除该功能分支，并在两台电脑同步远端状态：

```powershell
git switch main
git pull --ff-only
git fetch origin --prune
```

批量清理远端分支前必须同时满足：已经合并进 `origin/main`、没有开放 PR、不是 `main`、不是保护分支。删除分支不会删除已进入 `main`、PR 或版本标签的提交，但没有合并且没有标签的独立提交可能随分支删除而失去正常入口。

建议在 GitHub 为 `main` 开启分支保护，至少要求通过 PR、后端检查和前端检查后才能合并。启用以前要先核对工作流中的真实检查名称，避免把 `main` 锁死；启用后也不能允许普通发布流程绕过检查直接推送。

## 第一次配置电脑

复制项目配置模板：

```powershell
Copy-Item .env.example .env
```

然后编辑 `.env`，把所有 `replace-with-*` 示例值换成本机使用的值。不要把真实密码发到聊天或提交到 Git。

如果使用 Docker，可以检查配置：

```powershell
docker compose config --quiet
```

如果直接启动后端，还要在 `backend/` 中建立自己的 `.env`。字段示例：

```dotenv
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USER=binhu
MYSQL_PASSWORD=<本机数据库密码>
MYSQL_ONLINE_DATA_DB=OnlineData
MYSQL_ARCHIVE_DB=OnlineDataArchive
MYSQL_DAILY_REPORT_DB=daily_report
ENCRYPTION_KEY=<本机应用密钥>
```

## 本地启动

前端：

```powershell
Set-Location frontend
npm install
npm.cmd run dev
```

前端修改完成后检查生产构建：

```powershell
npm.cmd run build
```

后端：

```powershell
Set-Location backend
python -m pip install -r requirements.txt
python -m uvicorn main:app --reload --port 8000
```

后端启动前需要三个可用的 MySQL 数据库，具体用途见 [架构说明](architecture.md)。

## 工作日志日报

管理员和超级管理员可以在“工作台 → 文件生成”的“工作日志”Panel 选择业务日期并创建日报草稿。周报和月报在收到对应模板前保持禁用；“工作每日明细”使用另一个独立 Panel，不创建或修改草稿。

- 同一天只有一份日报草稿。创建者编辑，其他管理员可以查看、导出或主动接管。
- “草稿管理”集中显示全部日报草稿，并支持按日期、创建人或当前编辑人查找。管理员和超级管理员都可以删除草稿，删除前必须二次确认；删除不可恢复，但同一天可以重新创建。删除不会影响在线数据、走访数据或统计报表，并会写入超管操作记录。
- 页面约 1 秒自动保存。出现“保存冲突”时应重新读取草稿，不能反复覆盖。
- 创建草稿后系统统计不会自行变化；确需更新时点击“刷新系统数据”，人工填写和人工覆盖会保留。
- 工作日志中的“网格员数”由人员管理、统计岗位、请假和双休日备勤共同计算。已有草稿点击“刷新系统数据”后会补齐尚未填写的人数；已经人工修改的数字不会被覆盖。周末排班没完成时人数保持空白，应先完成人员管理中的排班。
- 导出前会列出尚未填写的字段。确认后可以带空白继续导出。
- 导出的 PDF 不保存在服务器，草稿保存在 `OnlineData._work_log_drafts`。
- 业务日期为 7 月 14 日时，正文和系统取数都使用 7 月 14 日，文件名以 `0714日报` 开头，落款为 7 月 15 日。

PDF 版式由工作日志结构和后端打印样式共同生成。旧 `.doc`、`.docx` 样例只能在本机参考，不能复制进仓库。发布前要检查 PDF 可以打开、中文正常、十六张表格没有截断、没有未替换占位符，也不能出现旧样例中的姓名、身份证号、电话号码或警情文字。

`0.8.0` 使用 `daily-v2` 表单结构。访问旧版草稿时先把原始 JSON 完整保存到新快照的 `legacy_v1` 区域，再映射能够识别的字段，不删除旧内容。部署前备份 `OnlineData` 并保留旧后端镜像和前端；部署后检查页面权限、旧草稿升级、自动保存冲突、PDF 下载、容器日志和 `/api/health` 版本。

`0.8.1` 只调整 PDF 公文版式，不修改草稿字段或数据库。发布时保留旧后端镜像即可；验收重点是红色标题和分隔线、基础数据与章节顺序、正文层级、问题分析颜色、表格分页和中文字体。

`0.8.2` 调整叮咛行动、矛盾纠纷和出租房责任落实文字，并把自购房走访人员汇总接入工作日志
系统快照。新建草稿会自动带入自购房数据；已经存在的草稿要由当前编辑人点击“刷新系统数据”
后才会读取，避免后台数据悄悄改变旧草稿。出租房屋核查同步同时允许把同一身份证号和手机号的
重复行合并为一个核查对象；两个身份字段都为空时仍停止同步，不猜测是否同一人。

`0.8.3` 在社区管理中增加社区民警名单，一个社区可以填写多位。新建工作日志草稿会把姓名带入
全部按社区生成的表格，多位民警用“、”连接。升级只给 `_communities` 增加可空的
`police_officers` 字段，旧版本会忽略该字段；上线前按兼容数据库变更流程备份三库和旧程序。

`0.8.4` 累积界面细节调整，增加工作日志草稿管理，以及面向全员的公告和个人提示。草稿删除只
移除被明确选中的记录；公告升级会新增两个兼容表。发布前应检查草稿筛选、指定日期打开、删除确认、
同日重建、普通账号查看公告、个人提示隔离、公告独立已读和超管发布删除权限。

下面以版本号开头的段落用于解释既有数据库结构、兼容边界和回退证据，不是当前版本的日常部署命令。当前发布一律使用文末的固定 GitHub 工作流；只有处理对应历史结构或回退时才查阅这些记录。

## 0.9.0 权限和账号名单上线

`0.9.0` 增加部门、权限组、账号关联、唯一登录和空闲退出。数据库变更都采用新增表、可空字段和
兼容字段，旧程序会忽略它们；但正式启用社区范围以前，必须先完成名单预览。

固定上线顺序：

1. 备份 `OnlineData`、旧后端镜像和旧前端，并把旧账号的角色、人员关联和有效会话清单保存到私密回退材料中。
2. 部署新程序，让后端只创建兼容结构。此时 `permission_enforcement_enabled` 仍为 `0`，未关联的旧低权限账号继续沿用原查看能力。
3. 把名单临时放入后端容器，只运行预览。预览必须逐行显示用户名、姓名、所属部门、岗位、默认权限组和“新增或跳过”。
4. 只要出现重复用户名、重复人员、人员姓名不唯一、部门不符合岗位、未知名单职位或岗位没有默认组，整批停止，不写入数据库。
5. 项目管理人确认预览无误后，才正式创建账号、发布初始密码公告并启用新权限。
6. 分别使用流口岗、片长、基础管控、管理员和超级管理员账号检查，再创建 `v0.9.0` 标签。

名单文件至少包含“用户名”“姓名”和“职位”，属于私密文件，不能复制到仓库、提交 Git 或写进共享文档。
已存在的用户名整行跳过，不补人员关联、不改权限且不重置密码。姓名能与人员管理唯一匹配时，
继续使用该人员的岗位默认组；未匹配人员只允许按以下固定规则处理：

- “社区民警”和“所（队）领导”创建为不关联人员资料的管理员账号。
- “内勤岗”创建为不关联人员资料的内勤业务组账号。
- “流口岗”先创建“组员、待分配部门”的人员记录并关联账号，之后由超级管理员在人员管理中分配社区。

手机号和身份证号没有参与当时的账号导入。一次性名单工具已在导入和核验完成后从当前源码移除；
历史实现可从 `v0.9.0`、`v0.9.1` 标签追溯，但不得直接复制到当前生产环境执行。以后再次批量建号时，
应针对新名单重新制作只预览、整批校验、密码脱敏和事务回滚都可验证的短期工具。

上线后固定检查：

- 旧超级管理员仍可登录，且至少保留一个超级管理员。
- 流口岗只能看到业务记录所属社区的数据，社区别名可以正确归入正式社区；无社区部门时显示空数据说明。
- 片长只能全局查看；中队长和基础管控可以同步、上传、排班、请假和管理工作日志，但不能修改人员或社区。
- 管理员可以修改人员和社区；超级管理员可以管理账号、权限组和岗位映射。
- 在另一浏览器登录同一账号后，旧会话显示“账号已在另一台设备登录”；同一浏览器多个标签页保持正常。
- 默认空闲 30 分钟，到期前 2 分钟提示；后台轮询、自动保存和文字输入不续期，“继续使用”、主动查询和提交会续期。

权限组调整会在账号下一次请求时生效。若上线检查失败，先切回旧程序；恢复账号或会话快照会
覆盖当前状态，属于高风险操作，必须另行确认，不能在普通回退中自动执行。

## 0.9.2 多权限组和在线汇总固定口径上线

`0.9.2` 新增 `_position_permission_group_links` 和 `_user_permission_group_links`，分别保存岗位和账号的
多个权限组。后端启动时会把旧单权限组关系写入新表；旧 `_position_permission_groups` 和
`_users.permission_group_id` 继续保存排序后的第一个组，所以旧程序可以直接忽略新表并回退。

本版同时改变在线汇总展示口径：单日、区间、总汇总、概览和工作日志自动取数固定只保留人员管理中
有有效社区部门的组长、组员。旧日报表和原始业务数据不重写，查询时动态过滤并重算社区合计。
日报不再有单独生成入口，只在手动或自动同步的末尾按“分汇总 → 总汇总”生成。

上线前固定准备：

1. 备份 `OnlineData` 和 `daily_report`；`OnlineDataArchive` 本版不变，不重复备份。
2. 保留旧前后端镜像，并确认准备上线的提交、`VERSION` 和前端产物属于同一版本。
3. 在服务器运行 `docker compose config --quiet`，再构建和切换容器。
4. 后端启动后只读核对两张新关联表：旧自定义账号和岗位的单组关系都已迁移，关联表中没有重复主键。
5. 使用普通组员确认可以读取同步状态和所属社区汇总、不能发起同步；使用多权限组测试账号确认逐权限数据范围没有交叉越权。
6. 检查在线汇总中没有名册外人员、非组长组员或未分配社区人员；重新同步一次后确认日报和总汇总自动生成。
7. 检查人员三段列表、社区民警部门校验、所队领导内勤归属，以及排班提示不会列出业务当天之后的周末。
8. 健康接口返回 `0.9.2`、容器和近期错误日志正常后，才创建并推送 `v0.9.2` 标签。

本版不补写任何历史或未来周末排班。若上线检查失败，先切回旧镜像；新关联表是兼容新增结构，
无需删除。恢复数据库备份会覆盖上线后的账号或权限调整，仍属于高风险操作，必须另行确认。

人员请假使用列表中的独立“请假”按钮：

- 长期：不选择日期，恢复工作时点击“恢复正常”。

“人员管理 → 双休日备勤”每周维护一次：

1. 选择要安排的周，通常先点“沿用上周”。
2. 电脑端可以拖动整张人员卡片到周六、周日区域；选错后可以批量“移回待安排”。
3. 手机端不使用拖动，直接点人员卡片上的“周六”“周日”或“双休”，已经安排的人也可以点“双休”移回第一栏。
4. 请假一天的人员只能安排另一天；两天都请假的人员自动免排。
5. 保存请求必须包含当周全部备勤人员；仍在第一栏的人保存后明确记为“周六、周日都休息”，不会继续被当成漏排。
6. 页面显示“已确认全部人员”后代表本周已经完整保存。历史周也可以重新选择并补录。

在周六或周日打开人员管理时，人员状态会同时读取本周备勤表：当天被排到备勤显示“今日备勤”，排在另一天或明确双休显示“休息”，当周排班尚未保存显示“未排班”。临时请假和长期离岗优先于备勤状态。工作日仍按正常在岗、请假和长期离岗规则显示。

这项功能新增 `_personnel_attendance_history` 和 `_personnel_weekend_duty`。旧字段继续保留供旧版本
回退；首次上线以前的请假历史无法自动还原，管理人可以按已知记录补录。部署时按兼容数据库
变更规则备份三个数据库和旧程序，并检查两张新表、周排班唯一约束和走访汇总的人日恒等关系。

业务数据中有姓名、但人员管理还没有登记的人会继续显示在汇总中。管理人确认身份后应及时把
该人员加入人员管理并设置正确岗位，之后系统才能按岗位配置准确判断是否纳入统计。

## 版本号与发布

项目使用 SemVer（语义化版本），根目录 `VERSION` 是唯一版本来源：

- 修复已有功能但不增加能力：提升最后一位，例如 `0.1.0` → `0.1.1`。
- 增加兼容的新功能：提升中间一位，例如 `0.1.1` → `0.2.0`。
- 出现不兼容改动：提升第一位。项目仍在早期开发阶段时，主版本可以继续保持 `0`。

前端侧栏和 `/api/health` 都会显示这个版本。先修改 `VERSION` 并完成测试、合并和上线验证，
确认服务器确实运行新版本后，才能创建并推送同名标签，例如 `v0.1.0`。不要提前给未上线的
提交打正式版本标签。

小型且不紧急的界面调整可以先集中在本机，不必每改一处就单独发布。用户明确说“先积攒”时，
停止提交、合并和上线；等用户指定版本后，再把这一批改动放进同一个发布分支，统一完成测试、
Pull Request、合并、部署和版本标签。这样可以减少频繁上线，同时仍保持每个正式版本可追查。

只修改共享文档、注释或开发说明，且不改变运行产物时，通常不提升 `VERSION`、不触发生产部署；仍应通过功能分支和 PR 合入，确保文档修改可审查。文档如果同时描述了尚未上线的程序行为，则必须明确标注“未上线”，不能提前把计划写成现状。

## 在线日报结转与历史回算

从 `0.2.0` 开始，日报会把前期未完成、当天仍在线的任务结转到当天。单日报表显示当天应处理的
总量；区间查询按业务类型和任务主键去重，只保留区间内最后状态。页面不会增加“结转数”列。

从 `0.3.0` 开始，页面在汇总表上方增加数据概览。概览会把任务分成结转、新下发和已有任务变化，
三项互不重复并与当前任务总数相等；“新下发”必须通过相邻快照判断，不能把已有任务的内容变化
误写成新下发。概览只读取现有任务流水和快照，不需要新增数据库字段或执行历史迁移。

从 `0.4.0` 开始，电脑端自动使用表格，手机端自动使用卡片或精简列表；旧的表格/卡片偏好只为
旧前端保留。手机默认使用浮空 Dock，账号可以改回侧边栏，也可以保存自己的分类和页面顺序。
这些设置保存在 `OnlineData._users` 新增的 `mobile_navigation_mode` 和 `mobile_dock_config`
字段中。两个字段由后端启动时兼容性补齐，旧版本会忽略它们。

部署 `0.4.0` 时只需要即时备份 `OnlineData`，并保留旧后端镜像和旧前端目录；不需要因为这两个
账号设置字段额外备份另外两个数据库。上线后要确认 `_users` 已新增两个字段、旧账号默认使用
Dock、手机可以切回侧边栏、普通账号看不到用户管理和运维中心。正式标签仍要等这些检查通过后
再创建。

`0.2.0` 上线时使用受控工具完成了已有历史快照的任务流水回算：先生成临时流水和日报，验证后再
替换正式结果，且没有修改 `OnlineData`、`OnlineDataArchive` 或走访数据。该一次性工具已在
`0.9.5` 移除，历史实现可从 `v0.2.0` 标签追溯。

如果以后出现任务流水缺失，不能把旧工具复制出来直接运行。应根据当前表结构重新编写迁移，先在
测试库跑通，再备份并校验 `daily_report`、确认没有同步任务、审计所有快照证据，最后检查流水唯一性
和每张日报中“未核查＋已核查＋已完成＝数据总数”。

如果需要回退本次计算，先停止后端，再把保留的 `_v010_` 日报表按明确清单换回；这会覆盖新版日报，
属于高风险操作，必须重新确认后执行。

## 部署服务器前

生产服务器已经在 2026-07-28 完成 HTTPS、端口收紧、凭据轮换和运维中心上线。
仍然要先看 [风险清单](known-risks.md)，尤其不要忽略 OAuth 明文、单机备份和凭据风险。

用户已经授权正常代码、前端更新和兼容性数据库变更默认同步到服务器。改动检查通过并合并到 `main`
后，除非用户明确说“不同步”“只改本地”或“先不要部署”，否则继续完成部署。

兼容性数据库变更是指只新增表或可空字段，而且旧版本仍能继续运行。部署前必须通过测试、
备份受影响的数据库并准备回退办法。删除或覆盖数据、恢复备份、删除/重建表和数据卷、不可逆迁移、
轮换凭据等高风险操作仍要单独确认。

每次部署前必须确认：

1. 要部署的是哪个版本。
2. 前端构建和后端检查已经通过。
3. 服务器上的 `.env` 和数据卷不会被覆盖。
4. 已按下面的风险等级准备回退办法。
5. 涉及数据写入或数据库结构时，相关数据库备份不是空的并已通过完整性检查。

部署备份按改动范围处理：

- 纯前端更新：保留上一版 `frontend/dist`，不额外备份数据库。
- 不改数据库结构和数据写入逻辑的后端更新：保留旧 Docker 镜像，不额外备份数据库。
- 修改同步、导入、报表计算等可能写入数据的逻辑：备份受影响的数据库；无法准确判断影响范围时备份三个数据库。
- 修改数据库结构、执行数据迁移或其他高风险操作：完整备份三个数据库，并按高风险规则再次确认。
- 修改 nginx、Compose 或证书配置：只备份相关配置，除非这次改动同时涉及数据库。

平台的每日数据库备份继续保留 7 天。它是日常兜底，但不能替代数据库迁移或高风险操作前的即时备份。

部署后要检查：

1. 健康接口能否访问。
2. 容器是否正常运行。
3. 日志是否有报错。
4. 登录和退出是否正常。
5. 同步、统计和关键数据是否正常。

## 服务器容量与发布材料保留

自动发布会保留历史源码包、发布记录、上一版镜像和按风险范围创建的即时备份，但不会自动执行宽泛清理。日常以 5GB 可用空间作为提前整理线；固定发布脚本在空间低于其硬性最低值时会拒绝切换，但这个保护只用于避免发布时耗尽磁盘，不能代替容量管理。

固定保留顺序：

1. 当前生产后端镜像及其 `latest` 标签。
2. 上一稳定版本的回退镜像。
3. 当前与上一版的发布记录、源码留档和必要即时备份。
4. 平台每日备份保留策略要求的最近成功备份。
5. MySQL 数据卷、证书续期镜像和正在运行容器依赖的镜像。

容量不足时先只读执行 `df -h /`、`docker system df`、发布目录分项统计和日志占用统计。确认当前版本、上一版和所有运行容器的真实镜像 ID 后，只能按完整仓库名和标签白名单删除更旧的 `binhu-backend` 镜像。系统日志可以压缩到明确上限；构建缓存可以在空间再次紧张时清理，但会让下一次构建变慢。

不得使用 `docker system prune -a`、`docker compose down -v`、针对 Docker 根目录的递归删除，或根据未验证变量批量删除文件。不得把 MySQL 数据卷、平台每日备份或当前发布记录当作普通缓存。`/root/binhu/releases`、`/var/lib/binhu-deploy/releases` 和 `deploy-backups/automated` 只有在逐项确认当前与回退版本后才能清理，不能因为目录名含有“旧”就整目录删除。

2026-08-06 的实际整理删除了 122 个更旧的后端镜像标签，并把 systemd 日志从约 632MB 压缩到约 184MB；当前 `0.15.2` 与上一版 `0.15.1` 镜像均保留。整理后可用空间为约 6.7GB，健康接口、三个容器和近期日志正常。此次没有删除数据库卷、数据库备份、发布源码留档或构建缓存。

## 安全入口怎么部署

生产环境由 nginx 统一提供 HTTPS，MySQL 和 Uvicorn 不能直接响应公网请求。
当前端口关系是：

- 滨湖平台使用 nginx 的 HTTPS 443。
- 后端只绑定 `127.0.0.1:37125`，由 nginx 转发。
- MySQL 不发布宿主机端口，只在 Compose 内部使用 `mysql:3306`。

当前服务器的 HTTP 80 还承载另一套独立应用，滨湖平台没有接管或重定向它。不能直接用
仓库里的默认 80 配置覆盖服务器现有站点；更新 nginx 时要保留 ACME 验证目录和原站点。

服务器没有域名时，可以使用支持 IP 地址的短期证书。部署时先用 Certbot 5.4 或更高版本
申请证书，再把实际证书软链接到：

```text
/etc/nginx/ssl/binhu/fullchain.pem
/etc/nginx/ssl/binhu/privkey.pem
```

IP 地址证书只有约 6 天有效期。生产服务器使用 `binhu-certbot-renew.timer` 每天检查两次，
续期成功后执行 `nginx -t` 和重新加载。日常检查：

1. 80 端口的 ACME 验证目录可以访问。
2. `nginx -t` 通过。
3. HTTPS 健康接口和登录都正常。
4. `systemctl is-active binhu-certbot-renew.timer` 返回 `active`。
5. 从外部确认 `443` 可连接，`3306` 和 `37125` 不可连接。

续期镜像和 systemd 模板保存在 `nginx/`。如果本地 Certbot 镜像被清理，可以重新构建：

```bash
docker build -f nginx/Dockerfile.certbot -t binhu-certbot:5.4.0 nginx
```

安装或更新定时器前，先比较服务器现有 unit 文件并备份，不能直接覆盖未知配置。

生产 `.env` 还要设置：

```dotenv
BINHU_SESSION_COOKIE_SECURE=true
BINHU_CORS_ALLOWED_ORIGINS=https://<公网地址>
```

新建空数据库时，临时设置 `BINHU_BOOTSTRAP_ADMIN_USERNAME` 和
`BINHU_BOOTSTRAP_ADMIN_PASSWORD`。首个超级管理员创建并成功登录后立即删除这两个变量。
已有用户的生产数据库不需要设置。

## 数据库备份与恢复

下面是给负责运维的人使用的备份命令。执行前仍要确认服务器、容器和备份目录是否正确：

```bash
docker exec binhu-mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers \
  --default-character-set=utf8mb4 \
  --databases OnlineData OnlineDataArchive daily_report' \
  > "/root/binhu_backup_$(date +%Y%m%d_%H%M%S).sql"
```

`--databases` 不能省略。省略后，`mysqldump` 会把第二、第三个数据库名称误当成表名，三库备份会失败。

备份后至少检查：

- 文件存在。
- 文件大小不是 0。
- 文件开头是正常的 SQL 转储内容。
- 重要操作前，备份已经复制到服务器之外的安全位置。

恢复会覆盖数据，不能自动执行。恢复前必须再次备份当前数据，并得到用户对目标服务器、备份文件和覆盖范围的明确确认。

不要使用 `docker compose down -v` 排错或恢复数据，它会删除数据卷。

## 定时同步怎么使用和排查

超级管理员可以在“设置 → 系统设置”中开启、关闭或修改同步间隔。修改间隔或重新开启后，
倒计时会从保存时刻重新开始。常用间隔可以直接选择，自定义值必须在 5 分钟到 7 天之间。

所有登录用户都可以读取同步状态和下一次倒计时；只有拥有 `sync.trigger` 权限的账号可以点击
“立即同步”，后端会拒绝其他账号发起同步，不能只依赖前端按钮隐藏。同步成功后自动生成日报，
页面不再提供单独的“生成日报”按钮。

同步状态分成四步：等待、同步在线数据、生成报表、完成。页面显示的步骤数来自真实任务进度，
不会再显示估算的假进度。自动同步失败或部分失败后，超级管理员可以从页面上的铃铛查看个人提示。

所有登录用户都能打开消息中心。公告对所有账号可见，但每个人的已读状态分别保存；个人提示只对
接收者可见。超级管理员可以在消息中心发布或删除公告。首次升级会自动发布“出勤历史数据说明”，
因此走访汇总页面不再重复显示同一条长期提示。

如果自动同步没有按时开始，按下面的顺序检查：

1. 查看“系统设置”里是否开启，以及下一次执行时间是否合理。
2. 查看最新同步状态，确认没有另一项任务仍处于等待中或运行中。
3. 查看后端日志中是否有 `[SCHEDULER]` 或 `[SYNC]` 报错。
4. 只读检查 `_sync_schedule` 和最新 `_sync_log`，不要直接修改时间或任务状态。
5. 如果刚发生后端重启，确认中断任务已经被标为失败，并且下一次时间已重新安排。

部署包含定时同步改动的版本后，还要额外检查：

1. `_sync_schedule`、`_notifications`、`_announcements`、`_announcement_reads` 和 `_sync_log` 已经存在。
2. 使用普通管理员、组长和组员验证手动同步权限。
3. 实际等待一轮定时同步，确认来源显示为“自动触发”。
4. 确认分汇总表全部成功后，总汇总表才最后更新。
5. 使用普通账号确认能看到公告、看不到他人的个人提示，并确认不同账号的公告已读状态互不影响。
6. 不要在生产环境故意制造失败；失败通知使用自动化测试验证。

## 正式部署入口

正式版本使用 GitHub 仓库中的 `Deploy production` 手动工作流发布，不再从开发电脑逐文件传输。普通 push、
Pull Request 和 `CI` 工作流没有生产 Secret，也不能连接服务器。代码必须先通过 PR 合并到 `main`，然后由
发布人手动填写：

- `ref`：已经合并到 `main` 的提交、分支或标签；通常使用 `main`。
- `expected_version`：必须与该提交根目录 `VERSION` 完全一致。
- `backup_scope`：`none`、`online`、`daily` 或 `all`，按本手册“部署服务器前”的风险范围选择。
- `release_scope`：默认 `auto`。生产提交可验证时，纯后端变化发送后端精简包，纯前端变化发送前端精简包；
  前后端同时变化、Compose、Nginx、部署脚本、未知路径或状态不确定时发送完整包。也可以明确选择 `backend`、
  `frontend` 或 `full`，但手动精简范围遇到不属于该范围的运行文件会被拒绝。

网页上可以从 GitHub Actions 手动运行，也可以在已经登录 GitHub CLI 的受控电脑执行：

```powershell
$version = (Get-Content VERSION -Raw).Trim()
gh workflow run deploy-production.yml --ref main `
  -f ref=main `
  -f expected_version=$version `
  -f backup_scope=none `
  -f release_scope=auto
```

`backup_scope=none` 只适用于纯前端，或不修改数据库结构和数据写入逻辑的普通后端更新。涉及在线同步、导入、日报计算、数据库结构或迁移时，必须按“部署服务器前”的风险表改为 `online`、`daily` 或 `all`，不能因为自动工作流方便就一律填 `none`。

触发后记录工作流地址并等待唯一一次运行结束，不要因构建时间较长重复点击。可以使用：

```powershell
gh run list --workflow deploy-production.yml --limit 1
gh run watch <运行编号> --exit-status
```

只有工作流成功、生产健康接口返回预期版本、容器和近期日志正常后，才创建并推送 `vX.Y.Z` 标签。工作流失败时先查看失败步骤；不要在原因不明时重复发布，也不要改用手工上传掩盖固定入口的问题。

工作流始终运行部署脚本测试；后端或完整发布运行后端测试和 Python 编译，前端或完整发布运行前端测试和生产构建。通过后
生成与发布范围一致的发布包：完整发布包含源码和前端产物，后端发布只包含 `VERSION` 与 `backend/`，前端发布只包含
`VERSION` 与 `frontend/dist`。包保存
30 天供审计，再用专用受限身份发送到服务器。目标提交不是 `main` 的
祖先、版本不一致、并发发布、主机指纹不一致或任一检查失败时都不会切换生产。

### 第一次安装固定入口

部署身份只需在每台生产服务器初始化一次：

1. 在受控电脑生成一把仅供 GitHub Actions 使用的 Ed25519 密钥，不设置为日常 root 登录密钥，也不放进仓库。
2. 使用已经验证的人工运维入口，把公钥和 `deploy/` 下三个服务器脚本复制到临时目录。
3. 以 root 执行 `install-server-deployer.sh <公钥文件> <平台 HTTPS 地址>`。安装器创建锁定密码的 `binhu-deploy` 账号、强制命令、固定 sudo 规则和 root 所有的发布目录，并把正式 HTTPS 地址写入服务器私密配置用于发布后自检。
4. 检查该密钥不能打开交互 Shell、不能端口转发，错误命令会被拒绝；同时确认原人工运维入口仍可用于紧急回退。
5. 在 GitHub 建立 `production` Environment，并保存 `BINHU_DEPLOY_HOST`、`BINHU_DEPLOY_PORT`、`BINHU_DEPLOY_SSH_KEY` 和 `BINHU_DEPLOY_KNOWN_HOSTS` 四个 Secret。主机指纹必须从已经信任的人工 SSH 连接核对，不能只相信临时网络扫描。

GitHub 不保存 root 密钥、服务器 `.env`、数据库密码或腾讯凭据。`binhu-deploy` 的公钥授权行固定带
`restrict` 和服务器强制命令；即使工作流配置写错，也不能把它变成普通远程终端。

`/usr/local/sbin/binhu-deploy` 和强制网关属于服务器安全边界，不会随普通应用发布自动覆盖。以后修改
`deploy/` 下的服务器脚本时，必须先走代码 Review，再由人工 root 入口重新运行安装器并复核权限；不能让
旧发布脚本自动更新它自己。

### 发布、回退和记录

GitHub 在受限命令中同时传入发布包的精确字节数，服务器只读取该长度，避免依赖 SSH 会话关闭来判断文件结束。
服务器随后按固定顺序执行：校验包与提交、检查磁盘、检查 Compose、确认没有运行中的同步或备份、
按范围构建候选后端或复用现有后端镜像、保存对应旧程序和必要的旧镜像、创建并校验所选数据库备份、切换、核验内部健康版本、前端资源和正式
HTTPS 健康接口。公网自检由服务器在固定脚本内执行，避免 GitHub Runner 到国内 443 的链路策略被误判为应用故障。成功记录在
`/var/lib/binhu-deploy/history/`，当前结果在 `current.json`；程序和即时数据库备份保存在项目的
`deploy-backups/automated/` 下。

后端精简发布不会替换现有 `frontend/dist`，但会先替换整个后端目录，避免已删除的旧 Python 文件残留。切换失败会
自动恢复旧程序和旧后端镜像并重建服务。前端精简发布不会构建或替换后端镜像，只备份和替换 `VERSION` 与
`frontend/dist`，随后重建后端和运维代理容器以加载新版本；失败时恢复旧版本号和旧前端。失败记录不会覆盖
`current.json` 中最后一次成功发布。自动流程绝不导入数据库备份，也不撤销腾讯文档等外部
结果。涉及迁移或外部写入时，发布前必须另写业务回退办法；需要恢复数据库时仍按“数据库备份与恢复”一节
重新确认。服务器磁盘上的历史发布目录、即时备份和旧镜像不会被发布脚本自动删除，清理前必须先核对当前与
回退版本、备份保留和目标绝对路径。

只有 GitHub Actions 故障且业务确实不能等待时，才使用 `AGENTS.local.md` 的私密人工入口应急发布。应急发布
仍要使用同一提交、检查、备份和回退规则，并在任务记录中说明绕过原因；不能在生产服务器临时修改业务代码。
真实地址、账号、密码、主机指纹和密钥不能写进仓库脚本、命令示例或共享文档。

一次性迁移、修复或核验代码在任务完成并留下 Git 标签后应从主线删除。再次遇到类似问题时，应按
当时的结构和风险重新编写短期工具，不把历史脚本当作长期运维入口。

## v0.16.0 八库迁移操作顺序

本版本的代码发布和数据库迁移是两件事。先通过 GitHub `Deploy production` 发布兼容代码，`backup_scope=all` 才表示八库完整备份；确认备份清单、SHA-256、磁盘空间和同步/备份空闲后，才进入维护窗口。

迁移窗口只允许按以下顺序执行：`measure` 只读测量 → `visit` → `dispatch` → `platform` → `work_logs` → `registry_addresses` → 身份证 HMAC/标记快照回填 → 最后启用 Registry/Workflow 功能。前六个阶段和 HMAC 回填已完成；后续开启 Registry/Workflow 前仍要单独备份、核对权限和回退条件。

示例（在后端容器或具备生产依赖的维护环境执行，不在本机执行）：

```text
python -m migrations.domain_migration measure --schema OnlineData
python -m migrations.domain_migration migrate --domain visit
python -m migrations.domain_migration migrate --domain visit --apply
python -m migrations.domain_migration verify --domain visit
python -m migrations.domain_migration migrate --domain platform --apply
python -m migrations.domain_migration verify --domain platform
```

Registry/Workflow 开关在全部迁移和权限核验完成前保持关闭。新库产生业务写入后不能自动切回旧表；异常时先冻结入口、备份新库，再制定反向复制方案。附件目录由 `BINHU_WORKFLOW_ATTACHMENT_DIR` 指定，数据库备份 manifest 同时记录八库段摘要和附件归档摘要。

### 0.18.1 腾讯接口传输超时修复

腾讯文档偶发返回 HTTP 200 但业务码 `400010`，并在错误信息中包含 `ReadFrame`、`transport` 或 `i/o timeout`。这表示上游 TCP 读取超时，不表示表格被清空，也不应触发历史数据归档。

- 客户端对明确的传输型 `400010` 最多重试 3 次，并使用递增等待；参数、权限和其他业务错误不重试。
- 预览失败时保持已有预览结果，不执行历史导入；只有预览统计稳定且经人工核对后才允许正式导入。
- 发布后先保持调照片名单读取、写回开关关闭，重新执行只读预览，比较行数、批次边界和异常数量后再决定下一步。

- 原生客户端通过 `X-Binhu-Client-Platform` 和 `X-Binhu-Client-Version` 报告平台与 SemVer，启动时调用 `/api/app/bootstrap` 取得服务端版本、最低版本、维护状态、业务时间、账号权限和平台功能开关。
- 部署变量为 `BINHU_WINDOWS_MIN_SUPPORTED_VERSION`、`BINHU_ANDROID_MIN_SUPPORTED_VERSION`、`BINHU_CLIENT_WRITE_VERSION_ENFORCEMENT_ENABLED` 和 `BINHU_CLIENT_WRITE_IDENTIFICATION_REQUIRED`。首次上线两端最低版本保持 `0.0.0`、身份必填保持关闭，确认网页和正式原生客户端都已经发送请求头后再提高最低版本并开启身份必填。
- 提高最低版本后，已声明 Windows 或 Android、但版本缺失、非法或过旧的客户端写请求返回 `426 client_upgrade_required`。这项检查只处理接口兼容性，不能替代登录、权限、数据范围和业务版本冲突校验。
- 本版不修改数据库结构和业务数据，正式发布使用 `backup_scope=none`；上线后检查健康版本、匿名及登录 bootstrap、维护状态、网页端正常写入和一组模拟旧客户端 `426`。回退时恢复上一版程序即可；紧急情况下可以先关闭写版本检查，但不得借此绕过业务权限。

### 0.19.1 照片调取工单创建修复

- 修复照片工单详情写入语句少一个参数占位符导致的 HTTP 500。事务在错误时会完整回滚，因此旧故障不会留下半截工单或腾讯名单写回队列。
- 增加照片快捷申请完整创建路径测试，直接校验 SQL 占位符与参数数量一致。本版不修改数据库结构和业务规则，正式发布使用 `backup_scope=none`；回退时恢复 `0.19.0` 程序和镜像即可。

### 0.19.7 腾讯批次结单后的照片补挂

- 本版不改数据库结构，但会重新计算既有照片导入批次并写入工单附件，正式发布使用 `backup_scope=all`。
- 对因腾讯时间分隔行先行结单而全部未匹配的 ZIP，基础管控重新上传完全相同的 ZIP；平台会复用原批次并返回新的预览，不会创建第二个批次。
- 确认前核对匹配、未匹配和姓名警告数量；确认后检查目标工单附件、`photo_import_complete` 事件、申请人通知和“已处理”列表。未匹配照片继续保留在批次明细，不猜测绑定。
- 补挂范围只包括最近一次腾讯批次、七天内自动结单且没有附件的工单，避免一万多条历史完成工单被新 ZIP 误命中。
- 若确认过程失败，数据库事务回滚并清理本轮新保存的附件文件；原工单完成状态和原批次记录保持不变。

### 0.19.8 工单入口与附件权限修复

- 程序启动时为旧 `flow_post` 权限组补充 `workflow.attachment.view`，为旧 `internal_business` 权限组补充 `workflow.ticket.create` 和 `workflow.ticket.view`；中队长重新登录后应看到工单中心。
- 组员只能预览、下载其本来就有权查看的工单附件。上传和删除接口改为要求工单处理或管理权限，不能通过直接调用接口绕过页面按钮。
- 本版不修改数据库结构和业务数据，只更新系统权限组 JSON；发布使用 `backup_scope=all`。上线后检查中队长导航、组员附件预览/下载、组员无上传/删除按钮及近期 403/500 日志，不制造测试工单或测试附件。
- 腾讯名单追加位置按 A–G 实际非空尾行计算，不再使用工作表容量。上线后执行一次完整同步，使被人工移动的现有平台申请按唯一摘要从旧物理行自动重定位；核对工单和腾讯正文均未重复创建。
- “立即同步”完整读取可能超过三十秒，前端最长等待五分钟。按钮执行时先清空到期的待写回队列，再读取全表；页面超时不能作为后端同步失败或腾讯未写入的判断依据。

### 0.19.6 调照片名单完整核对重定位

- 发布前备份范围使用 `all`。本版不改表结构，但完整核对会在事务内更新 `WorkflowData.photo_sheet_rows` 的物理行定位与同步状态。
- 部署后等待或手动触发一次完整核对，确认运行成功、`last_full_sync_date` 更新为当天、没有新增重复工单，且五分钟增量同步继续推进游标。
- 若完整核对失败，事务会恢复原映射；保留增量同步，不要删除旧映射或重复执行历史导入。先检查同步运行的安全错误摘要和冲突列表。
- 回退程序不会自动反向修改已经成功重定位的行号；由于工单和腾讯正文均未删除或覆盖，可保留新映射并回退镜像。需要人工调整映射时必须先备份 `WorkflowData`。

### 0.19.5 调照片名单同步恢复与即时写回

- 本版不新增表或字段，但会创建照片工单、来源行映射和腾讯写回记录，正式发布使用 `backup_scope=all`，发布范围可用 `auto`。
- 发布前确认调照片名单读写开关和全局在线回写开关保持现有值，不通过关闭回写来部署。暂停普通在线数据自动同步只用于避免部署切换与长任务重叠；不修改真实腾讯行做测试。
- 上线后先只读核对健康版本、`photo_sheet_sources.last_cursor_row`、腾讯当前总行数、最近 `photo_sheet_sync_runs` 和现有 outbox 状态。随后等待或手动触发一次照片名单增量同步，确认游标推进、腾讯自然新增行形成工单且没有重复映射。
- 平台向腾讯的即时追加使用下一条自然产生的照片申请验收：本地工单应立即创建，腾讯暂时失败时只显示待同步并保留重试，不得删除或重新提交工单。每日完整核对即使超时也不应阻止之后的增量运行记录出现。
- 回退程序时恢复 `0.19.4` 镜像即可，已经创建的自然工单、映射和腾讯行不得删除或自动回滚；如发现重复外部行，先关闭照片名单写入、备份八库并按冲突记录人工核对。

### 0.19.4 工单恢复待领取与页面间距优化

- 管理员、超级管理员及已有工单管理权限的账号，可以把误退回到“待补充”的工单恢复为“待领取”。恢复时必须填写原因，系统会清空当前处理人、释放旧领取记录、恢复原岗位队列和处理时限，并保留退回与恢复事件。
