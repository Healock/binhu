# 开发与运维手册

开始较大的功能、修复或数据库改动前，先看 [高效开发与验证流程](development-workflow.md)，提前确定检查范围，避免上线时临时追加和重复验证。

## 最常用：两台电脑怎么开发

记住三句话：

1. 开工前先拉取。
2. 换电脑前先提交并推送。
3. 功能完成后才合并到 `main`。

### 开始一个新功能

不管在家里还是单位，都先更新正式代码：

```powershell
git switch main
git pull --ff-only
```

然后建立一个功能分支：

```powershell
$branchName = "feat/example-topic"
git switch -c $branchName
git push -u origin $branchName
```

把 `example-topic` 换成简短的功能名称。不要建立“家里分支”或“单位分支”。

### 准备换电脑

离开当前电脑前，把进度保存到 GitHub：

```powershell
git status
git add -- path/to/reviewed-file
git commit -m "开发进度：简单说明做了什么"
git push
```

功能没写完也可以提交到功能分支，只要暂时不合并进 `main`。

### 在另一台电脑继续

这台电脑第一次使用该分支：

```powershell
git fetch origin
git switch --track origin/feat/example-topic
```

这台电脑已经有该分支：

```powershell
git switch feat/example-topic
git pull --ff-only
```

### 功能完成

检查通过后推送最后一次修改，在 GitHub 创建 Pull Request，然后合并到 `main`。

合并后，两台电脑分别运行：

```powershell
git switch main
git pull --ff-only
```

`.env`、`backend/.env` 和 `AGENTS.local.md` 不会通过 GitHub 同步，两台电脑要分别配置。

## 第一次配置电脑

复制项目配置模板：

```powershell
Copy-Item .env.example .env
```

然后编辑 `.env`，把所有 `replace-with-*` 示例值换成本机使用的值。不要把真实密码发到聊天或提交到 Git。

如果使用 Docker，可以检查配置：

```powershell
docker compose config --quiet
```

如果直接启动后端，还要在 `backend/` 中建立自己的 `.env`。字段示例：

```dotenv
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USER=binhu
MYSQL_PASSWORD=<本机数据库密码>
MYSQL_ONLINE_DATA_DB=OnlineData
MYSQL_ARCHIVE_DB=OnlineDataArchive
MYSQL_DAILY_REPORT_DB=daily_report
ENCRYPTION_KEY=<本机应用密钥>
```

## 本地启动

前端：

```powershell
Set-Location frontend
npm install
npm.cmd run dev
```

前端修改完成后检查生产构建：

```powershell
npm.cmd run build
```

后端：

```powershell
Set-Location backend
python -m pip install -r requirements.txt
python -m uvicorn main:app --reload --port 8000
```

后端启动前需要三个可用的 MySQL 数据库，具体用途见 [架构说明](architecture.md)。

## 工作日志日报

管理员和超级管理员可以在“数据工作台 → 工作日志生成”选择业务日期并创建日报草稿。周报和月报在收到对应模板前保持禁用。

- 同一天只有一份日报草稿。创建者编辑，其他管理员可以查看、导出或主动接管。
- “草稿管理”集中显示全部日报草稿，并支持按日期、创建人或当前编辑人查找。管理员和超级管理员都可以删除草稿，删除前必须二次确认；删除不可恢复，但同一天可以重新创建。删除不会影响在线数据、走访数据或统计报表，并会写入超管操作记录。
- 页面约 1 秒自动保存。出现“保存冲突”时应重新读取草稿，不能反复覆盖。
- 创建草稿后系统统计不会自行变化；确需更新时点击“刷新系统数据”，人工填写和人工覆盖会保留。
- 工作日志中的“网格员数”由人员管理、统计岗位、请假和双休日备勤共同计算。已有草稿点击“刷新系统数据”后会补齐尚未填写的人数；已经人工修改的数字不会被覆盖。周末排班没完成时人数保持空白，应先完成人员管理中的排班。
- 导出前会列出尚未填写的字段。确认后可以带空白继续导出。
- 导出的 PDF 不保存在服务器，草稿保存在 `OnlineData._work_log_drafts`。
- 业务日期为 7 月 14 日时，正文和系统取数都使用 7 月 14 日，文件名以 `0714日报` 开头，落款为 7 月 15 日。

PDF 版式由工作日志结构和后端打印样式共同生成。旧 `.doc`、`.docx` 样例只能在本机参考，不能复制进仓库。发布前要检查 PDF 可以打开、中文正常、十六张表格没有截断、没有未替换占位符，也不能出现旧样例中的姓名、身份证号、电话号码或警情文字。

`0.8.0` 使用 `daily-v2` 表单结构。访问旧版草稿时先把原始 JSON 完整保存到新快照的 `legacy_v1` 区域，再映射能够识别的字段，不删除旧内容。部署前备份 `OnlineData` 并保留旧后端镜像和前端；部署后检查页面权限、旧草稿升级、自动保存冲突、PDF 下载、容器日志和 `/api/health` 版本。

`0.8.1` 只调整 PDF 公文版式，不修改草稿字段或数据库。发布时保留旧后端镜像即可；验收重点是红色标题和分隔线、基础数据与章节顺序、正文层级、问题分析颜色、表格分页和中文字体。

`0.8.2` 调整叮咛行动、矛盾纠纷和出租房责任落实文字，并把自购房走访人员汇总接入工作日志
系统快照。新建草稿会自动带入自购房数据；已经存在的草稿要由当前编辑人点击“刷新系统数据”
后才会读取，避免后台数据悄悄改变旧草稿。出租房屋核查同步同时允许把同一身份证号和手机号的
重复行合并为一个核查对象；两个身份字段都为空时仍停止同步，不猜测是否同一人。

`0.8.3` 在社区管理中增加社区民警名单，一个社区可以填写多位。新建工作日志草稿会把姓名带入
全部按社区生成的表格，多位民警用“、”连接。升级只给 `_communities` 增加可空的
`police_officers` 字段，旧版本会忽略该字段；上线前按兼容数据库变更流程备份三库和旧程序。

`0.8.4` 累积界面细节调整，增加工作日志草稿管理，以及面向全员的公告和个人提示。草稿删除只
移除被明确选中的记录；公告升级会新增两个兼容表。发布前应检查草稿筛选、指定日期打开、删除确认、
同日重建、普通账号查看公告、个人提示隔离、公告独立已读和超管发布删除权限。

## 0.9.0 权限和账号名单上线

`0.9.0` 增加部门、权限组、账号关联、唯一登录和空闲退出。数据库变更都采用新增表、可空字段和
兼容字段，旧程序会忽略它们；但正式启用社区范围以前，必须先完成名单预览。

固定上线顺序：

1. 备份 `OnlineData`、旧后端镜像和旧前端，并把旧账号的角色、人员关联和有效会话清单保存到私密回退材料中。
2. 部署新程序，让后端只创建兼容结构。此时 `permission_enforcement_enabled` 仍为 `0`，未关联的旧低权限账号继续沿用原查看能力。
3. 把名单临时放入后端容器，只运行预览。预览必须逐行显示用户名、姓名、所属部门、岗位、默认权限组和“新增或跳过”。
4. 只要出现重复用户名、重复人员、人员姓名不唯一、部门不符合岗位、未知名单职位或岗位没有默认组，整批停止，不写入数据库。
5. 项目管理人确认预览无误后，才正式创建账号、发布初始密码公告并启用新权限。
6. 分别使用流口岗、片长、基础管控、管理员和超级管理员账号检查，再创建 `v0.9.0` 标签。

名单文件至少包含“用户名”“姓名”和“职位”，属于私密文件，不能复制到仓库、提交 Git 或写进共享文档。
已存在的用户名整行跳过，不补人员关联、不改权限且不重置密码。姓名能与人员管理唯一匹配时，
继续使用该人员的岗位默认组；未匹配人员只允许按以下固定规则处理：

- “社区民警”和“所（队）领导”创建为不关联人员资料的管理员账号。
- “内勤岗”创建为不关联人员资料的内勤业务组账号。
- “流口岗”先创建“组员、待分配部门”的人员记录并关联账号，之后由超级管理员在人员管理中分配社区。

手机号和身份证号没有参与当时的账号导入。一次性名单工具已在导入和核验完成后从当前源码移除；
历史实现可从 `v0.9.0`、`v0.9.1` 标签追溯，但不得直接复制到当前生产环境执行。以后再次批量建号时，
应针对新名单重新制作只预览、整批校验、密码脱敏和事务回滚都可验证的短期工具。

上线后固定检查：

- 旧超级管理员仍可登录，且至少保留一个超级管理员。
- 流口岗只能看到业务记录所属社区的数据，社区别名可以正确归入正式社区；无社区部门时显示空数据说明。
- 片长只能全局查看；中队长和基础管控可以同步、上传、排班、请假和管理工作日志，但不能修改人员或社区。
- 管理员可以修改人员和社区；超级管理员可以管理账号、权限组和岗位映射。
- 在另一浏览器登录同一账号后，旧会话显示“账号已在另一台设备登录”；同一浏览器多个标签页保持正常。
- 默认空闲 30 分钟，到期前 2 分钟提示；后台轮询、自动保存和文字输入不续期，“继续使用”、主动查询和提交会续期。

权限组调整会在账号下一次请求时生效。若上线检查失败，先切回旧程序；恢复账号或会话快照会
覆盖当前状态，属于高风险操作，必须另行确认，不能在普通回退中自动执行。

## 0.9.2 多权限组和在线汇总固定口径上线

`0.9.2` 新增 `_position_permission_group_links` 和 `_user_permission_group_links`，分别保存岗位和账号的
多个权限组。后端启动时会把旧单权限组关系写入新表；旧 `_position_permission_groups` 和
`_users.permission_group_id` 继续保存排序后的第一个组，所以旧程序可以直接忽略新表并回退。

本版同时改变在线汇总展示口径：单日、区间、总汇总、概览和工作日志自动取数固定只保留人员管理中
有有效社区部门的组长、组员。旧日报表和原始业务数据不重写，查询时动态过滤并重算社区合计。
日报不再有单独生成入口，只在手动或自动同步的末尾按“分汇总 → 总汇总”生成。

上线前固定准备：

1. 备份 `OnlineData` 和 `daily_report`；`OnlineDataArchive` 本版不变，不重复备份。
2. 保留旧前后端镜像，并确认准备上线的提交、`VERSION` 和前端产物属于同一版本。
3. 在服务器运行 `docker compose config --quiet`，再构建和切换容器。
4. 后端启动后只读核对两张新关联表：旧自定义账号和岗位的单组关系都已迁移，关联表中没有重复主键。
5. 使用普通组员确认可以读取同步状态和所属社区汇总、不能发起同步；使用多权限组测试账号确认逐权限数据范围没有交叉越权。
6. 检查在线汇总中没有名册外人员、非组长组员或未分配社区人员；重新同步一次后确认日报和总汇总自动生成。
7. 检查人员三段列表、社区民警部门校验、所队领导内勤归属，以及排班提示不会列出业务当天之后的周末。
8. 健康接口返回 `0.9.2`、容器和近期错误日志正常后，才创建并推送 `v0.9.2` 标签。

本版不补写任何历史或未来周末排班。若上线检查失败，先切回旧镜像；新关联表是兼容新增结构，
无需删除。恢复数据库备份会覆盖上线后的账号或权限调整，仍属于高风险操作，必须另行确认。

失败时先回退旧前后端镜像。新关联表和兼容字段保留不删除；恢复数据库备份会覆盖上线后的人员、

## 0.10.0 在线查询与腾讯安全回写上线

`0.10.0` 新增片区、腾讯来源定位、业务投影和 90 天完整回写审计。旧程序会忽略这些新增表和
`_communities.area_id` 可空字段，因此程序回退不要求删除新结构。在线回写配置首次创建时默认关闭，
只有完成只读核验后才启用。

固定上线顺序：

1. 完整备份 `OnlineData`、`OnlineDataArchive` 和 `daily_report`，检查文件非空、gzip/SQL 可读，并保留旧前后端镜像。
2. 确认待发布提交、根目录 `VERSION` 和前端产物均为 `0.10.0`；在服务器运行 `docker compose config --quiet`，再构建并切换程序。
3. 保持 `online_writeback_enabled=0`，只读核对 `_areas`、`_area_leader_links`、`_online_source_rows`、`_online_source_projection`、`_online_source_cache_state` 和 `_online_writeback_audit` 已创建，且东片、中片、西片及十二个社区映射正确。
4. 等待或执行一次正常同步建立来源定位；核对每个启用来源表的缓存行数、物理位置唯一约束、业务父行数量、重复来源数量和待同步数量。同步本身会照常更新业务库、快照和日报，不要为了测试回写制造业务数据。
5. 分别核对组员、片长、基础管控和超级管理员的查询范围、可编辑字段和新增删除按钮；归档、尚未定位的来源和回写开关关闭状态必须只读。
6. 通过系统设置启用在线回写，确认查询接口返回开关已开启，但 Agent 不对腾讯测试表或业务表执行新增、修改或删除。真实回写由项目管理人自行测试。
7. 检查健康接口为 `0.10.0`、容器正常且近期日志没有新增错误后，创建并推送 `v0.10.0` 标签。

异常时先在系统设置关闭在线回写，查询和同步仍可继续使用。程序问题则切回旧前后端镜像；新增表
和兼容字段可以保留。恢复三库备份会覆盖上线后的真实同步和业务操作，属于高风险操作，必须另行确认。

## 走访明细导入

“数据工作台 → 走访汇总”支持管理员和超级管理员分别上传走访明细、星级评定 `.xlsx`：

- 单个文件不超过 20MB，最多处理 10 万条有效记录。
- 页面会显示现有数据的起止日期和无数据日期，上传重叠区间不会重复增加记录。
- 去重按“业务日期＋标准化地址＋网格员姓名”判断；同一网格员同日同地址只保留最新一条，不同网格员分别保留。
- 错误行会跳过，其他正确行继续入库；上传完成后可查看错误和提醒。
- 组长和组员只能查看数据范围，后端也会拒绝他们上传。
- 社区管理可以为正式社区维护多个别名。别名必须按来源数据中的完整文字填写，系统只清理首尾空格，不会自动删除“社区”或“村”；匹配成功后，走访汇总和在线数据的单日、区间、总汇总都会统一显示正式社区名称。例如正式名称“南厍”可以添加别名“南厍村”。原始在线表格和快照不改写，历史汇总在读取时按当前别名配置归并。
- 网格员跨社区走访属于正常情况，不会因为社区部门与走访社区不同而产生提醒。
- 星级评定按标准化地址关联采集时间前后 24 小时内最接近的走访，只更新 `t_visit_details`，不建立第二张星级业务表。
- 无法匹配或时间距离完全相同而无法判断的评定不会强行写入；页面会显示提醒。
- 页面会显示已星级评定数量，以及“仅入户走访、没有星级评定”的数量。
- 页面上方的全库概览显示数据库日期范围；查询后还会显示当前类别和日期区间的走访户数、
  参与人员、在岗人日、总变动数、星级评定和仅走访未评定。
- 页面可以按入户业务日期选择一天或一段时间，同时查看网格员汇总和社区汇总。
- 汇总类型可以选择“出租房”或“自购房”。出租房默认统计组长和组员，也可以由超级管理员
  修改岗位范围；自购房固定统计人员管理中的“自购房”岗位。
- 汇总中的社区按本次实际走访社区统计；同一网格员跨社区走访时会分成多行。
- 社区表显示在岗人日、人均日走访户数和人均日变动数。请假、长期离岗和未被排到的周末日期
  不进入分母；跨社区走访按当天各社区走访户数分配这 1 个人日。
- 如果页面提示某周没有完成双休日排班，先去“人员管理 → 双休日备勤”补齐该周。补齐以前，
  两个人均日指标显示为 `-`，系统不会用参与人数代替。
- 网格员表和社区表的后端结果包含整段日期的总计；网页使用表头筛选后，表底总计和标题行数
  会立即按当前显示内容重算。后续导出筛选结果时也要按导出内容重新计算，不能使用整表总计。

这一功能新增了三张表，并给网格员资料增加身份证号字段。第一阶段已于 2026-07-28
完成上线，上线时未导入测试走访数据。以后部署相关改动时仍要检查：

1. 确认待部署版本，并完成三个数据库的有效备份。
2. 检查 `backend/init.sql` 和 `backend/database.py` 中的结构一致。
3. 更新后端依赖并重建镜像，再确认新表和字段已经创建。
4. 使用自动化测试验证上传、重叠去重、权限和身份证号遮盖，不向生产库导入测试业务数据。
5. 检查原有业务表数量、登录、同步、日报和日志没有异常。

走访汇总和当前筛选结果的 XLSX 导出已经接入。

## 人员岗位和请假

“基础资料 → 人员管理”用于维护姓名、所属部门、岗位、电话和备注。已有人员升级后默认是“组员”，
避免升级后原来的汇总人员突然消失。

超级管理员可以在“设置 → 系统设置 → 岗位范围”分别配置在线汇总、出租房走访汇总和双休日备勤
涉及的岗位，默认都是“组长、组员”。自购房走访汇总固定使用“自购房”岗位。修改后重新查询或
重新打开排班页面即可看到新结果，不需要重建数据库。

人员请假使用列表中的独立“请假”按钮：

- 临时请假：选择开始和结束日期。
- 长期：不选择日期，恢复工作时点击“恢复正常”。
- 已经结束的日期可以用同一个按钮补录，补录不会改变当前状态。
- 编辑按钮只修改人员资料和岗位，不再修改请假状态。

“人员管理 → 双休日备勤”每周维护一次：

1. 选择要安排的周，通常先点“沿用上周”。
2. 电脑端可以拖动整张人员卡片到周六、周日区域；选错后可以批量“移回待安排”。
3. 手机端不使用拖动，直接点人员卡片上的“周六”“周日”或“双休”，已经安排的人也可以点“双休”移回第一栏。
4. 请假一天的人员只能安排另一天；两天都请假的人员自动免排。
5. 保存请求必须包含当周全部备勤人员；仍在第一栏的人保存后明确记为“周六、周日都休息”，不会继续被当成漏排。
6. 页面显示“已确认全部人员”后代表本周已经完整保存。历史周也可以重新选择并补录。

这项功能新增 `_personnel_attendance_history` 和 `_personnel_weekend_duty`。旧字段继续保留供旧版本
回退；首次上线以前的请假历史无法自动还原，管理人可以按已知记录补录。部署时按兼容数据库
变更规则备份三个数据库和旧程序，并检查两张新表、周排班唯一约束和走访汇总的人日恒等关系。

业务数据中有姓名、但人员管理还没有登记的人会继续显示在汇总中。管理人确认身份后应及时把
该人员加入人员管理并设置正确岗位，之后系统才能按岗位配置准确判断是否纳入统计。

## 版本号与发布

项目使用 SemVer（语义化版本），根目录 `VERSION` 是唯一版本来源：

- 修复已有功能但不增加能力：提升最后一位，例如 `0.1.0` → `0.1.1`。
- 增加兼容的新功能：提升中间一位，例如 `0.1.1` → `0.2.0`。
- 出现不兼容改动：提升第一位。项目仍在早期开发阶段时，主版本可以继续保持 `0`。

前端侧栏和 `/api/health` 都会显示这个版本。先修改 `VERSION` 并完成测试、合并和上线验证，
确认服务器确实运行新版本后，才能创建并推送同名标签，例如 `v0.1.0`。不要提前给未上线的
提交打正式版本标签。

小型且不紧急的界面调整可以先集中在本机，不必每改一处就单独发布。用户明确说“先积攒”时，
停止提交、合并和上线；等用户指定版本后，再把这一批改动放进同一个发布分支，统一完成测试、
Pull Request、合并、部署和版本标签。这样可以减少频繁上线，同时仍保持每个正式版本可追查。

## 在线日报结转与历史回算

从 `0.2.0` 开始，日报会把前期未完成、当天仍在线的任务结转到当天。单日报表显示当天应处理的
总量；区间查询按业务类型和任务主键去重，只保留区间内最后状态。页面不会增加“结转数”列。

从 `0.3.0` 开始，页面在汇总表上方增加数据概览。概览会把任务分成结转、新下发和已有任务变化，
三项互不重复并与当前任务总数相等；“新下发”必须通过相邻快照判断，不能把已有任务的内容变化
误写成新下发。概览只读取现有任务流水和快照，不需要新增数据库字段或执行历史迁移。

从 `0.4.0` 开始，电脑端自动使用表格，手机端自动使用卡片或精简列表；旧的表格/卡片偏好只为
旧前端保留。手机默认使用浮空 Dock，账号可以改回侧边栏，也可以保存自己的分类和页面顺序。
这些设置保存在 `OnlineData._users` 新增的 `mobile_navigation_mode` 和 `mobile_dock_config`
字段中。两个字段由后端启动时兼容性补齐，旧版本会忽略它们。

部署 `0.4.0` 时只需要即时备份 `OnlineData`，并保留旧后端镜像和旧前端目录；不需要因为这两个
账号设置字段额外备份另外两个数据库。上线后要确认 `_users` 已新增两个字段、旧账号默认使用
Dock、手机可以切回侧边栏、普通账号看不到用户管理和运维中心。正式标签仍要等这些检查通过后
再创建。

`0.2.0` 上线时使用受控工具完成了已有历史快照的任务流水回算：先生成临时流水和日报，验证后再
替换正式结果，且没有修改 `OnlineData`、`OnlineDataArchive` 或走访数据。该一次性工具已在
`0.9.5` 移除，历史实现可从 `v0.2.0` 标签追溯。

如果以后出现任务流水缺失，不能把旧工具复制出来直接运行。应根据当前表结构重新编写迁移，先在
测试库跑通，再备份并校验 `daily_report`、确认没有同步任务、审计所有快照证据，最后检查流水唯一性
和每张日报中“未核查＋已核查＋已完成＝数据总数”。

如果需要回退本次计算，先停止后端，再把保留的 `_v010_` 日报表按明确清单换回；这会覆盖新版日报，
属于高风险操作，必须重新确认后执行。

用户已经授权正常代码、前端更新和兼容性数据库变更默认同步到服务器。改动检查通过并合并到 `main`
后，除非用户明确说“不同步”“只改本地”或“先不要部署”，否则继续完成部署。

兼容性数据库变更是指只新增表或可空字段，而且旧版本仍能继续运行。部署前必须通过测试、
备份受影响的数据库并准备回退办法。删除或覆盖数据、恢复备份、删除/重建表和数据卷、不可逆迁移、
轮换凭据等高风险操作仍要单独确认。

每次部署前必须确认：

1. 要部署的是哪个版本。
2. 前端构建和后端检查已经通过。
3. 服务器上的 `.env` 和数据卷不会被覆盖。
4. 已按下面的风险等级准备回退办法。
5. 涉及数据写入或数据库结构时，相关数据库备份不是空的并已通过完整性检查。

部署备份按改动范围处理：

- 纯前端更新：保留上一版 `frontend/dist`，不额外备份数据库。
- 不改数据库结构和数据写入逻辑的后端更新：保留旧 Docker 镜像，不额外备份数据库。
- 修改同步、导入、报表计算等可能写入数据的逻辑：备份受影响的数据库；无法准确判断影响范围时备份三个数据库。
- 修改数据库结构、执行数据迁移或其他高风险操作：完整备份三个数据库，并按高风险规则再次确认。
- 修改 nginx、Compose 或证书配置：只备份相关配置，除非这次改动同时涉及数据库。

平台的每日数据库备份继续保留 7 天。它是日常兜底，但不能替代数据库迁移或高风险操作前的即时备份。

部署后要检查：

1. 健康接口能否访问。
2. 容器是否正常运行。
3. 日志是否有报错。
4. 登录和退出是否正常。
5. 同步、统计和关键数据是否正常。

## 安全入口怎么部署

生产环境由 nginx 统一提供 HTTPS，MySQL 和 Uvicorn 不能直接响应公网请求。
当前端口关系是：

- 滨湖平台使用 nginx 的 HTTPS 443。
- 后端只绑定 `127.0.0.1:37125`，由 nginx 转发。
- MySQL 不发布宿主机端口，只在 Compose 内部使用 `mysql:3306`。

当前服务器的 HTTP 80 还承载另一套独立应用，滨湖平台没有接管或重定向它。不能直接用
仓库里的默认 80 配置覆盖服务器现有站点；更新 nginx 时要保留 ACME 验证目录和原站点。

服务器没有域名时，可以使用支持 IP 地址的短期证书。部署时先用 Certbot 5.4 或更高版本
申请证书，再把实际证书软链接到：

```text
/etc/nginx/ssl/binhu/fullchain.pem
/etc/nginx/ssl/binhu/privkey.pem
```

IP 地址证书只有约 6 天有效期。生产服务器使用 `binhu-certbot-renew.timer` 每天检查两次，
续期成功后执行 `nginx -t` 和重新加载。日常检查：

1. 80 端口的 ACME 验证目录可以访问。
2. `nginx -t` 通过。
3. HTTPS 健康接口和登录都正常。
4. `systemctl is-active binhu-certbot-renew.timer` 返回 `active`。
5. 从外部确认 `443` 可连接，`3306` 和 `37125` 不可连接。

续期镜像和 systemd 模板保存在 `nginx/`。如果本地 Certbot 镜像被清理，可以重新构建：

```bash
docker build -f nginx/Dockerfile.certbot -t binhu-certbot:5.4.0 nginx
```

安装或更新定时器前，先比较服务器现有 unit 文件并备份，不能直接覆盖未知配置。

生产 `.env` 还要设置：

```dotenv
BINHU_SESSION_COOKIE_SECURE=true
BINHU_CORS_ALLOWED_ORIGINS=https://<公网地址>
```

新建空数据库时，临时设置 `BINHU_BOOTSTRAP_ADMIN_USERNAME` 和
`BINHU_BOOTSTRAP_ADMIN_PASSWORD`。首个超级管理员创建并成功登录后立即删除这两个变量。
已有用户的生产数据库不需要设置。

## 数据库备份与恢复

下面是给负责运维的人使用的备份命令。执行前仍要确认服务器、容器和备份目录是否正确：

```bash
docker exec binhu-mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers \
  --default-character-set=utf8mb4 \
  --databases OnlineData OnlineDataArchive daily_report' \
  > "/root/binhu_backup_$(date +%Y%m%d_%H%M%S).sql"
```

`--databases` 不能省略。省略后，`mysqldump` 会把第二、第三个数据库名称误当成表名，三库备份会失败。

备份后至少检查：

- 文件存在。
- 文件大小不是 0。
- 文件开头是正常的 SQL 转储内容。
- 重要操作前，备份已经复制到服务器之外的安全位置。

恢复会覆盖数据，不能自动执行。恢复前必须再次备份当前数据，并得到用户对目标服务器、备份文件和覆盖范围的明确确认。

不要使用 `docker compose down -v` 排错或恢复数据，它会删除数据卷。

## 定时同步怎么使用和排查

超级管理员可以在“设置 → 系统设置”中开启、关闭或修改同步间隔。修改间隔或重新开启后，
倒计时会从保存时刻重新开始。常用间隔可以直接选择，自定义值必须在 5 分钟到 7 天之间。

所有登录用户都可以读取同步状态和下一次倒计时；只有拥有 `sync.trigger` 权限的账号可以点击
“立即同步”，后端会拒绝其他账号发起同步，不能只依赖前端按钮隐藏。同步成功后自动生成日报，
页面不再提供单独的“生成日报”按钮。

同步状态分成四步：等待、同步在线数据、生成报表、完成。页面显示的步骤数来自真实任务进度，
不会再显示估算的假进度。自动同步失败或部分失败后，超级管理员可以从页面上的铃铛查看个人提示。

所有登录用户都能打开消息中心。公告对所有账号可见，但每个人的已读状态分别保存；个人提示只对
接收者可见。超级管理员可以在消息中心发布或删除公告。首次升级会自动发布“出勤历史数据说明”，
因此走访汇总页面不再重复显示同一条长期提示。

如果自动同步没有按时开始，按下面的顺序检查：

1. 查看“系统设置”里是否开启，以及下一次执行时间是否合理。
2. 查看最新同步状态，确认没有另一项任务仍处于等待中或运行中。
3. 查看后端日志中是否有 `[SCHEDULER]` 或 `[SYNC]` 报错。
4. 只读检查 `_sync_schedule` 和最新 `_sync_log`，不要直接修改时间或任务状态。
5. 如果刚发生后端重启，确认中断任务已经被标为失败，并且下一次时间已重新安排。

部署包含定时同步改动的版本后，还要额外检查：

1. `_sync_schedule`、`_notifications`、`_announcements`、`_announcement_reads` 和 `_sync_log` 已经存在。
2. 使用普通管理员、组长和组员验证手动同步权限。
3. 实际等待一轮定时同步，确认来源显示为“自动触发”。
4. 确认分汇总表全部成功后，总汇总表才最后更新。
5. 使用普通账号确认能看到公告、看不到他人的个人提示，并确认不同账号的公告已读状态互不影响。
6. 不要在生产环境故意制造失败；失败通知使用自动化测试验证。
