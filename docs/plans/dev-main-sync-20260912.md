## 重点文件定位

| 目标 | dev 当前状态 | main 当前状态 | 同步注意事项 |
| --- | --- | --- | --- |
| `backend/config.py` | 只允许 `production` / `shadow`，不接受 `development` | 支持 `production`、`staging`、`development` 和兼容 `shadow` | 先做最小兼容同步，保留 dev 其他配置和校验边界 |
| `VERSION` | `0.28.8` | 当前为 `0.28.20` | 版本同步必须单独提交，不能用部署台账伪造版本 |
| `frontend/src/utils/queryGrid.ts` | dev 事件流查询网格核心文件（若存在） | 以 main 文件集合为准，不作为环境支持同步目标 | 保持 dev 版本，不覆盖 |
| 事件流后端（Kafka/Flink/Redis/outbox 等） | dev 独有/改动集中在上述核心文件列表 | main 侧可能有不同实现 | 后续逐文件评估接口兼容性 |
| `deploy/environments/*` | dev 当前缺失或版本不同 | main 提供环境制品、镜像和更新工具链 | 第三步按依赖分批移植，先做静态验证 |

## 分步同步边界

1. **环境配置兼容**：仅同步 `backend/config.py` 对 `development` 的支持及直接必需的配置校验，不搬运无关业务改动。
2. **版本管理**：单独同步根目录 `VERSION` 管理规则和目标版本，先确认 dev 的发布策略，再提交版本变更。
3. **部署工具链**：逐步引入 `artifact`、`image`、`update` 及其运行时依赖，验证只操作 `binhu-development` 和 `Dev_*` 八库。
4. **每步验证**：每个独立提交都运行 dev 完整 CI；任何失败都停在当前步骤，不把后续 main 改动一起带入。
5. **PR #613 部署**：前三步完成并验证后，再重新生成与当前 dev 基线兼容的制品；不直接部署原始 `566a662d`，不降级到 `0.28.8`。

## 风险与待确认项

- dev 与 main 共同祖先较早，不能直接 merge 或 rebase；同名文件差异必须逐项审查。
- `backend/config.py` 的环境枚举是启动硬门槛；未同步前，`APP_ENVIRONMENT=development` 会导致 `566a662d` 后端启动失败。
- `deploy/environments` 工具链包含服务器路径、Docker 项目和数据库身份检查，移植前必须确认代码与服务器证据一致。
- `VERSION` 不能只改台账；制品中的版本、`APP_VERSION`、Bootstrap 和 manifest 必须由同一提交生成。
- 真实 MySQL/Dev 服务器只做部署前后受控验证；本报告本身没有连接数据库或修改服务器。
