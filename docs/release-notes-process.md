# 发布级更新日志流程

## 原则

Pull Request 只记录可复核的技术事实：改了什么、为什么改、如何验收、风险和未完成事项。PR 不负责生成最终面向用户的版本更新日志。

一个版本可能合并多个 PR。准备发布时，由 Codex 一次性读取该版本发布范围内的全部已合并 PR，去重并按业务主题归纳成一份发布级日志。这样不会因为十几个 PR 各自写摘要而在 Release 中重复、割裂或顺序混乱。

## 发布时的操作顺序

1. 确认版本号、上一个版本标签和本次准备纳入的已合并 PR。
2. Codex 阅读这些 PR 的标题、正文、测试结果、风险和实际 diff，排除内部实现细节、重复描述和敏感数据。
3. Codex 在仓库中创建：

   ```text
   release-notes/v<version>.md
   ```

4. 日志按用户可理解的主题组织，每个主题下面列出 1～5 条结果导向的说明。例如：

   ```markdown
   1. 任务编辑与照片回写可靠性
   - 大量任务编辑改为分块处理，页面只加载当前可见编辑器。
   - 照片写回失败与重试相互隔离，减少重复扫描和无意义告警。

   2. 外部数据获取
   - 外部数据获取改为可查看进度的后台任务，并保留失败诊断。
   ```

5. 现有 Desktop release 工作流读取该文件，生成：

   - GitHub Release 使用的 `release-notes.md`；
   - 随桌面前端打包的 `release-notes.json`；
   - 升级后首次进入平台时显示的“版本已更新”弹窗内容。

6. Release 正文显示主题化更新内容，末尾保留 PR 编号和技术摘要作为追溯信息，但不把 PR 原文直接拼接成用户更新日志。

## 内容边界

- 只描述用户能感知的功能、修复、性能和兼容性变化。
- 不写身份证号、手机号、地址、Cookie、密码、外部系统原始返回正文或完整内部日志。
- 不把未合并、未验证或明确标记为暂时无法解决的事项写成“已支持”。
- 高风险外部写入、数据库迁移和已知限制应在 Release 的技术说明或验收说明中简洁注明。

## 兜底规则

如果发布时没有 `release-notes/v<version>.md`，工作流仍会生成安全的 PR 摘要，保证发布不会因为日志文件缺失而中断。该兜底只用于兼容旧版本；正常发布必须由 Codex 先生成发布级日志。

## 验收重点

- GitHub Release 的正文按业务主题展示，而不是十几个 PR 的原文堆叠。
- `release-notes.json` 存在 `sections`，并且主题和条目与 Release 一致。
- 客户端升级后第一次登录进入业务页面时，弹窗显示同一份主题化日志。
- 同版本重启、首次安装、网页端和离线模式不重复弹出。
- 技术追溯区仍能找到本版本实际合并的 PR 编号。
