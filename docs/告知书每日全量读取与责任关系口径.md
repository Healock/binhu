# 告知书每日全量读取与责任关系口径

## 获取方式

告知书来源目前不能依靠开始、结束时间稳定增量读取，因此服务器采用每日全量读取：

- 上游只执行只读分页查询；
- 每个业务日期最多自动创建一次任务；
- 读取失败、范围不符或结构异常时，不改变已有房屋档案；
- 完整读取成功后，按稳定来源标识区分新增、变化和未变化记录；
- 未变化记录只刷新最近见到时间，变化记录更新原挂载项，不重复创建；
- 确认完整快照时在一个本地事务中失效旧当前项、更新本次正常项、将旧待处理问题标记为 `superseded`；历史来源正文和记录保留，不物理删除；
- 同社区同标准化地址、业务内容完全一致的记录合并为一个当前代表项；
- 同地址不同内容只有所有记录均提供可解析的 `updateTime`、`updatedAt`、`updated_at` 或 `update_time`，且最新时间对应唯一内容时才采用最新版本。不把 ID 大小、物理行号或 `signTime` 当成更新时间；缺失、无效或并列最新内容冲突时继续核对；
- 外部来源中的真实当前冲突和无法匹配出租房的记录继续进入问题核查；未签订本身不是导入问题。

服务器配置：

- `CERTIFICATE_SOURCE_DAILY_ENABLED`：是否启用每日读取，默认关闭；
- `CERTIFICATE_SOURCE_DAILY_TIME`：按系统配置时区执行的时间，格式为 `HH:MM`；
- 来源地址和认证信息继续沿用服务器侧来源配置，不能进入前端或普通日志。

手动“读取告知书”入口继续保留。手动读取先生成预览，再由有权限的人员确认挂载；自动读取只有在完成全部分页和现有校验后，才自动应用可安全挂载的正常记录。

只有服务端全量读取创建的批次带 `certificate_full_snapshot=1`。用户提交的原始行预览及升级前的旧预览不能确认覆盖全量来源，必须重新读取。每次完整观察创建新批次，允许 A → B → A 的上游状态变化；重复确认同一批次幂等。确认复用 MySQL 命名锁，较旧批次在新快照已应用后返回 409。读取失败或空结果不创建新快照，不清空当前记录。来源消失的告知书使用既有 `source_missing_since` 标记历史，查询、详情及状态比较只统计当前项。

## 档案状态口径

房屋档案列表和详情统一显示以下责任书状态：

- **正常签署**：出租房存在一份告知书，实际出租人明确，签署状态为已签；
- **无需上传告知书**：至少完成过一次成功的告知书全量读取后，出租房在来源中仍没有对应房屋记录，且不存在待核对的重复、冲突或地址匹配问题；
- **未签订**：告知书全量来源中已经存在该房屋记录，尚未签署且无签署类型；即使实际出租人暂为空，也不将未签订本身归为问题；
- **已签署，需修改实际出租人**：来源已有签署类型，但签署状态提示实际出租人需要修正；
- **实际出租人未确定**：存在告知书，但实际出租人为空；
- **告知书来源待核对**：来源存在重复、内容冲突或地址匹配问题，不能直接认定当前责任关系；
- **非出租房屋**：当前住房类型不是个人出租或单位出租，不纳入责任书签署统计。

同时显示房东与实际出租人的关系：一致、不一致或未确定。

“无需上传”不能只根据挂载结果为空判断。来源重复、内容冲突或地址未匹配会进入问题数据核查，在问题解决前继续显示“告知书来源待核对”，不得误归为无需上传。

## 身份分类边界

历史工作簿中的“二房东”“管家”名单适合辅助分析，但名单不完整，不能直接作为正式档案依据。平台只在当前房屋已经存在正式人员关系，且角色明确标注为二房东或管家时显示对应身份；其余情况显示“未确认”。

后续需要业务确认：

1. 二房东、管家的权威数据来源和维护责任人；
2. 一人同时管理多套房时，是否需要专门的责任主体档案与汇总页面；
3. 若上游返回同址不同内容但没有更新时间，需确认可稳定识别最新版本的协议字段；目前保留真实冲突，不猜测。

## 验证与回退

本修补新增一个兼容标记列，不在启动时清理历史或制造新快照。上线前备份 `RegistryData`；固定部署的备份选项不支持单独 RegistryData 时使用 `all`。上线后重新完整读取并确认，历史问题才会收敛。真实 MySQL、驱动及全民防协议字段须在授权验收环境核对，合成游标测试不能替代。回退旧程序会重新统计历史项，因此回退前应评估旧页面问题数量回升；不删除历史或自动恢复数据库。
