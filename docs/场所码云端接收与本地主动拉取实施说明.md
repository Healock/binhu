# 场所码云端接收与本地主动拉取实施说明

日期：2026-09-01

状态：代码验证与云端基础设施候选准备中，不再是“待实施”。真实二维码、平台同步和主动拉取仍未启用。

## 边界

- 滨湖平台主业务服务器是“本地服务器”，`RegistryData` 是场所与登记数据唯一权威来源。
- “云端服务器”只接收公开表单、保存密文和维护交付租约，不持有滨湖数据库凭据；真实地址仅保存在私密运维记录中。
- 滨湖服务器只发起出站 HTTPS；云端不能反向连接滨湖服务器。
- 本次代码默认关闭云端配置同步和主动拉取，保留本地匿名入口。没有人工批准不得切换生产开关。
- 云服务器当前运行的是隔离候选环境，只用于虚构数据和协议验证，不代表真实场所码业务已经上线。
- 正式公开入口复用现有公网 IP HTTPS，不使用独立场所码域名。
- 照片只写入云服务器私有密文目录，不使用对象存储，也不映射为静态资源。
- 旧二维码不自动跳转；正式切换时统一换码重印，旧匿名入口返回 `410`。

## 云端运行方式

- 云端使用宿主机 Nginx、Docker Receiver 和独立 Docker MySQL 8.0.46。
- Docker MySQL 不声明宿主机端口，只加入 `venue_private` 内部网络；现有宝塔 MySQL 不属于场所码服务，不能复用其数据库或凭据。
- Receiver 与 MySQL 只加入 `venue_private` 内部网络，Receiver 通过 Docker DNS 访问 `mysql:3306`，两者都不映射宿主机端口。
- 独立 Ingress 容器不挂载密钥或数据库配置，只把宿主机 `127.0.0.1:48727` 固定转发到 Receiver，以兼容 Docker internal 网络不建立宿主机端口网关的行为。
- Nginx 继续复用现有 HTTPS 更新站点，保留 `/updates/`，新增 `/venue/`、`/api/public/` 和受 mTLS 保护的 `/api/internal/`。
- 主业务 Worker 通过受保护的 `POST /api/internal/submissions/wait` 建立最长 20 秒的出站长轮询；收到信号后主动拉取到队列为空，并每 5 分钟执行一次兜底拉取。
- `bt_proxy.conf` 与现有 80 端口站点重复，正式切换时只将重复文件改为非 `.conf` 后缀，不改变商城、宝塔代理和 ACME 行为。

## 更新服务器磁盘整理记录

2026-09-01 已把更新网关保留数量从 5 改为 3，并通过受发布锁保护的 root 清理工具移除旧归档、旧 history 独占资产和遗留上传包。服务器仅保留 `0.27.16`、`0.28.0`、`0.28.1` 三组 history；当前 `0.28.1` 清单和包未重写。清理前后均完成校验文件、HTTPS 下载和 Range 请求核对，可用空间由约 4.9 GiB 提升到约 26 GiB。完整历史继续由 GitHub Release 保存。

云端候选环境启动前还有一项外部前置条件：必须从公网确认现有 MySQL 的 TCP 3306 已被云厂商安全组阻断。不得为完成本项目而擅自修改未知业务使用的 MySQL 监听地址或启用未盘点的主机防火墙规则。

## 密钥与证书

滨湖服务器保存 RSA-3072 解密私钥、Ed25519 请求签名私钥及 mTLS 客户端私钥。云端只保存 RSA 公钥、滨湖请求验签公钥和自身响应签名私钥。轮换时滨湖保留当前和上一把 RSA 私钥，云端通过 `key_id` 选择公钥。

同一公网 IP 的 TLS 证书继续由既有 `binhu-ip-cert-renew.timer` 每日两次检查。场所码部署不得安装第二套证书续签任务。内部接口除 HTTPS 外，还需要 mTLS 和 Ed25519 请求签名；任一验证失败都拒绝请求。

## 数据生命周期

- 未交付密文最长保留 168 小时。
- `accepted` 后默认 24 小时内删除云端正文和照片。
- `rejected`、`uncertain` 和过期事件仅保留安全原因码，不记录表单正文、照片名或完整令牌。
- 云端数据库与照片备份最长保留 7 天，备份同样按密文处理。

## 影子验收

1. 仅部署云端服务和密钥，不启用真实二维码。
2. 使用虚构场所、虚构身份资料和测试照片验证创建、扫码、加密、租赁、解密、落库、确认和清理。
3. 验证错误证书、过期签名、随机数重放、未知 `key_id`、损坏照片和超限请求均被拒绝。
4. 模拟确认响应丢失，确认重复投递只命中 `cloud_submission_id` 唯一键，不重复登记。
5. 观察 Nginx、应用和数据库审计，确认不含完整令牌或个人信息。
6. 使用不支持 `crypto.randomUUID()` 的旧 WebView 打开登记页，确认备用 UUID 仍能通过提交接口校验。

## 正式切换

1. 备份 `RegistryData`，记录备份文件、校验值和恢复命令，暂停场所编辑。
2. 先运行 `venue_cloud_migration.py` 默认审计模式，核对启用场所数和既有待轮换数。
3. 取得单独人工批准后，使用 `--apply --backup-reference --expected-active-count --output` 生成待确认的新令牌。输出文件权限为 `0600`，属于敏感材料。
4. 先开启云端配置同步，等待全部场所的 `cloud_synced_revision` 确认；未确认场所不得查看或打印新二维码。
5. 开启主动拉取，用测试登记确认本地只产生一条记录。
6. 导出、打印并现场替换新二维码，完成后关闭本地匿名入口，使旧入口统一返回 `410`。
7. 连续观察至少 72 小时，核对接收、确认、积压、租约超时、拒绝、`uncertain` 和孤儿照片。

## 回滚

云端镜像失败时回到上一镜像，数据库不自动恢复。滨湖 Worker 失败时关闭主动拉取，云端继续排队；不得因此重新开放公网对滨湖主服务器的匿名写入。场所同步失败时保留旧令牌，只有云端确认后才提升新令牌。已进入 `uncertain` 的记录停止自动重放，由运维人员按 `cloud_submission_id` 对账。

真实 MySQL 8 已在本机独立数据目录和端口使用虚构数据完成闭环验证。Docker、Nginx、mTLS、证书续签和外网手机扫码仍必须在云服务器隔离候选环境或获批维护窗口内验收，不能用生产数据代替开发测试。
