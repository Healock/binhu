# 场所码云端独立接收与本地主动拉取设计

> 文档状态：待评审、待实施
> 编写日期：2026-08-29
> 目标读者：云服务器副开发、滨湖平台开发、部署运维和项目管理人

## 一、结论

场所码公开登记入口建议从滨湖平台主物理服务器拆出，部署为独立的云端公网接收服务。

目标链路固定为：

```text
扫码用户
  -> 云端场所码服务
  -> 云端短期加密待接收区
  <- 滨湖平台物理服务器主动拉取
  -> 滨湖平台本地业务库正式入库
  -> 滨湖平台确认接收
  -> 云端按保留策略清理敏感正文和照片
```

这不是简单的反向代理。云端不得把匿名请求继续转发到主物理服务器，也不得直接连接滨湖平台数据库。主物理服务器只允许通过出站 HTTPS 主动访问云端内部接口。

滨湖平台本地数据库继续是场所、登记记录和照片的唯一正式业务数据源。云端数据只用于公网接收、短期排队和可靠交付，不承担业务查询、统计、导出或长期档案职责。

## 二、背景与目标

当前场所码由滨湖平台同时承担：

- 场所目录和二维码管理；
- 匿名扫码页面；
- 姓名、身份证号、手机号、地址和照片接收；
- 正式数据保存、查看和导出。

匿名页面和文件上传是公网暴露面中风险较高的部分。将其拆到云端后，需要实现以下目标：

1. 主物理服务器不直接接收匿名用户请求和照片上传。
2. 云端受攻击、流量突增或磁盘压力异常时，不影响滨湖平台主体功能。
3. 物理服务器短时离线时，云端可以继续接收并等待恢复后交付。
4. 云端无法直接访问滨湖平台数据库、内部网络或其他业务接口。
5. 同一条登记无论网络重试多少次，在本地最多正式入库一次。
6. 场所新增、停用、移除和换码在云端与本地之间可追踪、可重试、可对账。
7. 云端不长期保存敏感正文，不在日志、指标和普通审计中记录敏感内容。

## 三、不采用的方案

### 3.1 云端反向代理到物理服务器

```text
手机 -> 云端 Nginx -> 物理服务器公开接口
```

不采用。该方案只隐藏物理服务器地址，请求处理、照片流量和攻击压力仍会进入物理服务器。

### 3.2 云端只托管页面，浏览器直接提交到物理服务器

不采用。物理服务器仍需暴露匿名写入接口，还会增加跨域、证书和浏览器安全策略复杂度。

### 3.3 云端直接写滨湖平台数据库

禁止。云端不得持有滨湖平台数据库账号，不得通过公网、VPN或 SSH 隧道访问正式数据库。

### 3.4 云端拥有完整内部网络访问权限

禁止。即使使用 VPN，也只能提供经过批准的单一服务访问能力，不能把云端加入内部可信网段。本方案默认不需要云端主动连接内部网络。

## 四、信任边界

### 4.1 云端可做的事情

- 根据二维码令牌判断场所是否允许展示登记页；
- 展示场所名称和登记表单；
- 校验字段格式、照片类型和大小；
- 执行限流、防重复提交和基础攻击拦截；
- 将正文和照片加密后写入短期待接收区；
- 向通过服务身份认证的滨湖平台返回待接收密文；
- 接收幂等的成功确认、拒绝确认和场所状态同步；
- 输出不含业务正文的运行指标和安全审计。

### 4.2 云端不能做的事情

- 查询、修改或删除滨湖平台正式业务数据；
- 读取流口指令、人员档案、房屋档案或其他业务库；
- 提供登记正文查询、导出或运营后台；
- 将姓名、身份证号、手机号、地址或照片写入普通日志；
- 使用滨湖平台数据库密码、应用 Fernet 密钥或内部管理员会话；
- 反向调用滨湖平台匿名接口完成正式入库。

### 4.3 滨湖平台职责

- 继续维护场所目录、权限、操作审计和二维码管理入口；
- 生成高强度二维码令牌；
- 通过本地事务 Outbox 将场所变更可靠同步到云端；
- 主动拉取云端待接收数据；
- 在本地重新校验、解密并正式入库；
- 保存登记记录和照片，继续执行现有90天业务保留策略；
- 向云端发送幂等确认，并在运维中心展示积压和失败状态。

## 五、总体架构

```text
                            公网
                             |
                  +----------v-----------+
                  | CDN/WAF 或云防火墙   |
                  +----------+-----------+
                             |
                  +----------v-----------+
                  | 云端场所码应用       |
                  | - 公开登记页面       |
                  | - 公开提交 API       |
                  | - 内部交付 API       |
                  +----+------------+----+
                       |            |
              +--------v--+    +----v----------------+
              | 云端数据库 |    | 私有照片对象存储    |
              | 仅密文/状态 |    | 仅密文、禁止公开读  |
              +-----------+    +---------------------+

                             ^
                             | 出站 HTTPS
                             | 双向证书或服务签名
                             |
                  +----------+-----------+
                  | 滨湖平台物理服务器   |
                  | - 场所同步 Outbox    |
                  | - 主动拉取 Worker    |
                  | - 解密与本地事务入库 |
                  +----------+-----------+
                             |
                  +----------v-----------+
                  | RegistryData/照片目录|
                  | 唯一正式业务数据源   |
                  +----------------------+
```

云端安全组只开放 HTTPS `443`。数据库、对象存储管理端口和内部调试端口不得向公网开放。

## 六、域名与二维码

建议使用独立域名，例如：

```text
https://venue.example.com
```

滨湖平台生产配置：

```env
BINHU_PUBLIC_WEB_BASE_URL=https://venue.example.com
```

二维码内容保持：

```text
https://venue.example.com/venue/{token}
```

域名必须满足：

- 手机所在网络能够访问；
- 使用有效 HTTPS 证书；
- 不包含 `/api` 或 `/venue` 后缀；
- 不指向容器名、回环地址或仅内部可访问地址；
- 云端页面、公开 API 和照片上传保持同源，避免不必要的跨域开放。

## 七、场所与二维码同步

### 7.1 令牌归属

首版继续由滨湖平台生成随机高熵二维码令牌，减少现有场所管理逻辑改动。

滨湖平台只在同步场所配置时通过加密传输把令牌发送给云端。云端收到后立即计算独立 HMAC，只保存 HMAC，不保存令牌明文。二维码令牌本身会印在二维码中，因此不能将其视为用户身份凭据，但仍不得进入普通日志。

### 7.2 同步字段

云端场所表只需要：

- `local_venue_id`：滨湖平台场所 ID；
- `display_name`：公开页面显示名称；
- `status`：`active` 或 `inactive`；
- `token_hmac`；
- `token_version`：每次换码递增；
- `config_revision`：场所配置版本；
- `updated_at`；
- `last_request_id`：幂等请求标识。

默认不向云端同步社区、内部责任人、后台创建人和其他非公开信息。确需在登记页显示地址时，再单独评审是否增加脱敏后的公开地址。

### 7.3 本地同步状态

滨湖平台不得在本地事务提交后直接假定云端同步成功。建议增加以下状态：

- `pending_activation`：场所已创建，但云端尚未确认，二维码不可下发；
- `active`：云端已经确认启用；
- `pending_update`：场所名称等配置待同步；
- `pending_disable`：本地已提出停用，但云端尚未确认；
- `inactive`：云端已经确认停用；
- `sync_failed`：同步失败，等待后台重试或人工处理。

### 7.4 启停和换码规则

- 新增场所：先本地事务创建场所和 Outbox，再由 Worker 同步云端；云端确认前不显示可用二维码。
- 编辑场所：本地保存后进入待同步，云端按更高 `config_revision` 幂等覆盖。
- 停用或移除：必须持久化高优先级 Outbox 并立即尝试云端停用；云端未确认时页面必须明确显示“云端停用待确认”，不能显示假成功。
- 换码：新令牌只有在云端确认后才成为有效二维码；旧令牌在同一次云端事务中失效。
- 定期全量对账：滨湖平台每天向云端发送一次签名的有效场所摘要，发现状态或版本漂移时自动修正并告警。

如果项目要求“物理服务器长期不可达时所有二维码自动失效”，可以增加云端场所租约：滨湖平台定期续租，超过约定宽限期未续租则云端统一暂停登记。该策略会影响离线可用性，首版是否启用需要项目管理人确认。

## 八、公开登记流程

### 8.1 打开页面

1. 用户扫描 `/venue/{token}`。
2. 云端对令牌计算 HMAC，查找唯一且启用的场所。
3. 云端生成短时、一次性 `form_token`，数据库只保存摘要。
4. 页面只返回场所名称、允许上传类型、文件大小上限和表单令牌。
5. 无效、停用或已轮换的令牌统一返回安全错误，不泄露场所是否曾经存在。

### 8.2 提交数据

公开提交使用一次 multipart 请求，字段保持现有口径：

- 姓名；
- 公民身份号码；
- 手机号；
- 地址；
- 照片；
- `form_token`；
- 浏览器生成的 `submission_id`。

云端必须执行：

- 原子消费一次性表单令牌；
- 校验姓名、身份证、手机号和地址格式；
- 同时校验照片扩展名、声明 MIME、文件头和大小；
- 限制单 IP、单设备摘要、单场所和全局请求频率；
- 使用随机对象键保存照片，不使用用户文件名；
- 正文和照片加密成功后，才返回“提交成功”；
- 数据库写入和对象存储之间出现不确定状态时进入隔离清理流程，不向用户重复承诺成功。

公开接口不得返回数据库编号、对象存储路径、内部错误堆栈或加密元数据。

## 九、云端加密与密钥

### 9.1 基本原则

云端不得复用滨湖平台现有 Fernet 密钥。建议使用非对称密钥加信封加密：

1. 滨湖平台生成接收专用密钥对；
2. 私钥只保存在物理服务器安全配置中；
3. 云端只保存公钥；
4. 每条提交生成随机数据密钥；
5. 正文和照片分别使用认证加密算法加密；
6. 数据密钥使用滨湖平台公钥封装；
7. 云端保存 `key_id`、算法、随机数、密文、完整性标签和密文摘要；
8. 只有物理服务器能够解密。

云端仍会在请求处理内存中短暂接触明文以完成格式和文件检查，因此云端主机仍属于敏感系统，不能把“数据库是密文”理解为无需加固。

### 9.2 密钥轮换

- 每把公钥拥有稳定 `key_id`；
- 云端允许同时使用当前公钥和上一把公钥；
- 每条提交记录其 `key_id`；
- 必须等旧密钥对应的未确认提交全部完成后，才能从物理服务器移除旧私钥；
- 密钥、证书和签名秘密不得写入仓库、镜像、日志或 PR。

## 十、物理服务器主动拉取

### 10.1 拉取模型

滨湖平台运行独立后台 Worker，建议默认每30秒拉取一次，也支持前一轮完成后短暂等待再继续。

拉取请求包含：

- 客户端服务身份；
- `request_id`；
- 单批上限，建议首版50条；
- Worker 实例 ID；
- 支持的加密版本；
- 可选的上次游标。

云端使用租约返回待处理记录：

- `lease_id`；
- `lease_expires_at`；
- `submission_id`；
- `local_venue_id`；
- 加密正文；
- 加密照片对象或受限下载地址；
- 密文摘要、大小和算法版本；
- 云端接收时间。

租约到期前同一提交不再分配给其他 Worker。租约到期但未确认时可以重新投递。

### 10.2 本地入库事务

物理服务器收到提交后必须：

1. 校验服务响应签名、租约、密文摘要和文件大小；
2. 使用对应私钥解密；
3. 再次执行身份证、手机号、地址和照片校验；
4. 确认场所在本地仍存在且允许接收；
5. 在本地事务中写入登记记录、照片元数据和 `cloud_submission_id`；
6. 使用唯一约束保证同一 `submission_id` 最多入库一次；
7. 照片正式落盘成功后提交事务；
8. 事务完成后再向云端发送确认。

如果本地事务已经成功但确认请求丢失，云端会再次投递。滨湖平台通过 `cloud_submission_id` 查到既有记录后直接重新确认，不重复创建登记。

### 10.3 确认结果

确认状态建议固定为：

- `accepted`：已经正式入库；
- `rejected`：永久无法入库，例如密文损坏、场所不存在或字段严重无效；
- `retry_later`：临时故障，不改变云端待交付状态；
- `uncertain`：本地无法确认事务结果，停止自动重放并进入人工对账。

拒绝原因只能使用安全原因码，例如 `venue_inactive`、`payload_invalid`、`photo_invalid`、`key_unknown`，不得把敏感正文返回云端日志。

## 十一、建议接口合同

以下路径是设计建议，云端副开发可在正式 OpenAPI 中细化，但不得改变数据流方向。

### 11.1 公开接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/venue/{token}` | 展示同源登记页面 |
| `GET` | `/api/public/venues/{token}` | 获取公开场所名称和一次性表单令牌 |
| `POST` | `/api/public/submissions` | 一次性提交文字和照片 |

### 11.2 仅滨湖平台调用的内部接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `PUT` | `/api/internal/venues/{local_venue_id}` | 幂等新增、更新、启停或换码 |
| `POST` | `/api/internal/venues/reconcile` | 提交有效场所摘要并对账 |
| `POST` | `/api/internal/submissions/pull` | 租约式拉取待接收提交 |
| `POST` | `/api/internal/submissions/ack` | 批量确认接收、拒绝或不确定 |
| `POST` | `/api/internal/submissions/renew-lease` | 长处理时续租，可选 |
| `GET` | `/api/internal/status` | 返回安全健康状态、队列数量和最老等待时间 |

内部接口必须：

- 使用双向 TLS，或使用独立客户端证书加请求体签名；
- 只接受固定滨湖平台服务身份；
- 每个写请求包含幂等 `request_id`；
- 校验请求时间和随机数，防止重放；
- 设置较小超时和有限重试；
- 不通过 Cookie 或用户登录态认证；
- 不在响应中返回与本次操作无关的数据。

## 十二、云端数据模型建议

### 12.1 `venues`

- `local_venue_id`，唯一；
- `display_name`；
- `status`；
- `token_hmac`，唯一；
- `token_version`；
- `config_revision`；
- `created_at`、`updated_at`；
- `last_request_id`。

### 12.2 `form_tokens`

- `token_hmac`，唯一；
- `local_venue_id`；
- `expires_at`；
- `consumed_at`；
- `created_at`。

### 12.3 `submissions`

- `submission_id`，全局唯一；
- `local_venue_id`；
- `state`：`queued/leased/accepted/rejected/uncertain/expired`；
- `encrypted_payload`；
- `wrapped_data_key`；
- `key_id`、`algorithm_version`；
- `ciphertext_sha256`；
- `photo_object_key`、`photo_ciphertext_sha256`、`photo_size`；
- `lease_id`、`lease_owner`、`lease_expires_at`；
- `attempt_count`；
- `safe_reason_code`；
- `received_at`、`acknowledged_at`、`expires_at`。

### 12.4 `delivery_events`

只记录：

- `submission_id`；
- 安全事件类型；
- Worker 实例摘要；
- HTTP 结果分类；
- 安全原因码；
- 时间和耗时。

不得记录解密后的姓名、身份证号、手机号、地址、照片、完整二维码令牌、客户端证书正文或请求体。

## 十三、照片处理

- 对象存储桶必须是私有桶；
- 禁止设置公共读或永久公开 URL；
- 对象键使用随机值，不包含姓名、身份证或原文件名；
- 上传大小上限与滨湖平台现有 `VENUE_PHOTO_MAX_BYTES` 保持一致；
- 只允许经过确认的 JPEG、PNG、WebP；
- 同时检查文件头、MIME、扩展名和大小；
- 可以增加病毒扫描或图片重新编码，但失败时不得把未确认文件交付给滨湖平台；
- 拉取照片使用短时、一次性受限下载能力，或直接通过内部接口流式返回；
- 云端删除数据库记录时必须同步删除对应对象，反向也要有孤儿对象清理任务；
- 不使用 CDN 公开分发登记照片。

## 十四、保留与清理策略

建议首版默认值，最终需要项目管理人确认：

- 已成功确认的云端正文和照片：24小时后删除；
- 尚未被物理服务器接收的数据：最多保留7天；
- 永久拒绝或不确定数据：最多保留7天并持续告警；
- 不含敏感正文的安全审计和数量指标：保留90天；
- 本地正式登记记录和照片：继续执行现有90天规则。

对象存储生命周期只能作为兜底，业务清理任务仍需按状态删除数据库和对象。物理服务器离线超过保留上限会造成待接收数据过期，因此必须对队列最老等待时间设置告警。

## 十五、故障与恢复

### 15.1 云端不可用

- 场所码页面暂时不可访问；
- 滨湖平台主体、任务核查和档案功能不受影响；
- 本地场所同步 Outbox 保留并退避重试；
- 管理页面显示云端不可用和待同步数量。

### 15.2 物理服务器不可用

- 云端继续接收并保存加密提交；
- 队列等待，不把失败展示为已正式入库；
- 超过告警阈值通知运维；
- 物理服务器恢复后从未确认记录继续拉取。

### 15.3 拉取成功但本地确认丢失

- 云端租约到期后重新投递；
- 本地唯一 `cloud_submission_id` 防止重复入库；
- 本地重新发送 `accepted` 确认。

### 15.4 照片保存成功但数据库失败

- 本地事务回滚；
- 临时照片进入本地孤儿文件清理；
- 不向云端确认成功；
- 下次重新拉取并处理。

### 15.5 场所停用同步失败

- 本地显示“云端停用待确认”；
- 高优先级持续重试并告警；
- 不允许界面宣称二维码已经失效；
- 云端运维保留独立的全局紧急停用开关。

### 15.6 云端数据库或对象存储恢复

- 恢复后必须按 `submission_id`、对象摘要和状态进行一致性扫描；
- 已确认记录不得重新变为可交付；
- 无数据库引用的对象进入隔离清理；
- 数据库有照片引用但对象缺失的记录进入 `uncertain`，不得返回假成功。

## 十六、监控与告警

云端和滨湖平台均应展示安全聚合指标：

- 最近一次场所配置同步时间；
- 场所同步待处理数和失败数；
- 当前待接收提交数；
- 最老待接收提交等待时长；
- 每小时接收数、确认数、拒绝数和过期数；
- 拉取成功率和确认成功率；
- 租约超时数量；
- 照片总容量和孤儿对象数；
- 401/403、限流、无效令牌和无效文件数量；
- 当前使用的公钥 `key_id` 和未知密钥错误数。

建议告警阈值：

- 连续5分钟拉取失败；
- 最老待接收数据超过15分钟；
- 待接收数量持续增长；
- 大量表单令牌失败或单来源请求突增；
- 云端磁盘或对象存储配额接近上限；
- 场所停用、换码连续失败；
- 出现 `uncertain` 数据。

指标标签中不得使用姓名、身份证号、手机号、地址、照片名或完整令牌。

## 十七、旧二维码迁移

修改 `BINHU_PUBLIC_WEB_BASE_URL` 只影响新生成或重新查看的二维码，已经打印的旧二维码仍指向原平台地址，因此必须单独处理。

推荐迁移步骤：

1. 在维护窗口中读取本地仍启用场所的现有加密令牌；
2. 通过受认证内部接口一次性同步到云端，过程不输出令牌；
3. 云端只保存令牌 HMAC；
4. 对每个场所执行只读校验，确认旧令牌在云端能够解析到同一场所；
5. 原平台 `/venue/{token}` 暂时只返回 `302` 到云端同一路径，不再展示表单或接收数据；
6. 观察迁移期访问量和错误率；
7. 确认旧码基本迁移完成后，再决定是否移除重定向；
8. 无法安全迁移的场所执行换码并重新打印。

重定向只能保留路径中的令牌，不得在 URL 增加姓名、身份证或其他业务信息。

## 十八、实施分工

### 18.1 云服务器副开发

- 建立独立场所码云端服务和部署仓库或独立服务目录；
- 实现公开页面、公开提交 API 和内部交付 API；
- 实现云端数据库、私有对象存储、加密、租约和清理任务；
- 配置域名、HTTPS、云防火墙、限流和监控；
- 提供版本化 OpenAPI、脱敏 fixture 和错误码清单；
- 提供部署、备份、恢复和密钥轮换文档；
- 不接触滨湖平台正式数据库凭据。

### 18.2 滨湖平台开发

- 增加场所配置同步 Outbox 和状态展示；
- 增加主动拉取 Worker、本地唯一键和确认机制；
- 增加云端公钥/私钥管理和解密；
- 保持现有场所权限、登记查询、照片查看、导出和审计；
- 将公开表单写入路径从本地后端移除或固定返回迁移提示；
- 将云端积压、同步失败和最近成功时间接入运维中心。

### 18.3 双方共同完成

- 固定字段、加密包和错误码合同；
- 交换测试证书和测试公钥；
- 使用虚构数据完成端到端联调；
- 验证重复投递、确认丢失、停用延迟和照片异常；
- 完成旧令牌迁移和回退演练；
- 上线前确认域名、证书、保留期和责任边界。

## 十九、分阶段交付

### 阶段一：合同和云端最小闭环

- 完成 OpenAPI、数据模型和错误码；
- 云端支持虚构场所、公开提交、加密排队、拉取和确认；
- 使用命令行测试客户端验证，不连接生产滨湖平台。

### 阶段二：滨湖平台接入

- 增加场所同步 Outbox；
- 增加主动拉取 Worker；
- 使用测试环境虚构数据完成本地入库；
- 运维中心显示云端状态和积压。

### 阶段三：影子验证

- 使用受控测试二维码；
- 云端接收并由滨湖平台拉取；
- 对照数量、照片摘要和入库状态；
- 不迁移真实旧二维码。

### 阶段四：旧二维码迁移

- 备份 RegistryData 和现有令牌配置；
- 同步启用场所和旧令牌；
- 启用原路径到云端的临时重定向；
- 将新二维码基地址切换到云端域名。

### 阶段五：收口

- 停止主物理服务器匿名登记写入；
- 保留受保护的本地登记查看和导出；
- 验证云端只能通过服务身份被物理服务器主动访问；
- 完成清理、恢复和回退演练。

## 二十、测试计划

### 20.1 功能合同

- 场所新增、编辑、停用、移除和换码；
- 场所版本乱序到达时只接受更高版本；
- 有效、无效、停用和旧版本二维码；
- 表单令牌签发、过期、重复使用和并发消费；
- 姓名、身份证、手机号、地址和照片校验；
- 提交成功、失败和结果不确定。

### 20.2 可靠交付

- 同一 `submission_id` 重复提交和重复拉取；
- 拉取后 Worker 中断；
- 本地入库成功但确认丢失；
- 确认重复发送；
- 租约超时和重新分配；
- 云端、物理服务器、数据库和对象存储分别短时不可用；
- 积压数据恢复后按原顺序继续处理；
- 超过保留期的数据安全过期。

### 20.3 安全

- 未认证客户端无法调用内部接口；
- 过期签名、重放请求和错误证书被拒绝；
- SQL 注入、脚本内容、超长字段和异常 Unicode；
- 伪造扩展名、伪造 MIME、错误文件头和超大照片；
- 对象存储文件不可公开访问；
- 日志、指标和审计不含敏感正文；
- 云端主机没有滨湖平台数据库和内部系统凭据；
- 私钥不存在于云端、仓库、镜像和 CI 日志。

### 20.4 上线验收

- 手机不同网络可以打开云端二维码页面；
- 主物理服务器关闭匿名入口后，云端仍可接收；
- 物理服务器只通过出站 HTTPS 拉取；
- 虚构登记在本地只入库一次；
- 场所停用和换码状态两端一致；
- 云端确认后的正文和照片按策略删除；
- 云端故障不会影响滨湖平台其他页面；
- 回退后旧二维码和新二维码的处理边界明确。

## 二十一、是否需要 WebSocket、OT、OCC 或 Redis

首版不需要 WebSocket，也不需要操作变换 OT。

场所登记是一次性追加提交，不存在多人同时编辑同一份文档的问题。云端和本地之间使用租约、唯一 `submission_id`、幂等确认和场所 `config_revision` 即可解决并发与重复问题。

场所配置同步需要简单的乐观并发控制 OCC，即云端只接受更高 `config_revision`，但不需要复杂的文档协同算法。

首版也不强制引入 Redis。规模较小时，可以使用云端关系数据库状态表作为可靠队列，配合索引、租约和 `SKIP LOCKED` 等能力实现并发领取。后续只有在接收量、等待延迟或多消费者规模明显增加时，再评估 Redis Streams 或专用消息队列。正式数据状态仍必须落数据库，不能只存在 Redis。

## 二十二、待项目管理人确认

1. 云端正式域名和证书由谁申请、续期和监控？
2. 云服务器和对象存储所在地域是否满足单位数据合规要求？
3. 已确认、未确认和不确定数据在云端分别保留多久？
4. 物理服务器长期离线时，云端二维码继续接收还是自动暂停？
5. 是否需要在云端增加验证码，还是只使用分层限流和一次性表单令牌？
6. 是否要求照片进行病毒扫描或安全重新编码？
7. 内部服务认证采用双向 TLS、请求签名，还是两者同时使用？
8. 旧二维码采用临时重定向继续使用，还是统一换码重印？
9. 云端是否允许保留脱敏后的场所公开地址？首版建议不保留。
10. 云端故障和队列积压由哪一方接收告警并负责首响？

## 二十三、实施红线

- 不得把云服务器配置成滨湖平台数据库客户端；
- 不得把主物理服务器匿名写入接口继续暴露给云端或浏览器；
- 不得用共享管理员账号、Cookie 或用户 Token 认证内部服务；
- 不得在云端保存滨湖平台私钥或现有应用加密主密钥；
- 不得在日志、指标、错误追踪或消息队列名称中包含敏感正文；
- 不得在云端确认之前向管理员显示二维码已经启用；
- 不得在云端停用未确认时宣称旧二维码已经失效；
- 不得因确认超时自动重复写入本地业务数据；
- 不得把对象存储设为公共读；
- 不得在未完成旧二维码迁移和回退演练前切换生产域名。

## 二十四、参考基线

- NIST SP 800-207，Zero Trust Architecture：服务之间不因网络位置自动互信，应持续验证服务身份并实施最小权限。
- CISA 网络分段与公网服务加固建议：公网接收区应与内部业务系统隔离，限制横向访问。
- OWASP File Upload Cheat Sheet：文件上传应使用允许列表、大小限制、内容验证、安全文件名和非公开存储。

本报告只定义目标架构和双方合同边界，不代表已经完成云端部署、生产域名配置或真实数据迁移。
