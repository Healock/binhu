# Staging realistic load acceptance

The `run-staging-realistic-load` workflow exposes two fixed profiles: `full75` (75 users, spawn rate 5/sec, 30 minutes) and `low20` (20 users, spawn rate 2/sec, 10 minutes). Both run the same request model. `low20` selects a role-balanced subset of the 75 fictional accounts so member, leader, internal-business, admin, and super-admin actions remain represented. The profile cannot be customized with arbitrary user counts or durations.

The `low20` result is a reduced-load functional and resource check. It is explicitly not equivalent to, and cannot satisfy, the full 75-user Staging load gate. Reports carry the selected profile, exact user count, spawn rate, duration, role-balanced account selection, and this limitation.

The workflow-dispatch input `waive_4gib_memory_gate` defaults to `false`. For an explicitly authorized low-load run below the 4 GiB preflight threshold, set it to `true`. The report records the required and observed memory, waiver request, and whether the gate was actually waived. A waiver only bypasses that preflight; it does not change workload resource limits, functional/error/data-path thresholds, Production monitoring or stop conditions. If the memory gate was waived or `low20` was used, final Staging promotion evidence keeps `passed` and `promotion_ready` false while separately reporting whether the selected load profile passed.

The workflow records required and observed memory, waiver request, approval basis and whether the gate was actually waived in `load-report.json`.

Before creating fixtures, preflight verifies the Staging run identity, Staging bootstrap identity, Production bootstrap identity, Production health, the fixed Production container set, and Staging service state. The restricted Staging gateway samples only fixed Production endpoints on `127.0.0.1:37125` and the fixed containers `binhu-backend`, `binhu-mysql`, and `binhu-ops-agent`. It emits aggregate status, restart/OOM state, and an error-line count; it never includes log or response bodies. Production log sampling uses one fixed run-start timestamp, a 5,000-line limit and an 8 MiB output limit. Inspection failure, identity mismatch, counter regression, or sampling-limit overflow fails closed.

The pipeline candidate ID and load-run ID are separate identities and must both use the Staging run format while remaining different. The gateway binds them to the applied candidate manifest, the current Staging application manifest, live backend/container project labels, and exact image digests; workflow input alone does not authorize a candidate. Every task row key, including the preferred Suzhou police case-number key, is namespaced by the load-run ID. Seed evidence records exactly 1,440 unique task row keys/source IDs, conflicts, and committed fictional account/community upsert attempts. Seed validation and query smoke are separate workflow steps; Locust is only marked started after both pass. A failed seed is a preload failure, not a Locust result, and its server evidence is not overwritten by a retry.

During Locust, the workflow samples every 30 seconds. It terminates Locust if Production health fails twice consecutively, a fixed Production container becomes unhealthy/restarts/OOMs, a new Production error line appears, or the monitor cannot complete. Staging service/pipeline OOM or restart, persistent request failure above 2% for 60 seconds, request stalls, and sampling failures also stop the run. Stop reasons and execution policy are preserved in the run artifacts.

Both profiles exercise login, core business operations, polling, SSE/WebSocket streams, token refresh, multi-client sessions, reconnects and retry behavior. Production health, Staging service/pipeline health, error rate, request progress, and derived-queue drain checks remain active in both profiles. A resource-gate waiver does not establish that the run passed the 4 GiB precondition.
